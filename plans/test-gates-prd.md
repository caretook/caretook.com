B-531 (modes) is dropped. B-532 (the staging candidate) and B-533 (the staging to main gate) are the follow-on topic `test-gates-2`.

**The skeptic pass (Fable)**, on this rewrite, found these, all fixed above and in the plan:

- A merged slice's worktree is removed, so an idle agent had nowhere to fix.
- A quarantine commit counted as dev drift for every branch, and a flake landing refused itself.
- A narrowed run could pass the gate, and dev's tip can't carry a file list.
- `scripts/ci/` was in no test project and no path rule.
- The workflow slice was too big, and its green `full` run could hang on tests that have never run on Linux: split in two, and a Linux-only failure is filed, not a blocker.
- The last wave's two slices depend on each other, and nothing said which gate lands it.
- A brake dev already had was neither blamed nor filed.
- The `ci/` ref: a push of the same commit starts nothing, a delete at the timeout breaks a rerun, and a cancelled run had no kind.
- After the gate changes, nothing checked dev as a whole.
- The modes' confirmation point differed between the two documents.
- Slices were told to fold docs, which loops never do, into docs with no room.
- A flake the branch introduced was quarantined and landed.

## Problem

Checks take longer than the work they guard, and most failures are not about the change.

- A slice's quick check took a median 7.9 minutes over 111 runs since 2026-11-21, and 30 of them failed. It ran 22% of the test files on average but took 72% of a full check's time.
- Two causes: the static steps run one after another (2.2 minutes on a quiet machine, about 4 under load), and nearly any app change selects all 160 component tests, because the test harness imports the app shell.
- Chromium tests in bulk are what loads the machine and what flakes under load. About 30 backlog items are tests that fail only in a busy full check.
- The log keeps only an exit code, so nobody can say which test failed, and four runs hung for 28 to 93 minutes.
- Nothing runs in CI at all.

## Solution

Three levels, each slower and stricter than the one before:

| Level                                        | Runs                                                                                                   | Where                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------- |
| A slice hands off                            | typecheck, lint, format, every unit test, the slice's own integration and component test files         | local, about 2.5 minutes  |
| The orchestrator merges a slice or syncs dev | the same, plus the integration tests related to the merge; then the tier it asks CI for, on the branch | local, then CI on request |
| A landing into dev                           | the tier the orchestrator declared, read by its kinds                                                  | CI on request             |

Dev itself is checked when it is promoted to staging (`test-gates-2`).

## User stories

1. As the user, I want a slice's check to take a couple of minutes, so that loops spend their time building.
2. As the user, I want slice agents to run only the Chromium tests they wrote or changed, so that the machine stays quiet and flakes stop failing unrelated work.
3. As an orchestrator, I want to ask CI for a tier on any branch, so that I pay for only as much of the suite as the change needs.
4. As an orchestrator, I want a failed run sorted into brake, file, flake or infra with the failing tests named, so that I know what blocks and what is filed.
5. As an orchestrator, I want to know whether my branch or dev caused a failure, so that I fix mine and file dev's without asking.
6. As an orchestrator, I want to send a failure to the agent that wrote the slice, so that the fix comes from the context that made the change.
7. As the user, I want a test that passes on a rerun quarantined and filed, so that flakes stop blocking anyone but still get fixed.
8. As the user, I want the landing report to say which tier ran and why, so that I can see how well a landing was checked.
9. As the user, I want nothing to run in CI unless someone asked, so that a push or a PR never starts a suite by itself.
10. As the user, I want to see which step and which tests failed a local check, and a check that stops at a time limit, so that failures can be counted and nothing hangs for an hour.
11. As the user, I want a GitHub outage to report itself and retry once, not block every landing.

## Implementation decisions

- **The CI workflow** runs on a push to a `ci/**` ref and on nothing else.
  - The ref names the tier; the workflow runs the jobs that tier includes: static (format, lint, typecheck); unit (the six small Vitest projects, `tooling:unit` without the browser harness test); integration (a Postgres service container on the test port, and the browser harness test); components (Playwright's Chromium); build (the build budget, `build:native`, the `caretookSync` grep).
  - A run can be narrowed to named test files (the blame rerun): a throwaway commit on top of the target, with a verdict marked narrowed.
  - A test job that fails reruns only its failed files once, in the same job, and records both results. A separate step runs the quarantined tests and can't fail the run.
  - The last job writes and uploads the verdict (kept 7 days).
  - `scripts/deploy/workflows.test.mjs` and its YAML reader learn the workflow's shapes.
- **The verdict module** is pure and unit-tested. In: the tier, the jobs' results, the test results before and after the rerun, the brake list and the quarantine. Out: one verdict, `green`, `brake`, `file`, `flake` or `infra`, with the failing jobs, files and tests, the commit and the tier.
- **The CI command** (`pnpm prd ci`):
  - `run <tier> [--ref <branch>] [--files …] [--wait]` pushes the ref, and with `--wait` blocks until the verdict (exit codes by kind; 75 at the timeout), deletes the ref and writes the commit status.
  - With no arguments, or a branch, it prints the latest verdict for that branch's tip.
  - `blame` reruns the failed files of a `file` or `brake` verdict on dev's tip and splits them into the branch's and dev's.
  - It files on a transition: a dev failure gets one `fixes-bug` item per test (later runs add a note); a flake in a file the branch didn't touch gets a `fixes-tooling` item and a quarantine entry, unless it is on the brake list; a dev brake also posts a notice.
  - An unreachable GitHub reads as unknown, never green. An infra verdict is rerun once.
- **The brake list and the quarantine** are committed lists beside the workflow, each with a header saying who writes it. A Vitest setup skips quarantined tests unless the run's quarantine step asks for them.
- **The landing gate:** the check plan proposes a minimum tier from the diff (pure, tested). `pnpm prd pr` and `land` take the declared tier, and a reason when it is below the proposal.
  - `land` needs a verdict for that tier or higher on the tip: green lands; flake lands when the flakes are in files the branch didn't touch, and files them after the merge; file lands when every failure is dev's, and otherwise refuses naming the tests; brake refuses, unless it is dev's and this landing fixes it; unknown and infra refuse with how to retry. A narrowed verdict never counts.
  - `--force` works on the user's word, as today.
  - The local full check is no longer a gate; `pnpm prd check` still runs it for anyone who asks.
- **The local check runner:** the log gains the failed step and the failed test files; a check stops at a time limit and says so; a failed test file reruns once alone before the check fails, and a pass on the rerun is logged as a flake; the static steps get faster (measured first: typegen runs twice, and three whole-repo passes run in series).
- **The orchestrator's flow** (its handbook and prompts): the quick check on each slice merge and dev sync; the requested tier at the wave gate; failures sent to the slice's agent; slice worktrees kept until the wave is green; no rotation until the wave's run is back; idle slices without a stack.

## Testing decisions

- Unit tests cover: the verdict module (every kind, the rerun, quarantine, infra, the tier); the tier proposal in the check plan; the blame split; the filing's transitions; the check runner's log line, time limit and rerun.
- Prior art: `check-plan.test.mjs`, `check-body.test.mjs`, `check-run.test.mjs`, `codex-review.test.mjs` (fixtures of `gh` output), `land.test.mjs`.
- `land.test.mjs` cases for each kind against the declared tier, and for a tier below the proposal with and without a reason.
- The workflow is proven by real requested runs from the slice's own branch, linked in the hand-off: one green, one with a failing test, one with a test forced to fail once and then pass.

## Out of scope

- The staging candidate, the staging to main gate and required status checks: `test-gates-2` (B-532, B-533).
- Modes (B-531): dropped.
- Selecting component tests by area for the orchestrator: CI runs them all, so nothing local needs it.
- Fixing the flakes themselves: fixes-tooling. Most are load flakes and should be re-tested once Chromium leaves the Mac.
