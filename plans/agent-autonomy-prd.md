## Problem

The user starts a dispatcher and leaves. Overnight on 2026-11-22 two run-through orchestrators stopped for hours:

- test-health asked whether to land on passes it already had (a31) and waited six hours for the answer it had recommended.
- fixes-bug and ui-kit-2 ran full checks at the same time on ten cores (load over 20), failed each other on load flakes seven times, and then asked (a33). Every failing test passed alone.

And every landing makes the others redo work. When dev moves, `pnpm prd land` refuses until the branch syncs, and the sync makes the last check stale: a sync and a quick check again, even when the two sides never touched the same file. With the full check moved into CI (test-gates), that sync and recheck is the main local cost left per landing.

## Solution

The user comes back to landed work and a short list of what was decided without them.

- ✅ A routine question takes its recommended answer after 30 minutes of silence. The list of asks shows what was decided that way. Questions about money, data, a live deploy, a destructive step or compliance still wait.
- ✅ Sessions leave short, expiring heads-ups on a shared board that the tools print for everyone; a landing posts "landed, sync at your next wave boundary".
- A branch whose files dev's new commits didn't touch lands without syncing: land typechecks the merge, and the landing report says so.

## User stories

1. As the user, I want a routine question to take its recommended answer after about 30 minutes without me, so that a run doesn't stall overnight on an answer I would have given. (B-503)
2. As the user, I want every defaulted question listed with what was chosen and when, so that I can see what was decided without me. (B-503)
3. As the user, I want questions about money, data loss, a live deploy, a destructive step or compliance to wait for me however long it takes, so that nothing costly happens by default. (B-503)
4. As the user, I want the push for a defaulting question to say when it will default and to what, so that I know how long I have. (B-503)
5. As an orchestrator, I want `pnpm prd ask --wait` to return the default like any answer, so that I carry on the same way. (B-503)
6. As a planner the dispatcher started, I want my recommended questions to default after 30 minutes like any other, outside the never list, so that planning doesn't stall overnight either. (B-503, the user's note)
7. As an orchestrator, I want to post a short heads-up that expires, and to see other sessions' heads-ups before each step without asking for them. (B-506)
8. As an orchestrator, I want a landing to tell the others to sync by itself. (B-506)
9. As an orchestrator, I want to land without syncing when dev's new commits touch none of my files and none of the risky ones, with land typechecking the merge, so that I don't sync and check again for nothing. (B-518)
10. As the user, I want the landing report to say a landing went in on an unsynced tip, so that I know what was only typechecked together. (B-518)

## Implementation decisions

### Asks that default (stories 1 to 6)

- **The ask record** gains: whether it may default, when it would (`askedAt` plus the wait at filing), and, once settled that way, that it was defaulted. A defaulted ask has an answer (the recommendation) and an answer time like any other.
- **Filing:** `pnpm prd ask --question … --recommend <a>` takes `--defaults` or `--waits`. With a recommendation and neither flag it files nothing and exits non-zero, naming the two flags and the never-default classes. `--defaults` without a recommendation is refused. A question with no recommendation waits. A report is unchanged.
- **Settling** is one store function, "apply this ask's default if it is due": it writes the default only when the ask is still unanswered and not dismissed. Settling and answering share one exclusive step per ask (a lock taken atomically, as creating an ask takes its id), so neither can overwrite the other and a user's answer that got there first always stands. `--wait` and the dispatcher's tick call it, so a question whose session died still settles while the dispatcher runs, and its reopened session finds the answer. Reading the list never settles: with no session waiting and no dispatcher, a due question stays open and answerable.
- **`--wait`** prints the answer as today; for a default it adds one line saying it was defaulted after the wait.
- **The filing output:** the push line a defaulting question prints ends with the time it defaults and the option it takes. A waiting question's line is unchanged.
- **Listing:** `pnpm prd asks` shows, for an open defaulting question, how long until it defaults (or that it is due); and lists defaulted questions under their own heading until dismissed (`--done`). `pnpm prd answer` on a defaulted ask is refused and says why.
- **Two predicates, not one:** "awaits an answer" (an open question, not defaulted) and "still listed" (also defaulted-and-undismissed, and reports). The dispatcher's "a topic with an open question" uses the first.
- **Prompts:** the run-through orchestrator's asking paragraph says to pass `--defaults` on every question with a recommendation except the never-default classes, which take `--waits`, and that the tool, never the agent, puts the recommendation in place of an answer. The unattended planner's line follows the same rule: `--defaults` on a question with a recommendation, `--waits` for the never list. An attended planner asks with AskUserQuestion in front of the user, so nothing defaults there. The dispatcher files its own question as waiting.

### The notice board (stories 7, 8)

- **A notice** is one small file in the main checkout's `.loops/`: an id, the posting session and topic, one line of text (200 characters at most), when it was posted and when it expires.
- **Commands:** `pnpm prd notice "<text>" [--for <minutes>] [--topic <t>]` prints the id; `pnpm prd notices [--json]` lists the live ones, oldest first; `pnpm prd notices --done <id>` withdraws one. Every write and list deletes expired files. Life: 60 minutes by default, 24 hours at most.
- **Shown without asking:** `pnpm prd status` prints the live notices; `check`, `sync`, `slice`, `browser`, `pr`, `ready` and `land` print other sessions' live notices first (at most five lines, to stderr, never failing the command).
- **Posted by tools:** a code landing (`prd/` or `hotfix/`, not Markdown only) posts "landed `<topic>` in dev (`<sha>`): sync at your next wave boundary", living six hours. A failure to post never fails the command.
- **When an agent posts** (the orchestrator handbook): before changing a file another running topic lists as hot ("sync first"), and for anything the leases and the load gate can't say. Never to ask a question: nothing reads replies.

### What dev brought (story 9)

- **One pure module** answers "what did dev bring since this branch last synced, and does it touch the branch?" Given a checkout, dev's ref and the tip, it returns the branch's own files (`dev...tip`), the files dev changed since the branch's merge base with dev, the incoming dev commits (first parent), whether the two sides share a file (the backlog files excluded), and the risky files on dev's side. It diffs with `--no-renames`, so a file dev renamed shows on dev's side under both paths. A refusal reads like the Codex carry's ("`dev` changed `<file>`, which the branch touches"). Anything git can't answer is a refusal.
- **The risky files** are one list: `check-plan.mjs`'s forced-full list (a migration, seeds, `sync-config.yaml`, the lockfile, a `package.json`, `vitest.config.ts`), exported once, plus what reaches code without an import: the test setup directories (`packages/*/test/`, `apps/web/test/`), the Vite and TypeScript configs (`vite.config.*`, `tsconfig*.json`) and `pnpm-workspace.yaml`; and, since the unsynced landing only typechecks and test-gates brakes dev on a format or lint failure, the lint and format config (`eslint.config.js`, `scripts/eslint/`, the Prettier config and ignore file). test-gates stops the check plan escalating on that list in rapid mode but keeps the list; this module reads the same export.

### Land on an unsynced tip (stories 9, 10)

- **When `land` finds drift** (dev changed files since the branch last synced), after test-gates' brake check, it asks the module. It goes ahead when the files dev changed since the last sync share none with the branch's own diff and dev brought no risky file. Every other refusal (the brake, the check gate on the tip, the PR and its verdict, the doc budget) stays. In pre-deployment mode (`pnpm prd mode`) it never relaxes.
- **Where it sits in `land`:** after test-gates' CI read and after `--recheck` (which runs and releases its own check lease), before the PR merge and the throwaway seam's exit, so the seam tests reach it. A leftover marked merge (below) is aborted first, before the uncommitted-changes refusal. **The typecheck** runs in a check lease and is refused while the branch's worktree holds a check or browser lease of its own. It runs in the branch's worktree: a merge of dev with no commit (`--no-commit --no-ff`), then `pnpm typegen` and `pnpm typecheck` (route types first, since dev may have brought a route), then the worktree is put back to the tip on every exit it can catch. A marker beside the merge lets the next `land`, `check` or `sync` in that worktree abort a merge a kill left behind. A failure lands nothing and says to sync. A merge that conflicts is aborted and refused, and the worktree restored. A branch whose diff is Markdown only (`docs_only`) skips the typecheck, whatever its kind, and needs no worktree (as land allows today). A branch that needs the typecheck and has no worktree, or a dirty one, keeps today's drift refusal. `pnpm prd sync` in the worktree also aborts a leftover marked merge. Dev is read again after the typecheck: if it moved, land judges once more, and refuses rather than looping.
- **The merge** is the branch's unsynced tip, as on the PR path today: GitHub merges the PR's head, pinned with `--match-head-commit`, with the unsynced line in its body (`gh pr merge --body`; a second `-m` on the local path). The landing report says "landed on an unsynced tip: `dev` had `<n>` commits since the last sync, sharing no file with it; only the merged result's typecheck ran", and the run-through report repeats it. Nothing tests the merged result beyond that typecheck until someone requests a dev run (test-gates ended the automatic ones).
- The branch syncs at its next wave as usual. `CARETOOK_UNSYNCED=off` restores the refusal.

## Testing decisions

- Everything is tooling, tested as unit tests in the tooling project beside the code, against temporary directories and stub binaries; never the real asks queue, leases, backlog or `origin`. Prior art: the landing tests, the Codex carry's tests (throwaway git repositories in a temporary directory), the check-gate tests.
- Pure parts tested alone: the module's sides, shared files and risky files, over throwaway repositories.
- Commands: a landing with drift that lands unsynced through the `CARETOOK_PR_THROWAWAY` seam with a stub `pnpm` for the typecheck; the refusals (shared file, risky file, brake, pre-deployment mode, a dirty or missing worktree).
- No app code changes, so no component, integration or browser checks; each landing runs `pnpm test:tooling` and `pnpm exec eslint scripts`.
