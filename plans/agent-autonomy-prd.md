## Problem

The user starts a dispatcher and leaves. Overnight on 2026-11-22 two run-through orchestrators stopped for hours:

- test-health asked whether to land on passes it already had (a31) and waited six hours for the answer it had recommended.
- fixes-bug and ui-kit-2 ran full checks at the same time on ten cores (load over 20), failed each other on load flakes seven times, and then asked (a33). Every failing test passed alone.

Agents also can't tell each other "I'm landing, hold your full check" or "I'm changing this hot file" without a message and a reply.

And every landing makes the others redo work. When dev moves, `pnpm prd land` refuses until the branch syncs, and the sync makes the last check stale. The quick check that follows runs every test related to what dev brought. After a big landing that is over half the suite, even when the two sides never touched the same file. An orchestrator that full-checks while another landing is on its way then checks twice.

## Solution

The user comes back to landed work and a short list of what was decided without them.

- A routine question takes its recommended answer after 30 minutes of silence. The list of asks shows what was decided that way. Questions about money, data, a live deploy, a destructive step or compliance still wait.
- A landing's full check gets the machine to itself: other checks and new slices wait their turn, for a bounded time.
- A full check that fails only on tests that pass alone lands anyway, and each flaky test is filed as a bug.
- Sessions leave short, expiring heads-ups on a shared board that the tools print for everyone.
- A landing says when it's coming and when it has landed, and what it touches. A full check that would be wasted by it waits for it.
- A sync that brings only fully checked work on other files keeps the full pass: only the tests that depend on both sides run again.
- A branch whose files dev's new commits didn't touch lands without syncing: land typechecks the merge, and the landing report says so.

## Implementation decisions

### Asks that default (stories 1 to 6)

- **The ask record** gains: whether it may default, when it would (`askedAt` plus the wait at filing), and, once settled that way, that it was defaulted. A defaulted ask has an answer (the recommendation) and an answer time like any other.
- **Filing:** `pnpm prd ask --question … --recommend <a>` takes `--defaults` or `--waits`. With a recommendation and neither flag it files nothing and exits non-zero, naming the two flags and the never-default classes. `--defaults` without a recommendation is refused. A question with no recommendation waits. A report is unchanged.
- **Settling** is one store function, "apply this ask's default if it is due": it writes the default only when the ask is still unanswered and not dismissed. Settling and answering share one exclusive step per ask (a lock taken atomically, as creating an ask takes its id), so neither can overwrite the other and a user's answer that got there first always stands. `--wait` and the dispatcher's tick call it, so a question whose session died still settles while the dispatcher runs, and its reopened session finds the answer. Reading the list never settles: with no session waiting and no dispatcher, a due question stays open and answerable.
- **`--wait`** prints the answer as today; for a default it adds one line saying it was defaulted after the wait.
- **The filing output:** the push line a defaulting question prints ends with the time it defaults and the option it takes. A waiting question's line is unchanged.
- **Listing:** `pnpm prd asks` shows, for an open defaulting question, how long until it defaults (or that it is due); and lists defaulted questions under their own heading until dismissed (`--done`). `pnpm prd answer` on a defaulted ask is refused and says why.
- **Two predicates, not one:** "awaits an answer" (an open question, not defaulted) and "still listed" (also defaulted-and-undismissed, and reports). The dispatcher's "a topic with an open question" uses the first.
- **Prompts:** the run-through orchestrator's asking paragraph says to pass `--defaults` on every question with a recommendation except the never-default classes, which take `--waits`, and that the tool, never the agent, puts the recommendation in place of an answer. The unattended planner's line follows the same rule: `--defaults` on a question with a recommendation, `--waits` for the never list. An attended planner asks with AskUserQuestion in front of the user, so nothing defaults there. The dispatcher files its own question as waiting.

### The notice board (stories 14, 15)

- **A notice** is one small file in the main checkout's `.loops/`: an id, the posting session and topic, one line of text (200 characters at most), when it was posted and when it expires.
- **Commands:** `pnpm prd notice "<text>" [--for <minutes>] [--topic <t>]` prints the id; `pnpm prd notices [--json]` lists the live ones, oldest first; `pnpm prd notices --done <id>` withdraws one. Every write and list deletes expired files. Life: 60 minutes by default, 24 hours at most.
- **Shown without asking:** `pnpm prd status` prints the live notices; `check`, `sync`, `slice`, `browser`, `pr`, `ready` and `land` print other sessions' live notices first (at most five lines, to stderr, never failing the command).
- **Posted by tools:** a code landing (`prd/` or `hotfix/`, not Markdown only) posts "landed `<topic>` in dev (`<sha>`): sync at your next wave boundary", living six hours. The machine claim posts its own (below). A failure to post never fails the command.
- **When an agent posts** (the orchestrator handbook): before changing a file another running topic lists as hot ("sync first"), and for anything the leases, the claim and the load gate can't say. Never to ask a question: nothing reads replies.

### The machine claim (stories 7 to 10)

- **One claim, machine-wide**, a lease of its own kind with one slot, taken over from a dead holder like any lease. Claimers queue in arrival order: each waiter leaves a ticket, and the oldest live ticket takes the claim when it frees.
- **Who claims:** a full check (after the check plan has decided the mode) in a `prd/` or `hotfix/` worktree. `CARETOOK_QUIET=off` turns the claim and the waits off, as does `CARETOOK_LEASES=off`.
- **The claimer**, holding the claim, waits until no other check or browser lease is held and the 1-minute load is at or under the core count (`CARETOOK_QUIET_LOAD`), for at most `CARETOOK_QUIET_SETTLE` (600 s), then runs and says whether the machine was quiet. This replaces the load gate's wait for that check. It posts a notice for the claim's life: "`<session>`: landing check until `<time>`: checks, browser checks and slice starts wait".
- **Everyone else:** `pnpm prd check` (before taking a check lease), a browser check (before its browser lease) and a slice worktree's creation wait while another worktree holds the claim or queues for it, until none does or the waiter itself has waited `CARETOOK_QUIET_MAX` (2700 s; a slice's creation at most the load gate's `CARETOOK_LOAD_WAIT`, 600 s, since orchestrators run it in the foreground), then go ahead and say which. The bound is the waiter's own time, so a queue of landings can't hold it longer. A queued claimer also waits before taking its check lease, so the holder's wait for quiet never waits on it. The dispatcher's facts gain "claimed", which stops starts and plans like "busy" with its own reason. Running agents, quick edits and single test files run by hand are not held.
- **The check-times log** gains two fields at the end: the seconds waited for the claim or for quiet, and whether the check ran quiet. `pnpm prd status` prints the holder, its age and the queue.

### The flake rule (stories 11 to 13)

- **The full check's test step leaves a machine-readable result** (Vitest's JSON reporter beside the usual output; no new dependency): the test files that failed and the failing test names. A test keeps the full check's steps the same as `pnpm check`'s.
- **The rule** is a pure decision over that result: "real" when a non-test step failed, when there is no result, when the test step failed with no failed file named (a crash, an unhandled error, a teardown timeout), when more than `CARETOOK_FLAKE_MAX` (8) files failed; else "retry these files". It runs for every full check in a `prd/` or `hotfix/` worktree, whether or not the check got the claim; `CARETOOK_FLAKE_RULE=off` disables it. A failed check's last lines always say whether the rule ran and what it decided, or why it didn't run.
- **The retry** first waits for quiet again (the claimer's test, at most `CARETOOK_QUIET_SETTLE`; no wait with `CARETOOK_QUIET=off`) and says whether it got it, so a check that started loaded still retries on the quietest machine it can get. Then each failed file alone, three times, in its own project; any failure makes the check fail as today, naming the file. Then the failed files together, once. All passing, the remaining steps of the check run (the build budget, the tooling tests), and the tip is recorded as a full pass that names its flaky files. The tooling tests' failures follow the same rule.
- **The gate** (`pnpm prd land`, `ready`) accepts that record as full and says "full, N flaky test files rerun". The landing report lists them under what wasn't checked.
- **The flake ledger:** one line per flaky file per check in the main checkout's `.loops/` (time, branch, commit, file, failing test names, load).
- **Filing:** after a flaky pass the check files each ledger line not yet filed: when an open item (not landed or dropped) in `fixes-tooling` names the test file, a note on it ("seen again `<date>` on `<branch>`, load `<n>`"); else a new bug, "Flaky under load: `<file>` '`<test>`' fails in a full check; passes alone 3/3", `prd=fixes-tooling`, triaged. Filing goes through `pnpm backlog` and never fails the check; `pnpm prd flakes` lists the ledger and `pnpm prd flakes --file` files what's left.
- **The rules that change:** the orchestrator handbook's "never `--force` unless the user says so" stays; the flake rule needs no force. A check the rule called real goes back to the loop that caused it, as today, with the rule's last lines: a file that failed alone is a broken test; files that pass alone and fail together are an order or shared-state bug. Asking about flakes stops. The one question left: the same tip failing for real twice with nothing a loop can fix is asked as any real failure is.

### What dev brought: one verdict for the sync, the gate and the hold (stories 16 to 21)

- **One pure module** answers "what did dev bring since this branch's checked point, and does it matter?" Given a checkout, dev's ref, a checked commit and a tip, it returns the two sides' files, the dev commits that came in (first parent), how each of them landed, the risky files on each side, whether every merge of dev since the checked commit is plain, and one verdict: carry, or a refusal with its reason. A refusal reads like the Codex carry's ("`dev` changed `<file>`, which the branch touches"). The Codex carry and this module share the plain-merge test, so the two agree. Anything git can't answer is a refusal.
- **The carry-risky files** are one list. It starts from `check-plan.mjs`'s forced-full list (a migration, seeds, `sync-config.yaml`, the lockfile, a `package.json`, `vitest.config.ts`), exported once. It adds what reaches tests without an import: the test setup directories (`packages/*/test/`, `apps/web/test/`), the Vite and TypeScript configs (`vite.config.*`, `tsconfig*.json`) and `pnpm-workspace.yaml`. The carry, the unsynced landing and the hold read it; the check plan keeps its own list.
- **The `Checked:` trailer.** Every `prd/`, `hotfix/` and `plan/` landing writes one trailer line in its merge commit's body, saying how the tip passed the gate: `full <sha>`, `full <sha> flaky <n>`, `full <sha> carried <from>`, `quick <sha>`, `none`, `forced`, with ` unsynced` appended by B-518. It goes in through `gh pr merge --body` on the PR path and a second `-m` on the local path. The commit hook reads only the subject, so nothing else changes. "Landed through a full check" is a pure reading of a commit: its trailer is full and not unsynced, or it touches only `plans/backlog.md`, `plans/inbox.md`, Markdown or the tooling. A commit with no trailer, from before slice 7 or committed straight onto dev, doesn't count.

### A full pass carries over a dev sync (stories 16, 17)

- **When:** the check record is a full pass (plain, flaky or carried) on a commit `F`, and the tip is a descendant of `F`. Every branch commit since `F` that isn't dev's is Markdown or tooling only, or a plain merge of dev (its tree is `git merge-tree`'s for its parents, the Codex carry's test). Then the two sides are computed. The branch side is `dev`'s merge base with `F`, up to `F`. The dev side is that merge base up to dev's merge base with the tip. Excluding the backlog files, they share no file. Neither side has a risky file. Every incoming dev commit landed through a full check.
- **What runs** (`pnpm prd check --quick "<why>"`, so also `land --recheck`, picks it by itself when the verdict is carry): typecheck and lint. Then the test files related to both sides: those that depend, in Vitest's own module graph (no new dependency), on a file changed on each side, or that were changed on one side and depend on a file of the other. Then the always-run list, the check-areas lint and the docs budget. The tooling tests join when both sides touch the tooling. If the related files can't be worked out, it runs today's quick instead and says why.
- **The record:** `<tip> full carried <F> <why>`. A carried check that fails leaves the full record as it was (today's check deletes the record before it runs), so the next try can carry again. Older readers read the first two fields, so it is a full pass to them. `checked_how` says "full on `<F>`, carried over a dev sync to `<tip>` (`<n>` related test files)". The landing report lists it under what wasn't checked: "the full check ran on `<F>`; the sync to `<tip>` ran typecheck, lint and the `<n>` tests related to both sides". A carried record can itself be carried by a later sync. The check-times log's mode is `carry`.
- **Otherwise** `--quick` runs today's quick, and its first line gives the verdict's reason. `pnpm prd sync` prints the verdict after its merge: either "the full pass on `<F>` carries: `pnpm prd check --quick "dev sync"` runs only `<n>` related tests", or why it doesn't. `CARETOOK_CARRY=off` turns it off.
- The carried check takes a check lease like any check, but no machine claim, and the flake rule doesn't apply: it isn't a full check.

### Land on an unsynced tip (stories 18, 19)

- **When `land` finds drift** (dev changed files since the branch last synced) it asks the module, with the branch tip as the checked point. It goes ahead when the files dev changed since the last sync share none with the branch's own diff, and dev brought no risky file. The item asks only that dev's incoming commits are risky-free. Whether they landed through a full check doesn't matter here. Every other refusal (the check gate on the tip, the PR and its verdict, the doc budget) stays as it is.
- **The typecheck** runs in a check lease, after waiting for another worktree's machine claim like any check, and is refused while the branch's worktree holds a check or browser lease of its own. It runs in the branch's worktree: a merge of dev with no commit (`--no-commit --no-ff`), then `pnpm typegen` and `pnpm typecheck` (route types first, since dev may have brought a route), then the worktree is put back to the tip on every exit it can catch. A marker beside the merge lets the next `land` or `check` in that worktree abort a merge a kill left behind. A failure lands nothing and says to sync. A branch whose diff is Markdown only (`docs_only`) skips the typecheck, whatever its kind. A branch with no worktree, or with a dirty one, is refused as today. Dev is read again after the typecheck: if it moved, land judges once more, and refuses rather than looping.
- **The merge** is the branch's unsynced tip, as on the PR path today: GitHub merges the PR's head, pinned with `--match-head-commit`. Its trailer ends in ` unsynced`, so the next carry over it doesn't count it as fully checked. The landing report says "landed on an unsynced tip: `dev` had `<n>` commits since the last sync, sharing no file with it; only the merged result's typecheck ran", and the run-through report repeats it.
- The branch syncs at its next wave as usual. `CARETOOK_UNSYNCED=off` restores the refusal.

### Landing notices and the hold (stories 20, 21)

- **The landing notice** is a notice with a kind (`landing`) and fields beside its line, which the store keeps and the listing's `--json` shows. The fields are the topic, the branch, the expected check end, the areas, the touched hot prefixes, the branch's changed files (dev...tip, at most a few hundred paths; past that it counts as touching everything) and whether it has a risky file. Every full check in a `prd/` or `hotfix/` worktree posts it when it starts, before it queues for the claim, and with no claim at all (`CARETOOK_QUIET=off`). It replaces the topic's earlier landing notice, and it records the checked tip; readers treat it as ended once the branch has a code commit past that tip, or is gone (a wave sent back to a loop). The line reads "landing `<topic>`: full check until about `<time>`, then the PR; areas `<a>, <b>`; hot `<prefix>`". On a pass it stays. On a failure it is withdrawn. At the merge, land withdraws it and posts the landed notice. Two hours at most.
- **The landed notice** (slice 2's, six hours) gains the same fields and a line naming the areas.
- **The areas** come from `check-areas.mjs`: the rule file that answers for each changed file (`_global` left out). **The hot prefixes** are the other running or planned topics' hot prefixes from the PRD table that the files match.
- **The hold:** a full check in a `prd/` or `hotfix/` worktree reads the live landing notices of other topics posted before its own, when it starts and again when it gets the claim (a landing queued ahead of it may have posted meanwhile). Only earlier notices count, so two overlapping landings never wait on each other. For each, it asks the module's pure overlap test whether that landing, once in dev, would stop its own pass carrying over: a shared file, or a risky file on either side. If any would, it waits until the notice ends, polling, for at most `CARETOOK_LANDING_HOLD` (3600 s), and prints which landing it waits for. If a landed notice replaced it, the check stops with its own exit code, keeps the record it had, and says "`<topic>` landed in dev and touches your files: `pnpm prd sync`, then `pnpm prd check`". On a withdrawal, an expiry or the limit it runs, and says which. A landing that doesn't overlap never holds it. `CARETOOK_QUIET=off` turns the hold off with the claim.
- **The orchestrator's landing steps:** the check's exit tells it to sync and check again. The SendMessage round at step 7 is gone (slice 2's change).

## Testing decisions

- Everything is tooling, tested as unit tests in the tooling project beside the code, against temporary directories, a stand-in load file and stub binaries; never the real asks queue, leases, backlog or `origin`. Prior art: the asks store and command tests, the lease tests, the load-gate tests, the check-run and check-gate tests, the dispatcher pick tests, the landing tests.
- Pure parts tested alone: the default's due time and settling, the notice store, the claim queue's order, the dispatcher pick with "claimed", the flake decision, the match of a flaky file to an open item, the trailer's writing and reading, the module's verdict and overlap test (over throwaway git repositories built in a temporary directory, as the Codex carry's tests do), the related-files choice over a stub module graph.
- Commands tested through their command line with a fake clock or short settings: an ask that defaults under `--wait`; a check that waits for a claim and one that gives up at the limit; a full check with a stub test step that fails then passes alone; a sync followed by a quick check that carries; a landing with drift that lands unsynced through the `CARETOOK_PR_THROWAWAY` seam with a stub `pnpm` for the typecheck (the printed merge carries the trailer); a full check held by a landing notice and released by a landed one.
- Prompt tests cover the changed prompt lines.
- No app code changes, so no component, integration or browser checks. The gate needs none; each landing runs `pnpm test:tooling` and `pnpm exec eslint scripts`.
