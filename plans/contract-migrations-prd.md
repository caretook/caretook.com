## Problem

From the side of whoever runs Caretook's database and sync:

- `care_group_member.simple_mode` and `simple_mode_locked`, `care_group.simple_tiles` and the `simpleMode` preference key have been unread since the easy roles, but the Drizzle schema still names them, so every member read selects them and they can't be dropped yet. They keep `care_group` and `care_group_member` on the replication role's whole-table list.
- `appointment_series` still allows the `note` kind, and stored note series (repeating reminders from before planner-2) sit in the table, skipped by every reader.
- `todo.event_id` is still written: the server mirrors an old client's `eventId` into a link row, clears it when an event is deleted or unlinked, takes it on upload and syncs it, although link rows (`timeline_entry_todo`) replaced it in planner-3.
- Groups made before default med times existed would have none (every create path has added them since 2026-11-19).

## Solution

- **The note kind goes:** one migration deletes stored note series (their notes stay) and narrows the check to `event`.
- **`todo.event_id` stops moving:** no service writes it, no upload carries it, no device receives it; `todo` joins the whole-table list until its drop.
- **Older groups get their med times**, and their 08:00 and 20:00 doses join them.
- **The simple-mode columns leave the Drizzle schema**, ready for `contract-migrations-2` to drop them a deploy later.

Nothing a member sees changes.

## User stories

1. As the operator, I want the retired simple-mode columns out of the Drizzle schema, so that a later migration can drop them without breaking live or rolled-back code. (B-455)
2. As the operator, I want no note series left and the database to allow event series only, so that a reminder can't come back through an old path. (B-456)
3. As a caretaker whose group has an old note series, I want the notes it already wrote to stay, so that nothing I wrote disappears. (B-456)
4. As the operator, I want no service, upload or device to write or receive `todo.event_id`, so that it can be dropped safely. (B-625)
5. As a caretaker on an old app version, I want my todo uploads still accepted (their `eventId` ignored), so that my offline changes aren't refused. (B-625)
6. As an owner of a group made before default med times, I want Morning and Evening there, so that my group starts like everyone else's. (B-457)
7. As a caretaker in that group, I want doses given at 08:00 and 20:00 to sit under Morning and Evening, so that Given all covers them. (B-457)

## Implementation decisions

- **Migrations** (three, numbered at landing): the note kind (a hard `DELETE` of every `kind = 'note'` series, soft-deleted ones too since a check binds every row; visits keep their rows through `series_id`'s `ON DELETE SET NULL`; the check re-created as `kind IN ('event')`); the med-time backfill and relink (`--custom`, idempotent); the simple-mode Drizzle step (a plain generate, its three drops replaced by a comment, its snapshot without the columns).
- **Expand-contract through Drizzle:** a column leaves the Drizzle schema through a plain generate whose drops are replaced by a comment (the snapshot moves, the database keeps it; `--custom` keeps the previous snapshot); a deploy later, a hand-written custom migration drops it.
- **The replication whole-table list:** gains `todo` when `event_id` leaves the stream; `care_group` and `care_group_member` stay until `-2`'s drop.
- **The series kind:** `SERIES_KINDS` is `["event"]`; `topUp`'s note skip goes.
- **`todo.event_id`, step one:** the mirror and `releaseEvent` go; `timelineEntryService.remove` and `entryTodoService.unlink` stop clearing it; the upload registry's todo content drops it (an old client's upload is accepted, the field ignored); the todo stream drops it. The Drizzle and device schemas keep it; `todoRules.ts` (`code-health-4`'s hot file) is left alone.
- **No API, screen or permission change**, beyond the two retired member fields leaving `PERMISSIONS`.

## Testing decisions

- Integration tests against Postgres. The data migrations replay their statements on rows set up as staging had them (prior art `easyRolesMigration.int.test.ts`); the todo services in `todo.int.test.ts`; old-client uploads in `syncEventTodos.int.test.ts`.
- The roles guards (`roles.int.test.ts`, `rolesSql.test.ts`) prove the whole-table list matches the streams.
- No component or browser test: nothing a screen shows changes.
