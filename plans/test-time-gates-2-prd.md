One question went to the user (a255): how to handle a local gate that never judges a run. The rest falls outside the planner's _What to ask_. No item is dropped (B-859 asks for a fourth shard **or** trims; its "integration beside unit" is deferred above, not dropped), and the extra CI job costs no money (a public repo's runners).

The first skeptic (s55) sent the plan back: the arming line alone (`scripts/ci/tiers.json`) runs no tooling step, so slice 2 could have armed `quick` on the fast case; the quiet window clashed with slice 1 running beside it; the row named no hot files; slice 1 was past 8 files; and the PRD blamed the stale New York entries for the imbalance (the sequencer only reads the files it runs). The tooling split is now unconditional, the measurement waits for slice 1's hand-off, the refresh and arming are slice 3, and the hot files are set. The second skeptic (s56) sent it back too: the gate's end-load rule counts the check's own load, so the measurement might never count, with no bound on retries. That went to the user, who chose to judge on the start load only; slice 2 now changes the rule and has a bounded retry.

## Problem

The unit tests now fail CI past 6 minutes, but the component tests and the local quick check only warn. One component shard still runs 309 s on a balanced run, and branches see 470 to 513 s. No quiet quick check has been measured since the gate came in, so nobody knows whether it meets the aim. Until both gates fail past the cutoff, either can grow again and nothing stops it.

## Solution

Bring every component shard well under 5 minutes with a fourth shard and a fresh durations table, and arm the components gate once the slowest shard leaves room for a slow runner. Measure the quick check in a quiet window. If it is over, split the slowest tooling test files the way the landing tests were split, then arm the quick gate.

## User stories

1. As the user, I want every component shard's test step under 5 minutes with room for a slower runner, so that the component tests stop being the slowest part of CI (B-772, B-859).
2. As the user, I want the components gate to fail a CI run past 6 minutes, so that the component tests can't quietly grow again (B-837, B-859).
3. As the user, I want the local quick check measured on a quiet machine and kept under 5 minutes, so that a check the agents run many times a day stays fast (B-837, B-859).
4. As the user, I want the quick gate to fail a quiet check past 6 minutes, so that the quick check can't quietly grow again (B-837, B-859).
5. As an orchestrator, I want the times each gate was armed on recorded in the plan, so that a later breach can be read against them (B-837).

## Implementation decisions

- **Component shards:** CI's components tier runs four shard jobs instead of three. The tier data's job list, the tier plan's outputs (the first shard alone on a narrowed run, the rest together, as today), the workflow's jobs and the jobs the final gate waits on all name the fourth. The sequencer and the balancer already take any shard count, so neither changes.
- **The durations table** is refreshed from one green four-shard run with the balancer's existing refresh command, so its per-file times are the runners' as they are now (it also drops the 58 New York files that no longer run there). No schedule refreshes it; a gate warning names the slowest files when it drifts.
- **Arming** (slices 2 and 3) is one switch per measure in the gates' data (`armed: true`), set by the slice that measured its run, with the seconds in the plan's _Status_.
- **The quick check's measurement:** after slice 1 has handed off (its checks load the machine too), the orchestrator asks the user for a quiet window (`pnpm prd ask`), then runs one quick check of slice 2's own diff in it. That diff touches the tooling tests, so the tooling step runs; the check log's step times show a `tooling` field, or the run doesn't count. The check log's step times and the gate's verdict are the record; a run the gate didn't judge (a busy start) doesn't count either. One quiet window is asked for; if its run still isn't judged, the orchestrator asks once more, and after that the slice records the times, leaves `quick` unarmed and files a `fixes-perf` item.
- **The quiet rule:** the time gate judges the local measure when the start load is quiet; the end load stays in its input and its lines (for reading a slow run), but no longer decides `unjudged`. The CI measures are unchanged.
- **The tooling test split:** `recover` always, `rotate` and then `dispatch` only if the quiet run is still over 275 s; each split along their existing `describe` groups, their shared setup moved into a fixture module, as `land.test.mjs` and `land-fixture.mjs` were. No test changes what it asserts.

## Testing decisions

- The tier data and the workflow: the existing unit tests over the tier plan's outputs, the job lists and the workflow's job names (`tiers.test.mjs`, `ci.test.mjs`, the workflows' test), updated for four shards.
- The balancer: its existing unit tests, with one case for four shards.
- The fourth shard proves itself by one requested `components` CI run: every shard's test step in _Status_, the same component test count as before.
- The time gate: its existing unit tests, with a quiet start and a busy end now judged, and a busy start still `unjudged`.
- The tooling split proves itself by the same `pnpm test:tooling` test count before and after, and by the quiet quick check's step times.
- No browser check: nothing here crosses the server and sync.

## Out of scope

- Trims of individual slow component test files (timeline, planner, `inScreens`): a `fixes-perf` item if the gate warns again.
- A scheduled or automatic refresh of the durations table.
- The unit shards balanced by duration (B-863, `fixes-perf`).
- The quick check's integration step run beside its unit step (B-859 names it as a possible trim): `fixes-perf` if the quick gate warns again.
- Gating the integration job, the browser checks or the full check.
