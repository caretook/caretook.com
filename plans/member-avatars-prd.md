## Problem

Every member's avatar is the same primary-colored circle of initials, and timeline author circles are plain grey. In a family care group, people with similar initials look alike, and nobody can make their avatar their own.

## Solution

Each member picks a color and an icon from a fixed set in account settings. Everyone in their care groups sees it wherever that member appears. A member who hasn't chosen keeps initials, on a color that differs from everyone else's in that group. It all works offline and makes no external request.

## User stories

1. As a member, I want to pick a color from a fixed set, so that people recognise me at a glance.
2. As a member, I want to pick an icon from a fixed set, so that my avatar feels like mine.
3. As a member, I want to clear my choice, so that I can go back to the default.
4. As a member, I want to choose while offline, so that my choice is kept and sent when I reconnect.
5. As a co-member, I want to see each member's choice on the Timeline, Planner, Members page, live-note editors and filters, so that I can tell who did what.
6. As a member who hasn't chosen, I want initials on a color no one else in the group has, so that I'm still easy to tell apart.
7. As a member, I want my default color to stay put when people join or leave, wherever that can be avoided, so that the group's colors stay familiar.
8. As a member of several groups, I want one choice that applies in all of them, so that I set it once.
9. As a user of either theme, I want avatars to stay readable, and not to look like a status or section color, so that a color never implies urgency.
10. As a member, I want no third party to learn anything from my avatar, so that my privacy holds.

## Implementation decisions

- **Avatar catalog (client-safe, pure):** the color ids and icon ids, the Zod schema for a choice, and a reader that treats an unknown id as unset, so an older device survives a newer id.
- **Default-color resolver (pure, deep):** takes a group's members (user id, membership id, join time, chosen color and icon) and returns each member's look. It is the only place that knows the assignment rule. The hash is a small stable string hash, identical on every device.
- **Schema and sync:** an additive migration adds the two nullable `user` columns with checks and changes the `powersync` publication's `user` column list by dropping and re-adding that one table (`SET TABLE` would remove every other table). The public profile fields, the user model's co-member row and type, the `member_profiles` stream and the device schema gain both columns. They sync down only: `user` stays out of the upload registry.
- **API:** `me.get` returns the choice. A self-only `me` procedure sets or clears it, writing through `userService`.
- **Device queue:** the choice has its own cache and pending entry, cleared at sign-out and sent by its own step, never through `updatePreferences`. A refused avatar never drops queued settings, or the reverse. Your own choice overlays your synced row until that row matches what was sent, so it never flickers back.
- **Avatar display:** `UserAvatar` stays a pure `ui/` primitive and gains an optional look (color id, icon id). A member-aware avatar reads a per-group looks provider, so call sites pass a user id instead of threading props. Author circles become this avatar, keeping their links, tooltips and screen-reader text.
- **Tokens:** avatar color tokens live beside the accent tokens, and only the avatar module names them.

## Testing decisions

- **Unit:** the catalog (schema, unknown ids); the resolver (agreement regardless of input order, distinct colors up to ten members, chosen colors reserved, a joiner with no chosen color moves nobody, a joiner with one moves only its holder and anyone that shift pushes on, a leaver moves only those pushed off their hashed color, repeats past ten, ties on join time); token contrast of at least 4.5:1 in both themes and hue distance from status and section colors, read from the stylesheet.
- **Integration:** the `me` procedure (own row only, invalid ids refused, clearing); a co-member's read includes the two ids and never email or preferences; the roles and permissions tests that pin the public column list are updated, and the registry agreement test covers the new columns.
- **Component:** the picker, `UserAvatar` looks, and each changed screen's existing test, following [components](../docs/domain/components.md#component-tests).
- **End to end:** one short step in the existing `roundtrip` check (one member chooses, the other sees it). No new check; the lean set is close to its ceiling.

## Out of scope

Photo upload, Gravatar, per-group choices, custom colors or icons, a default look in the header, and avatars in emails, print views or connector output.
