## Problem

The dispatcher now plans and runs topics by itself, in the PRD table's row order. The user's part is to say what they want and what comes first, and that part is still awkward:

- **Adding an idea means editing a file in the main checkout,** which the dispatcher, landings and every `pnpm backlog` write also change. An agent that edits it there for the user can collide with what they have open, and can't write at all while the checkout is mid-merge or off `dev`.
- **Priority lives in the backlog's PRD table.** To change what runs next the user opens the tracker, finds the row and runs `pnpm backlog prd move`, or asks a session to.
- **The same idea gets filed twice.** Nothing compares a new line with what is already there or already done.
- **Finished items stay in the tracker** until someone runs `pnpm backlog archive`; the cleanup run only reports them.
- **The main checkout's update stops on the inbox:** `pnpm prd dev-sync` refuses when the inbox has uncommitted lines, and a landing then waits on the user.

## Solution

- **An inbox agent** (`pnpm prd inbox`). The user tells it things in plain words, at the desk or from the phone. It checks for look-alikes, puts each line under the right heading, and keeps the Next up list in the order the user gives. Its writes go straight to `origin/dev`.
- **A Next up list** at the top of the inbox: a few plain lines, most important first. The dispatcher reads it and plans and runs those topics first. The user reads and changes priority in the one file that is theirs.
- **A pickup that is always safe.** The main checkout takes in what was pushed without ever losing or refusing over the user's own unsaved-to-git lines.
- **Duplicates shown before filing,** from any agent.
- **Archiving by the cleanup run.**

## User stories

1. As the dev keeper, I want to tell an agent an idea in plain words and have it land in the inbox under the right heading, so that I don't edit the file myself. (B-425)
2. As the dev keeper, I want that agent's writes to go to `origin/dev` without touching my main checkout's files or HEAD, so that it never collides with what I have open and still works while the checkout is busy. (B-425)
3. As the dev keeper, I want lines I typed in the inbox and haven't committed to survive every update of the main checkout, so that a pushed line or a landing never costs me my own. (B-425)
4. As an orchestrator, I want `pnpm prd dev-sync` not to stop on the inbox, so that a landing never waits on the user for it. (B-425)
5. As the dev keeper, I want the agent to move a line to another heading when I say it is a bug, not a feature, so that its type is right before it is filed. (B-425)
6. As the dev keeper, I want to write a short Next up list in plain words in the inbox, so that I set priority without opening the backlog. (B-406)
7. As the dev keeper, I want the dispatcher to plan and run the listed topics first, in my order, and leave the rest in their order, so that the list is all I maintain. (B-406)
8. As the dev keeper, I want the PRD table's row order to follow the list, so that every tool that reads the table agrees with it. (B-406)
9. As the dev keeper, I want a line nothing can match to reach me as a question with choices, so that no agent guesses what I meant. (B-406)
10. As the dev keeper, I want to tell the inbox agent "put sync safety first" and see the list change, so that I can reorder from the phone. (B-406, B-425)
11. As a backlog session, I want `pnpm prd queue <topic>` to change the same list, so that two orders never fight. (B-406)
12. As the dev keeper, I want to see similar open and archived items before a new one is filed, so that I don't file the same thing twice. (B-435)
13. As an agent filing a follow-up, I want the tool to stop me on a likely duplicate and name it, so that I note the existing item instead. (B-435)
14. As the dev keeper, I want my own inbox lines always filed, with look-alikes noted on the new item, so that triage sees them and nothing I wrote is refused. (B-435)
15. As the dev keeper, I want finished items moved to the archive without running a command, so that the tracker shows what is left. (B-435)
16. As an orchestrator, I want my topic's landed items to stay listed until my PRD worktree is gone, so that my reports and notes still find them. (B-435)

## Implementation decisions

**The inbox merge** (pure, in the backlog tooling). `mergeInbox(base, ours, theirs)` returns the merged text and a list of notes; it never fails and never writes conflict markers. An entry is a bullet with its indented detail lines, known by its text without the tag. Rules: an entry added on either side is kept, once when both added it; an entry removed on one side and untouched on the other is removed; a tag added on either side stays; an entry reworded on one side takes that wording, on both sides both are kept; an entry moved to another heading on one side moves; new entries from `theirs` go to the end of their section; Next up takes the order of whichever side changed it, `theirs` when both did. Text outside the lists comes from `ours`.

**The pickup** (`pnpm prd dev-sync`, same command, same lock):

- When the update changes the inbox and the working copy has uncommitted inbox edits, it no longer refuses: after moving `dev` it writes the merge of the old committed copy, the working copy and the new committed copy. The user's lines stay uncommitted.
- When replaying or merging `dev`'s own commits conflicts only in the inbox, the inbox merge resolves it. A conflict in any other file stops as today.
- `pr` and `land`'s push of `dev` runs the pickup first when `origin/dev` has commits `dev` lacks, instead of stopping.
- Of `dev`'s own commits it replays only backlog commits that no other ref or detached worktree holds (the amend rule's test); with any other it makes the merge commit.
- `pnpm backlog ingest` runs it first, before taking the backlog lock (skipped with a line when it can't).

**The origin writer** (in the backlog tooling). Given a pure edit of the inbox text and a subject, it fetches `origin/dev`; when local `dev` is ahead of it by backlog commits only, it pushes local `dev` first (a fast-forward, no force); then it applies the edit to `origin/dev`'s copy, builds a commit on that tip changing only the inbox (a `chore(backlog): …` subject with the `Backlog-Tool:` trailer, so `pnpm log` hides it and dev-sync knows it), and pushes it to `dev` without force. A rejected push is retried on the new tip, five times. It then runs the pickup, best effort: a busy main checkout only prints a line. It never pushes a commit of the user's own, and reads and writes nothing in any working tree. To know which bullets are filed it also reads the tags in local `dev`'s committed copy.

**Inbox commands** (through the origin writer):

- `pnpm backlog inbox add <type> <text…> [--details <text>] [--anyway]`: a new bullet at the end of the type's section. It stops on look-alikes (below), counting unfiled inbox lines too.
- `pnpm backlog inbox move <words> <type>`: an unfiled bullet (found by its words; it must match exactly one) to another heading. A filed bullet is refused with the `pnpm backlog set B-<n> type=…` line that changes the item.
- `pnpm backlog inbox` (no arguments) still lists unfiled bullets, now from `origin/dev`'s copy merged with the working copy.

**Next up:**

- A `## Next up` section, first in the inbox. The inbox parser gives its bullets no type, so `ingest` never files them.
- **Resolve** (pure): for each line, the topic in a trailing `(topic)` tag when the registry has it; else a line that is a topic's name, hyphens or spaces; else an item id, standing for its topic; else unmatched. A line whose topic is `done` is skipped and reported; a topic listed twice counts once.
- `pnpm backlog next`: the list as resolved, the unmatched and skipped lines (`--json`).
- `pnpm backlog next add <words or topic> [--first|--before <t>|--after <t>]`, `next move <topic> …`, `next rm <topic or words>`, `next tag <words> <topic>`: through the origin writer.
- `pnpm backlog next apply [--now]`: reads the main checkout's working copy, resolves it and moves the registry's rows so the listed topics come first in list order, in one backlog commit, only when the order changes. It prints what it moved and the unmatched lines. A working copy with uncommitted edits saved less than a minute ago is skipped (a line being typed) unless `--now`.
- `pnpm prd queue <topic>`: with a non-empty list, `next add <topic> --first` then `next apply --now`; else as today. `pnpm backlog prd move` warns when the topic it moves, or the one it moves past, is listed.

**The dispatcher** reads the list: every five minutes (`CARETOOK_PICKUP_EVERY`) it runs the pickup, and every tick `next apply` before gathering its facts. For each unmatched line it files one question (session `dispatch`, the three closest topics by shared words and "remove the line" as options) and remembers it in its state, so a line is asked once. An answer naming a topic becomes `next tag`; "remove the line" becomes `next rm`. Its pick is unchanged: it still reads row order.

**Look-alikes** (pure): `similarItems(text, items)` ranks open and archived items by shared content words (the folding and stop words the tool already uses to compare a title with its bullet) and returns those over a threshold with id, status, topic and title.

- `pnpm backlog similar <text…>`: the list, read only.
- `pnpm backlog add` and `inbox add` print it and file nothing (exit 3) unless `--anyway`.
- `ingest` files every line and, for one with look-alikes, adds a note naming them and prints them.

**Archiving:** `pnpm backlog archive [B-<n>…]` takes ids (all finished items without). `pnpm prd tidy` moves archiving from its ask list to its safe list: with `--yes` it archives dropped items and finished items whose topic has no `prd/` worktree. The tidy prompt stops calling archiving an ask, and the orchestrator prompt's line on filing Codex findings says what to do when `add` stops on a look-alike (note the existing item, or `--anyway`).

**The inbox session:** `pnpm prd inbox [--model <m>]` (opus by default) starts a session named `inbox` in the main checkout's directory with `pnpm prd prompt inbox`. The prompt: read the role doc; show the unfiled lines and Next up from `origin/dev`; poll what the session is for (add, sort, set what's next) with AskUserQuestion; before each add run `similar` and show what it finds; write only through `pnpm backlog inbox …` and `pnpm backlog next …`; name items and topics by their plain titles; edit no file, commit nothing, and leave ingest, triage, holds and asks to the backlog session. The backlog session's prompt learns that priority is Next up (`pnpm backlog next …`), not row moves, once the list is in use.

**Docs at landing** (the orchestrator): a role doc `docs/agents/inbox.md` with its _Area index_ entry; [backlog](../docs/agents/backlog.md) (the origin path, Next up, look-alikes, archiving, who may change the inbox); [machinery](../docs/agents/machinery.md) (dev-sync, tidy, the dispatcher's pickup); [orchestration](../docs/orchestration.md) (the human guide); the inbox file's own opening lines. AGENTS.md's line on how agents reach the main checkout gains `pnpm prd dev-sync`.

## Testing decisions

Tooling tests only (`pnpm test:tooling`); the check gate needs nothing else for a tooling and Markdown diff. A good test here drives a pure function with text in and text out, or a command against throwaway git repositories (a bare one standing in for `origin`), and asserts on the files, refs and output, never on how the code is arranged.

- **Pure, unit:** the inbox merge (each rule, and that the result parses and holds every entry once); resolve; look-alikes; the tidy sort; the dispatcher's handling of unmatched lines where it is pure. Prior art: `format.test.mjs`, `registry.test.mjs`, `tidy.test.mjs`, `dispatch-pick.test.mjs`.
- **Commands against temporary repositories, unit project:** the origin writer (a push, a rejected push retried, the main checkout untouched, a busy checkout); dev-sync with uncommitted inbox lines and with an inbox changed on both sides; `inbox add|move`, `next …`, `next apply`, `similar`, `add` stopping, `ingest` noting, `archive` with ids; `queue`; the dispatcher's tick with a fake clock. Prior art: `backlog.test.mjs`, `registry.cli.test.mjs`, `land.test.mjs`, `dispatch.test.mjs`, `tidy-cli.test.mjs`.
- **Prompts:** `prompt.test.mjs` gains the inbox prompt and the backlog prompt's Next up lines.
- No component, integration or browser tests: no app code changes.

## Out of scope

- **Every agent's questions through the backlog session, and asks hygiene** (B-467, B-429): `asks-relay`.
- **Moving the tracker to `origin/dev`.** Tracker writes stay local commits, pushed at landings and by the pickup.
- **A push service,** and reopening the inbox or backlog session after a crash: the user restarts them.
- **Ordering items inside a topic,** or the order between the fixes topics beyond what the user lists.
- **A model judging duplicates.** The check is word overlap; the inbox agent uses its own judgement on what it shows.
- **Editing archived items** (B-458, in `fixes-tooling`).

## Follow-on topic

**`asks-relay`** (B-467, B-429), the row after this one; it needs its own PRD. The backlog session becomes the go-between for every agent's questions: askers say how blocking a question is, a pure ranking checks that against the sessions and the registry, the backlog session relays questions word for word and records answers, the phone is pushed only for a blocked-now question when the user isn't active there, and reports arrive as a digest. With it: reports that expire or are re-checked, answered asks archived (ids never reused), and a fallback push when no go-between is live or an asker has died. This planner's sketch is in the two items' notes.

## Notes

- **Shared files:** this topic changes `scripts/backlog/`, and in `scripts/loops/` the dev-sync part of `lib.sh`, `prd.sh`, `prompt.sh`, the dispatcher and tidy. `fixes-tooling`, `test-health` and `code-health` change the same directories; the hot-file rule keeps them apart.
- **Local `dev` is usually ahead of `origin/dev`** by unpushed backlog commits. The origin writer pushes those first, so the two stay in line. They diverge only while the user has a commit of their own unpushed; then each inbox push costs one `chore(dev): merge origin/dev` commit at the pickup.
- **Until B-458 lands,** an archived item refuses `set` and `note`. Archiving only once a topic's worktree is gone keeps that away from running PRDs.
- **Word overlap misses a reworded duplicate and flags some near-topics.** It is a prompt to look, and `--anyway` is always there.
- **The inbox agent pushes to a shared branch on the user's spoken word.** Each push changes one Markdown file and is a normal, visible commit; nothing deploys from `dev`.
