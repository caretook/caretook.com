## Problem Statement

The orchestration tooling (about 63k lines in `scripts/loops`, `scripts/backlog`, `scripts/ci`, `.githooks`, half of it tests) lives inside Caretook and is wired to it both ways: about 125 `CARETOOK_*` variables, app paths in about 50 files (20 outside tests), Caretook's stack in its stack scripts, Caretook's browser checks in its gates, and Caretook's CI and checks importing it. The user wants one tool that runs Claude across all their repos. Today it can't be pointed at another repo, every tooling change lands in Caretook's history, and Caretook carries code that isn't Caretook.

## Solution

First, inside Caretook and with no change in behaviour, every Caretook fact moves out of the core into one config file and a project folder, Caretook's checks and CI stop calling the core, a lint rule proves the line, and the tool's names become Risa's. Then, in one hand session with nothing running, the clean core moves to `~/git/risa` with its history, and Caretook keeps its config, plans, docs and scripts. From then on the user runs `risa` and it manages Claude in Caretook as one configured repo.

## User stories

1. As the user, I want every Caretook fact the tooling uses to live in one config file and one project folder, so that I can see what a repo must provide.
2. As the user, I want a lint rule that fails when the core names Caretook or an app path, or when Caretook's code imports the core, so that the line stays drawn.
3. As the user, I want Caretook's stack, test DB, browser checks, check areas, budgets and test gates to be Caretook's own scripts and data that the tool calls, so that another repo can bring its own.
4. As the user, I want the tool's knobs named `RISA_*`, so that nothing about the tool says Caretook.
5. As the user, I want the host calls (iTerm2, launchd, nvm, the CLIs) in one place, so that they're easy to find and swap later.
6. As the user, I want Caretook's checks, tests and GitHub CI to run with no tool present, so that Caretook doesn't depend on Risa.
7. As the user, I want the move done in one drained session with history kept and a one-commit undo, so that it can't strand running work.
8. As the user, I want to run `risa` against Caretook as a configured repo, with its prompts and hints naming `risa`, so that Caretook is a plain repo.
9. As the user, I want the generic role docs to come with the tool and each repo to add to or replace them per role, so that Risa and Caretook don't keep two drifting copies.

## Implementation decisions

- **The project config** is one module at Caretook's root with a small, validated shape: name, the command names, paths (backlog, inbox, archive, plans, docs, agents doc, each role's additions or replacement doc, browser checks, CI lists, the tier data, the check plan's rules), branch names (trunk, protected, prefixes), commands (check, quick check, project tests, typecheck, typegen, datastore start, reset and seed), hooks (the check's body; stack up, down, status, ready; test DB; lease; the browser runner; check areas for a diff; doc budget), and the Risa version expected. It is JSON (`risa.json`); a core loader validates it in Node and a `config get` helper reads it from bash; nothing else knows where it lives. Bash reads it once per process, not once per value: sourcing `lib.sh` starts Node at most once (the tooling tests already run dozens of git commands each).
- **The core manifest** lists every file in `scripts/loops`, `scripts/backlog`, `scripts/ci`, `scripts/project` and `.githooks` with its owner, core or Caretook, tests included. The boundary lint and the move's `filter-repo` both use it.
- **The boundary lint** works both ways: it fails on a Caretook name, an app path (`apps/`, `packages/`, `powersync/`, `docs/domain/`, `ops/`) or a `CARETOOK_` variable in a core file, on a core file importing a Caretook file, and on any Caretook file (anywhere in the repo) referring to a core path in any form (import, spawn, path string, `--import`), minus an allowlist each slice shrinks; stage 1 ends with only the named residual list (_Decisions_). The core-to-Caretook rule covers spawns and path strings too, not only imports.
- **The CI split:** core and Caretook CI modules exchange facts through files and config, never imports. Caretook owns the GitHub jobs (`browser-job`, `test-job`, `env`, `zones`, `verdict`, `quarantine-setup`), `tiers.mjs`, its `lists.mjs`, the half of `release.mjs` the verdict runs (job names and summarizers), the tier data and the two lists; the core owns the rest (`ci*.mjs`, `gate`, `release-gate`, `candidate`, `promote`, the rest of `release`, `outstanding`, `filing`, `blame`, its copy of the lists parser). Everything the core takes from `tiers.mjs` (tier names and jobs, file groups, the browser-check pattern, marker files, the ref prefix) becomes a data file both sides read; the core reads a verdict as a file with its own reader; each side has its copy of the lists parser.
- **The check:** its body is Caretook's script behind the `check` hook (mode, base and own tests in; exit code, state files and counts file out; the core runs its own tooling tests after it); the core keeps the lease, load gate, log, timings and rerun rules around it.
- **The check plan:** its rules are a Caretook data file; the core's engine reads it through the config, and the sample project brings its own rules.
- **The role docs:** one generic doc per role in the core; `doc <role>` prints it followed by the project's additions, or the project's replacement alone. The prompts name that command, not a path.
- **The host layer** is one core module for tabs, autostart, Node, notifications, running `claude`, `codex` and `gh`, and where Claude Code keeps its own files (its config, the project transcripts, the session settings with the status line and hooks).
- **The renames** (variables, command names) are scripted and mechanical; the lint confirms nothing is missed. Names shared between worktrees or with GitHub (the backlog lock, the checked and inbox-merged markers, the launchd label, the commit-status context) are built from the config's project name and keep today's values.
- **Tests:** a sample project config and fixture repo for the core's tests; generic tests with Caretook-like sample paths get neutral ones; Caretook's tests sit beside Caretook's scripts under a Caretook test script; the prompt golden splits in two.

## Testing decisions

Tooling unit and CLI tests, as today, plus the config loader and its validation, the boundary lint, the lease from both sides, the CI split's file exchange, and the split goldens. Each slice keeps the whole tooling suite green with no behaviour change, and `pnpm test`, `test:tooling` and `test:browser-harness` run exactly today's test sets until the move. Before the move, a throwaway GitHub CI run on a branch with the core files deleted must be green. Slices touching the app's test helpers, `vitest.config.ts`, `package.json` or `.github/` take the tier the check gate asks for (named per wave in the plans).

## Out of scope

Risa's multi-repo features; moving tool state out of `.loops/`; Caretook's history cleanup; other hosts; a remote for Risa; releasing it. Each is a `risa-next` item.
