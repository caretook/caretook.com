## Problem

Test-gates removed automatic CI, so dev is checked as a whole only when it is promoted, and until now that check is a handbook rule. Promotion takes whatever dev is at that moment while other work keeps landing. The browser suite has never run in CI, and nothing stops an unchecked commit reaching production.

## Solution

| Step            | Runs                                                                                                            | Enforced by                                                   |
| --------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| dev to staging  | a fixed candidate branch, the `candidate` tier: everything in `full` plus the browser suite on the Docker stack | the tool; the user can merge by hand                          |
| staging to main | the `release` tier: the suite three times and a second-zone run that reports                                    | GitHub's required check; the user can override, on the record |

## User stories

1. As the user, I want a release candidate cut from a fixed dev commit, so that work landing in dev doesn't change what is being tested.
2. As an orchestrator, I want the browser suite to run in CI on the Docker stack, so that it no longer loads the Mac.
3. As the user, I want promotion to refuse a candidate that isn't passing, so that dev's only whole-suite check can't be skipped by accident.
4. As the user, I want to merge a candidate by hand when I choose to, so that the gate never traps me.
5. As an orchestrator, I want only fixes to reach a candidate, and each fix to be in dev already, so that a release doesn't pick up new work or lose a fix.
6. As the user, I want main to require a passing release run of the exact commit, so that production gets only what was tested.
7. As the user, I want repeated runs to catch flakes before production, so that intermittent failures are filed instead of shipped unseen.
8. As the user, I want second-zone failures reported without blocking, so that time-zone bugs surface before they can stop a launch.
9. As the user, I want a recorded emergency override for main, so that I can ship a critical fix and the reason stays visible.

## Implementation decisions

- **Tiers:** `candidate` and `release` join the one tier list. The landing gate's proposals are unchanged: no diff proposes them.
- **The browser job** has its own limit of about 30 minutes (the checks' caps total 1,550 s). It starts the Docker stack with a generated fictional env, migrates, seeds, builds and serves the app itself on an interface PowerSync can reach from its container, and runs the manifest's checks in order through the existing runner.
- **Browser results** reach the verdict per check, with one rerun, and the brake list learns check names.
- **The candidate command** (`pnpm prd ci candidate cut [<commit>] | fix <commit> | status`) cuts and pushes the branch with its `-s ours` merge, opens the PR into staging, cherry-picks a dev fix and shows the candidate's commit and verdict. One open candidate at a time.
- **Promotion** (`pnpm prd ci promote`) reads the verdict for the candidate's tip, refuses unless it passes, merges the PR with a merge commit and deletes the candidate.
- **The release run** (`pnpm prd ci release`) runs the `release` tier on the head of the open staging to main PR and writes `release-gate` from its verdict. With no open PR it refuses and says how to open one. A newer commit on the PR needs a new run.
- **The second-zone setting** is a committed value, `report` or `block`.
- **The override** (`pnpm prd ci override <commit> --reason "…"`) refuses without a terminal or inside a recorded agent session (`CARETOOK_SESSION_NAME`). Reasons appear in a public repo, so its prompt says to leave out health details and names.
- **Handbooks:** the interim "request a `full` run before a staging PR" rule and the dev keeper's local backstop are replaced; the runbook's "staging takes PRs from `dev`" lines change to candidates, and it gains the ruleset step and the override.

## Testing decisions

- Unit tests: the tier list and job selection; browser results and the rerun; the candidate's cut, the `-s ours` merge against a staging that holds a cherry-pick dev later changed, the staging-only refusal, and fix refusals; promotion's refusal for each verdict kind; repeat-run classification; second-zone `report`, `block` and the filing cap; the override's refusals. `gh` and `git` output comes from fixtures or temp repositories, as in `ci.test.mjs`.
- `scripts/deploy/workflows.test.mjs` learns the new jobs and keeps asserting no `pull_request` trigger and no secret in `ci.yml`.
- Workflows are proven by real requested runs of the slice's branch, linked in its hand-off.

## Out of scope

- One-command shipping, Codex findings by tool, the staging to-test report: `staging-ship` (B-404, B-430, B-436).
- Fixing second-zone failures and pinning zones per test: `test-health-2` (B-372).
- A quarantine for browser checks.
- Editing GitHub rulesets from a tool.
- Automatic CI on any branch.

## Notes

- Until the user adds `release-gate` to the main ruleset, the check is visible but not enforced.
- Production isn't live yet, so the first release run has no users waiting on it.
