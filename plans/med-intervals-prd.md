## Problem

On hospice, a care recipient's medications change timing quickly: comfort meds go from as needed to every 6 hours, then every 4, then every 3, while some single meds stay every 12 hours. Caretook only knows fixed clock times each day and as needed. A caretaker can't say "every 4 hours from when it was last given", so Today shows the wrong doses as due or missed, and every change of frequency means retyping clock times.

## Solution

A medication can be scheduled **every N hours**, counted either from its last due time or from when it was last given (the caretaker picks). Today shows the dose that's due now and the next one, never a day laid out ahead; a given-anchored med waits for an answer. Changing the frequency is one edit and keeps the history, so past days, missed counts, the weekly sheet and the connector read the timing each day had. The same rule then serves Med times in `med-intervals-2`.

## User stories

1. As a caretaker, I want to schedule a medication every N hours, so that its doses come due on its real rhythm, not on clock slots.
2. As a caretaker, I want to choose whether the next dose is due from the last due time or from when the last one was given, so that the schedule matches the order.
3. As a caretaker, I want to set when the first dose (or the next one after a change) is due, so that the rhythm starts where it really is.
4. As a caretaker, I want Today to show only the dose due now and the next one, so that I'm not shown a whole day that will shift.
5. As a caretaker, I want a given-anchored dose that hasn't been given to stay overdue rather than be skipped over, so that nothing silently moves on.
6. As a caretaker, I want to change a medication from every 6 to every 4 hours in one edit, so that frequent hospice changes are quick.
7. As a family member reading history, I want past days to show the timing they had, so that missed-dose counts and the record stay true after a change.
8. As a caretaker printing the weekly sheet, I want interval meds on it with a box per expected dose, so that the paper record works too.
9. As a member using my own AI through the connector, I want interval medications described correctly and addable, so that its answers about due doses are right.
10. As a caretaker, I want interval doses to work offline and sync like every other dose, so that two of us never log the same dose twice.

## Implementation decisions

- **The interval rule** (client-safe, in the medications schema module): `{ everyMinutes, from: "due" | "given", startsAt }` (`startsAt` an ISO instant; `everyMinutes` 60–1440). The medication schedule's third kind is `{ type: "interval", everyMinutes, from, startsAt, amount? }`, validated by the same Zod union as the other two and read through `normalizeSchedule`. Schedule edits remain tracked fields, so a change writes the existing change entry with the before schedule.
- **Every reader handles three kinds.** Anything that branched on "as needed, else scheduled" handles interval explicitly (display text, list item, device sync, slot times, the weekly sheet, the connector). `scheduleText` reads e.g. "Every 4 hours, from when given".
- **A deep pure module for interval instances:** given a rule, the answers (doses) for its medication, and a time range, it returns the instances (moment, answering dose, state input), applying from-due grids and from-given chaining, the window rule and the "next upcoming only" cut. `dueDoses` calls it for interval medications and feeds its instances through the same states (upcoming, due, overdue, given, skipped, refused, missed) and `DoseSlot` shape (`time` is the instance's clock time, `passId` null), so Today, `duePasses`, Given all and the timeline need no new shape. An interval slot carries its moment as its key: `doseSlotIdFor` and `duePasses`' round key use it for interval slots (clock slots keep day and time, so no id already written changes). `med-intervals-2` calls the same module with a Med time's rule and round answers.
- **The last answer:** a from-given rule needs the latest answer, which can be older than the doses `dueDoses` reads (from yesterday). Its input gains the latest answered dose per interval medication, required: the device query and every server caller (the `todays_doses` tool, the assistant action service's quick-entry dose logging) supply it.
- **Logging against an interval dose:** the assistant action service's scheduled-dose lookup (quick entry, the connector's `log_dose`) and connectors-3's `log_past_doses` (`doseRecord`, `sheetDoseOutcomes`, which name a slot by medication, day and time) find an interval dose by its instance's day and clock time (at the fall-back hour, a repeated clock time names the earlier dose unless the mark gives its moment), with the same dose id rule (keyed by the instance's moment, with the interval window), so two writers (the device's dose writer and the service) never log one dose twice.
- **The connector's `add_medication`** has its own schedule input (connectors-3): it gains an interval branch (every hours, from due or given, next dose at, default now) mapped to the interval kind and validated by the shared schema.
- **Equal schedules:** `sameSchedule` compares interval schedules field by field, so saving an unchanged interval writes no change entry.
- **History:** `scheduleHistory` reads an interval kind before and after a change: instances of the old rule stop at the change, the new rule starts at its `startsAt`. `doseSlotsBetween`, `missedDoseCounts`, `doseSchedule` and connectors-3's `doseRecord` use it, so visit prep, `dose_schedule` and `past_doses` count interval doses; from-given doses ahead of the next one aren't predicted (the schedule lists the next due one).
- **The form:** the Schedule choice has three options; Every few hours shows hours, from due or given, and Next dose at (default from the rules above) inline. The form data module parses it into the interval kind; the shared schema's messages show on the fields.
- **Seeds:** one fictional interval medication appended to the seed group.

## Testing decisions

- **Unit** (web:unit, beside `dueDoses.test.ts`, `scheduleHistory.test.ts`, `medicationDisplay.test.ts`): the interval module (both anchors, DST, re-anchor, window, next-only, missed vs overdue); `dueDoses` with interval meds beside clock meds; the Zod kind; `scheduleText`; `scheduleHistory` across a change; `doseSchedule`; the weekly sheet builder.
- **Component** (`medicationWorld.tsx` prior art): the form's Every few hours fields and save; Today showing an interval med's due and next dose and logging one; the weekly sheet print.
- **Integration:** one case each in the existing files: the medication service saves an interval schedule and writes one change entry, an unchanged save none; the assistant action service logs a quick-entry dose onto an interval dose; `addMedication.int.test.ts` adds an interval medication; `logPastDoses.int.test.ts` logs a mark onto an interval dose. Connector text: its existing tool tests.
- **No new e2e:** no new flow across server and sync (the schedule column already syncs).

## Out of scope

- Interval Med times, round anchoring and the Med time form: `med-intervals-2`.
- As-needed Med times (a group PRN together): `med-intervals-2` (skeptic a334).
- Reminders or notifications for interval doses (push waits for Capacitor).
- Intervals under 1 hour or in half hours in the form.
