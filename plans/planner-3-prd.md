# PRD: A note can carry a todo; quick entry reads a repeat

Topic `planner-3`. Backlog items B-245 (attach a todo to a note) and B-254 (quick entry: "bins out every monday" makes a repeating todo). Both follow `planner-2` (B-248: notes are past-only, todos repeat), which is in `dev`. Areas: [todos](../docs/domain/todos.md), [assistant](../docs/domain/assistant.md), [timeline](../docs/domain/timeline.md), [live-notes](../docs/domain/live-notes.md), [connectors](../docs/domain/connectors.md).

## Problem

Planner-2 took reminders away: a note is now only something that happened. But what happened often leaves something to do: "Dr. Alvarez said to book a follow-up in two weeks", "the pharmacy is out of Latanoprost, call back Thursday". Today the caretaker writes the note, then goes to the Planner and makes a todo that has no tie to it. Whoever picks the todo up can't see why it exists, and whoever reads the note can't see whether anyone followed up. The same goes for events: a note about what the doctor said has no tie to the visit it was said at, or to the follow-up it led to.

And the fastest way to add anything, the quick entry box, can make a todo but not a repeating one. "Bins out every monday" makes a todo for next Monday only; the repeat has to be set by opening the form.

## Solution

- **A note links todos.** A note's page has a Todos section under its text: add a new todo from it, or link one that exists. Each todo keeps its own due day and assignee and shows in the Planner, the Today card, calendars and emails like any other. One todo can be linked from several notes.
- **A note links events** the same way: the visit it is about, the follow-up it led to.
- **A todo and an event show the notes that link them,** and open them.
- **The timeline shows which notes still have a todo open.**
- **Quick entry reads a repeat.** "Bins out every monday" makes a todo due Monday that repeats weekly on Monday; the card says so before Save.

## User stories

1. As a caretaker, I want to add a todo from a note's page, so that what the note asks for gets done.
2. As a caretaker, I want that todo to have its own due day and assignee, so that the note stays a record of what happened and the todo says who does what by when.
3. As a caretaker, I want to link a todo that already exists to a note, so that a note discussing it points at it.
4. As a caretaker, I want one todo linked from several notes, so that every note about it leads to it.
5. As a caretaker, I want the note's page to list its open todos with a tick, so that I can finish one where I read about it.
6. As a caretaker, I want the note's page to keep its done todos, with who did them and when, so that the note shows the follow-up happened.
7. As a caretaker, I want a todo's page to show the notes that link it and open them, so that I know why the todo exists.
8. As a caretaker, I want a linked todo to appear in the Planner, the Today card, my calendar and my emails like any other todo, so that nothing about it is second-class.
9. As a caretaker, I want to see on the timeline which notes have an open todo, so that I can spot what is still waiting.
10. As a caretaker, I want to take a todo off a note without deleting either, so that a wrong link can be fixed.
11. As a caretaker, I want deleting a note to keep its todos and events, so that nothing to do is lost with the note.
12. As a helper (viewer) with a note's todo assigned to me, I want to tick it on the note's page, so that it works for me as elsewhere.
13. As a caretaker working offline, I want linking, unlinking and ticking to work and sync later, and two devices linking the same pair to end with one link, so that sync never doubles it.
14. As a caretaker, I want to link the events a note discusses, any number of them, so that the note leads to the visit and the follow-up.
15. As a caretaker, I want an event's page to show the notes that link it, so that I can find what was written about it.
16. As a caretaker, I want "bins out every monday" in quick entry to make a todo that repeats weekly on Monday, so that I set a routine up in one line.
17. As a caretaker, I want daily, every-other, every-N, several weekdays and monthly phrases read too, so that the common routines all work.
18. As a caretaker, I want a time in the line ("every monday 7am") to be the todo's due time, and "for Sam" its assignee, so that the line says everything.
19. As a caretaker, I want the card to say "Repeats weekly on Monday" before I save, so that I can see what Save will make.
20. As a caretaker, I want the card's Edit to open the todo form with the repeat filled in, so that I can add an end date or change it.
21. As a caretaker, I want "gave tylenol every 4 hours" to stay a dose or a note, so that logging what happened never turns into a todo.
22. As a caretaker, I want a line that names a provider with a repeat to tell me quick entry doesn't make a repeating event, so that I'm not surprised by a single one.
23. As a screen-reader user, I want the timeline's todo mark, the link pickers and the card's repeat line to have text names, so that nothing depends on an icon.

## Implementation decisions

### The link table (B-245)

- **Table `timeline_entry_link`** (one additive migration; area `timeline`), modelled on `timeline_entry_provider`: `id`, `group_id`, `entry_id` (the note), `todo_id` (nullable), `linked_entry_id` (nullable: the event), timestamps and audits. A check: exactly one of `todo_id` and `linked_entry_id`. Composite keys with the group to `timeline_entry` (twice) and `todo`, all cascading. Unique per pair (a constraint per target). In the publication.
- **The id is derived:** `entryLinkId(entryId, targetId)`, a UUID v5 as `entryProviderId` is, so the device and the server make the same id and a pair is one row. **Unlink is a hard delete.**
- **`entryLinkService`** (write through it; RBAC in SQL in its model): `link(ctx, { entryId, todoId | linkedEntryId })` and `unlink(ctx, id)`. It refuses an `entry_id` that isn't a live note, a `linked_entry_id` that isn't a live event, a todo that is deleted, anything in another group, and a note linking itself. Linking a pair twice is a no-op that returns the row.
- **Permissions** (`PERMISSIONS`, the timeline part): read any member; create and delete the roles that write timeline entries; update `system`, as `timeline_entry_provider`.
- **Soft deletes:** a soft-deleted note, todo or event keeps its link rows; every reader joins live rows only, so a restored record gets its links back. A hard delete cascades.
- **Sync:** a stream in `care_groups` (`sync-config.yaml`), the device schema, and the upload switch: PUT → `link`, DELETE → `unlink`, PATCH → `sync:readOnlyTable`, as the provider links. Device queries and writes live in `lib/timeline/entryLinks.sync.ts`: `linkTodo`, `linkEvent`, `unlink`, `noteTodosQuery`, `noteEventsQuery`, `notesLinkingQuery` (the notes that link a todo or an event), `openTodoCountsQuery`.
- **`todo.event_id` is not touched,** and neither are `todoService`'s link checks.

### The note's page

- **Todos section** (a new `NoteTodos` in `components/todos`, reusing `TodoTick`, the Undo status and the row wording `LinkedTodos` uses): linked open todos in `todoOrder`, then done ones (`doneOrder`, at most 20) with `doneText`. Shown to everyone when it has rows; writers always see its actions.
  - **Add todo** opens `todos/new` with the note's id as a `noteId` prefill; saving writes the todo and the link in one local transaction, and returns to the note.
  - **Link a todo:** a `ComboBox` over the group's open todos not linked yet (by title, up to 20), as the With row's provider picker.
  - **Remove** on a row takes the link off (the todo stays).
- **Events section** (slice 4): linked events with their title, day and time (cancelled ones struck through, as the todo page shows them), "Link an event" over upcoming and recent events (the todo form's event choices), and remove.
- Both show for notes only, once the note is stored.

### The other side

- **The todo page:** Linked to gains a "Note" row per linking note: the note's first line as its timeline row words it, and its day, opening the entry page. The todo form is unchanged.
- **An event's page** (slice 4): a "Notes" list of the notes that link it, the same row.
- **An event that changes id keeps its links** (slice 4): rescheduling copies the notes' links onto the new event, as provider links are copied; a repeating event's visit that a note links counts as touched, so a series edit keeps it.
- **The timeline:** a note's row in the full view shows "1 todo" / "2 todos" (text, with a decorative icon) when it links open todos. One live query for the group (`openTodoCountsQuery`); the list passes each row its count. No per-row query, and nothing read from note documents.

### Quick entry reads a repeat (B-254)

- **`quickEntryRepeat`** (a new pure module beside the parser, in `schema/assistant/`): `readRepeat(tokens, today)` → `{ rule: RepeatRule, firstDay, used }` or null, where `used` is the token positions the phrase took. It builds the rule with the existing `ruleText` grammar (`repeatRule.ts`: no `rrule` import, so nothing joins the first load) and works the first day out with plain date arithmetic: the first day the rule gives from today on. A weekly phrase with no day ("weekly") and a monthly one with no date take today's weekday or day of the month.
- **Vocabulary:** the words that start a repeat ("every", "each", "daily", "weekly", "monthly", "weekdays") are `QUICK_ENTRY_VOCABULARY` rows with a new role `repeatWord`, with test rows, as the area doc requires. "every" before a count of hours or minutes ("every 4 hours") is not a repeat.
- **The splitter** keeps a weekday list together: "every mon, wed and fri" is one part.
- **The reading:** `todoReading` takes the repeat: `repeatRule` on the action, `dueOn` the first day, `dueTime` when the line says a clock time, and a title without the repeat words. A part with a repeat and no vital, dose, pass or symptom reading ranks Todo first, then Note (dated now, the whole line), then Event, as a note line ahead does. A part with a clearly named provider or an appointment word keeps its event first, with a non-blocking warning ("Quick entry can't make a repeating event. Set Repeat on the event."), and the repeating todo second.
- **The action:** `addTodo` gains `repeatRule` (RRULE text, optional; refused without `dueOn`, by the todo schema's existing rule). The device runner (`plannedTodo`) and the server runner (`assistantActionService.run`) already write a todo through the todo create schema, which starts the chain (`repeatColumnsFor`); each gets a test, and a fix only if the field doesn't pass through.
- **The connector's `add_todo`** builds its input from the action's shape: it leaves `repeatRule` out, as it leaves `assigneeId` out, until B-253.
- **Preview** (`actionPreview`): a repeating todo's card reads "Todo · Due Mon · Repeats weekly on Monday". That wording (`todoRepeatLine`) lives in the web app today; it moves into the schema package's todo display module, beside `dueText`, so the preview and the connector can share it (it needs only `parseRule`, not `rrule`).
- **Edit:** the card's Edit opens `todos/new` with `repeatRule` among the prefills (`TODO_PREFILL_PARAMS`); the form's Repeat control starts from it.

## Testing decisions

Tests check behaviour through public interfaces, as the area docs describe.

- **Unit:** `entryLinkId` (the same id on both sides, a different one per pair); the link schema (exactly one target); the mark's wording; `quickEntryRepeat` (each phrase family, the first day with today included, several weekdays, "every 4 hours" refused, month ends); `quickEntry.test.ts` rows (the item's line, a time and an assignee with a repeat, a dose line with "every", a provider line's warning and order, the weekday list kept whole, each new vocabulary row); `quickEntryPreview` (the repeat wording); `quickEntryCards` (the Edit prefill).
- **Integration:** `entryLinkService` (link and unlink a todo and an event; twice is one row; refused: a non-note source, a non-event entry target, a deleted target, another group's, a viewer, a non-member; a member of another group reads none; deleting a todo hard cascades); the sync upload (PUT, DELETE, a refused PATCH); the permissions test's row for the table; the replication role's read (`roles.int.test.ts`); reschedule and series edits keeping a note's link; `assistantActionService` (an `addTodo` with a repeat makes a repeating todo; one without a due day is refused); the connector (`mcpWrites.int.test.ts`: a `repeatRule` sent to `add_todo` is ignored).
- **Component:** the note's page (the Todos section: Add todo, Link a todo, remove, tick and Undo, done todos, a viewer's own tick, a reader with nothing sees no section; the Events section the same); the todo page's Note rows; an event's Notes list; the timeline's mark; quick entry (`timelineQuickEntryTodos.browser.test.tsx`: the item's line saves a repeating todo, the card's wording, Edit's prefill, the provider line's warning).
- **End to end:** one row added to `roundtrip`'s sync matrix for `timeline_entry_link` (a link made on one device reaches the server and the other), as every synced table has; unlinking is covered by the upload's integration test. No new check and no new step: the tick and the repeating tick are already there.
- **Prior art:** the provider links (`entryProviderService`'s integration tests, the With row's component tests, the matrix row), `todoRepeat.browser.test.tsx`, the LinkedTodos component tests, `quickEntry.test.ts`'s table.

## Out of scope

- Changing a todo's own link to one event (`todo.event_id`), or letting a todo link many events.
- Renaming "Appointment" to "Event" on existing screens, or the `appointments` area's names.
- Links from vitals, symptoms or doses; links between two notes.
- Linking from the todo form or an event's page (links are made on the note).
- Mentioning a todo or event inside the note's text (`@`), as providers are.
- Connector tools for links.
- Making a note and its todo from one quick-entry line.
- Repeat ends, "last friday of the month" and yearly repeats in quick entry; repeating events from quick entry.
- The connector's `add_todo` taking a repeat (B-253, connectors-3).
- Retiring the leftover reminder data (B-456, contract-migrations).
