## Problem

The orchestration core is about to move out of Caretook into Risa (B-543 step 2). A dry run on a scratch copy of only the 257 core files showed its tests aren't the core's own: on the sample project's config 560 of 1,991 tests failed in 54 files; with Caretook's config copied in, 206 failed in 25 (the land tests, `doc`, `skeptics`, `ci/gate` and others reading `scripts/ci/tiers.json`, `docs/agents/`, `scripts/project/check-plan-rules.json`, `scripts/ci/quarantine.txt`); with no root config the run hung in `lease.sh` (`file_mtime: command not found`, looping). Moved as they are, Risa's tests would fail or hang, and Caretook's would keep reading files it no longer owns.

## Solution

Every core test runs on a config the core owns: the sample project, or a fixture project with today's names and its own data. A shared setup file makes that the default, so no test falls back to the checkout's `risa.json`. What the tests checked about Caretook's own files (its tier data parses, every role doc is named, the never list is readable) becomes a project-data check the core runs on whichever project it serves, from `pnpm test:tooling` and the check. A config that fails to load stops the scripts instead of hanging them. A standalone-run command repeats the dry run on demand; when it passes in all three root modes, the move can go.

## User stories

1. As the user preparing the move, I want the core's tests to pass in a copy of only the core files, so that Risa's tests pass on day one (B-929).
2. As the user, I want one command that repeats the dry run, so that I (or the move's runbook) can prove it before the move and see which files still fail.
3. As an agent running a tooling script with no config, I want it to stop with one clear line, so that nothing hangs in `lease.sh` (B-929).
4. As a core test author, I want the fixture config by default, so that a new test never reads Caretook's files by accident.
5. As the user, I want Caretook's own data (tier data, check-plan rules, CI lists, role docs, preferences) still checked, so that a broken file is caught before it lands, in Caretook now and in any repo Risa serves later.

## Implementation decisions

- **The standalone run** (new core script): reads the manifest's `core` lines, copies them to a temp dir with a minimal `package.json`, links the checkout's `node_modules`, writes a Vitest config naming the core setup file and the core test folders, puts the chosen root config (`sample`: the sample project's; `project`: the checkout's `risa.json`; `none`), commits once on the config's trunk, runs Vitest with a JSON report and prints `<failed> <file>` lines and a total; exit 0 only when nothing failed. A per-file timeout (the progress reporter's idea: a file running past it is named as hung) so a hang is reported, not waited on. `--keep` leaves the copy for a look.
- **`lib.sh`'s failure path:** the config line stops the sourcing script (`exit 1`) with its one line; a test sources `lease.sh` with no config and asserts it exits within a second with that line.
- **The fixture project** (new folder beside the sample project): its `risa.json` with today's names, its own tier data and check-plan rules (or the sample's where tests pass on them), CI lists, and a small docs set (one role's additions, a preferences doc with a never list) that the doc and skeptic tests read. `config-fixture.mjs`'s `FIXTURE_CONFIG` points at it; `stubHookConfig` and `sampleFoldersConfig` start from it.
- **The core setup file** (new): sets `RISA_CONFIG` (unless set) to the fixture and `RISA_MACHINE_CONFIG` (unless set) to empty; Caretook's Vitest config names it in `core:unit`, `tooling:unit` and `tooling:browser`. `config-fixture.mjs` keeps its own default for scripts run outside Vitest.
- **Tests that copy Caretook files by path** (`scripts/ci/tiers.json` into throwaway repos: reclaim, rotate, stack, tidy-cli, ci-ids, check-run) copy the fixture's file the config names instead.
- **The project-data check** (new core command, generic): for the configured project, each failure one line naming the file: every path the config names exists; the tier data passes `tierDataProblems`; the check-plan rules load; the quarantine and brake lists parse with the project's id prefix; every role entry's file exists and every file in the docs folder but the preferences doc is a role's; the skeptic brief's rules read (the never list found); the gates' data runs through the time gate; the boundary lint passes on the tree (when the project has a manifest). the prompt golden the config names (`paths.promptGolden`) matches the prompts rendered on the project's config (the golden test's renderer, moved into a core module both use). Exit 1 on any. `prd.sh` dispatches it as `project-check`; `tooling-tests.mjs` and `check-tooling.mjs` run it first, and a failure fails the step.
- **The Caretook test that runs it in CI** (new, `scripts/project/`): reads `tool.prd` from `risa.json` and runs `<that> project-check` from the checkout; passes when the check does, and shows its lines when not.
- **The "this repo's" cases** (`doc`, `skeptics`, `ci-lists`, `tier-data`, `check-plan`, `config`, `time-gate`, `dev-brought`, `boundary`, `prompt-golden`): each runs on the fixture project, or is deleted where the project-data check now covers it (named in the slice).

## Testing decisions

- Unit tests (Vitest, `tooling:unit` / `core:unit`) for the standalone run's pure parts (which files it copies, how it reads the report), the project-data check on the fixture project (passes) and on broken copies (one line each), `lib.sh`'s stop.
- The standalone run itself is the end-to-end proof: run by each slice for its files and by the last wave in all three root modes. It isn't a Vitest test (it runs the whole tooling suite) and isn't a CI job.
- Prior art: `sample-project/repo.mjs`'s `makeRepo`, `config-fixture.mjs`, `tooling-tests.mjs`, the progress reporter's per-file watchdog (`scripts/ci/progress-reporter`, Caretook's: the idea, not an import).

## Out of scope

- The move itself (B-543 step 2, the runbook); Risa's own Vitest config, `package.json` and CI (step 2 writes them, naming the setup file this topic adds).
- Converting tests to the sample project's names where the fixture config keeps them passing.
- Caretook's `scripts/project/` tests (they may read Caretook's files; they stay).
- A CI job for the standalone run.
