The sync matrix rows are device-written; repeating todos keep their tags; the Planner's filter no longer depends on the timeline slice, and a tag has its own `EntryFilters` field beside the search; id collisions have defined outcomes; rename's upload path is pinned down; `record_tag` gets its own small handler for null targets; rename and delete moved from slice 1 to slice 3; slice 6 needs no stack; the topic's row names its order and hot files.

## Problem

A care group's records live in separate lists. Caretakers following something that cuts across them, such as a move to a new care home or a fall and its aftermath, have no way to mark the related notes, todos, providers, medications and events, or to bring them back up later.

## Solution

Each care group has one shared list of tags. People who can write put tags on timeline entries, events, todos, providers and medications, adding a new tag in the same step. Every list and the search page can filter by a tag. Tags sync to every member and work offline.

## User stories

1. As a caretaker, I want to put tags on a timeline entry or event, so that I can find related records later.
2. As a caretaker, I want to put tags on a todo, so that work on one concern stays together.
3. As a caretaker, I want to put tags on a provider or medication, so that they're grouped with the same concern.
4. As someone tagging, I want to add a new tag in the same step, so that tagging doesn't interrupt me.
5. As a group member, I want one shared tag list, so that we all use the same words.
6. As an Easy helper, I want to tag entries I logged, and only those, so that I can help organize without changing others' records.
7. As a viewer or Easy viewer, I want to see tags and filter by them, so that I can follow a concern without being able to change anything.
8. As an owner, admin or caretaker, I want to rename any tag, and as an Easy helper, a tag I created, so that a typo or better word is fixed on every record at once.
9. As an owner, I want to delete a tag after a clear confirmation, so that the shared list stays tidy and no record is lost.
10. As a member, I want to filter the timeline by a tag, so that I see only its entries.
11. As a member, I want to filter the Planner and todos by a tag, so that I see what's coming for one concern.
12. As a member, I want to filter providers and medications by a tag, so that I find the ones involved.
13. As a member, I want to filter search by a tag, or see everything with a tag, so that I can gather one concern across record types.
14. As a caretaker offline, I want tagging and filtering to work, and two devices adding the same tag to end up with one, so that offline use creates no duplicates.
15. As a caretaker rescheduling an event, I want its tags to come along, so that it stays with its concern.

## Implementation decisions

- **The tag rules module** (pure, client-safe, in a new `tags` schema area): `tagKey(name)`, `tagId(groupId, key, counter)`, `recordTagId(tagId, recordId)`, the name's Zod schema, `canTagRecord(role, record, userId)`, `canRenameTag(role, tag, userId)` and `?tag=` parsing and setting. Device and server both call it.
- **Table `tag`:** `id`, `group_id` (cascade with the group), `name`, `name_key`, `timestamps`, `audits`. Unique on `(group_id, name_key)` and `(group_id, id)`. Hard delete.
- **Table `record_tag`:** `id`, `group_id`, `tag_id`, `entry_id`, `todo_id`, `provider_id`, `medication_id`, `timestamps`, `audits`. Composite foreign keys on `group_id` to the tag and each target, cascading. A check for exactly one target. Unique per tag and target, and an index per target column.
- **Permissions:** `tag`: read and list any group role; create `LOGGERS`; update (name only) `WRITERS`, and Easy helpers through `groupOwn` on `created_by`, enforced in SQL; delete owners. When two people add the same tag offline, the first upload's author is its creator. `record_tag`: read and list any group role; create and delete `LOGGERS`; update `system`.
- **`tagService`:** `create` is idempotent on id. A create whose id exists returns that tag, even if it has since been renamed. A create whose name is held by another id is `tagService:nameTaken`. `rename` refuses a name in use with the same error and derives `name_key` from the name, ignoring any key a device sends. `remove` deletes the tag, and the links cascade.
- **`recordTagService`:** `link` and `unlink`, idempotent. It checks that both ends are live and in the group, then applies the tagging rule: writers on any target, an Easy helper only on a timeline entry whose `created_by` is them, read in SQL. Unlink applies the same rule to the link's target, whoever put the tag there.
- **Sync:** both tables join the `care_groups` stream for every role and the device schema. Upload: `tag` takes PUT, a name PATCH and DELETE, and a refused own-row update reads as `permissions:unauthorized` when the row exists, as `softDelete` does. `record_tag` gets a small handler like `linkTable`'s (PUT, DELETE; PATCH read-only) that passes null targets as null.
- **Repeating todos:** `todoService` copies the ticked todo's links to the next occurrence as the system, because a viewer's tick can create it. The device's twin writes the same derived ids, so its upload is a replay.
- **Device (`lib/tags/`):** live queries for the group's tags and a record's tags, and local writes that check the same rule first. Deleting a tag removes its links and the tag in one local transaction.
- **The picker sheet:** lists the group's tags with a filter box, toggles them on the record, adds a typed new name, and renames in place. Owners also get Delete, with a native `<dialog>` naming how many records carry the tag.
- **Filters:** each list's existing filter gains a "Tag" section when the group has tags, and `?tag=` stays in the URL. An unknown or deleted tag reads as no filter. `EntryFilters` gains its own `tag` field (a `record_tag` subquery), ANDed with the search's `match`, which it never replaces.
- **Search page:** `?tag=` narrows every section. With no text it lists all live records with that tag. Conditions, which can't be tagged, are left out while a tag is on.

## Testing decisions

- **Unit:** the tag rules module (keys, ids, the counter, `canTagRecord` for every role, `?tag=` parsing). Prior art: `timelineFilters.test.ts`.
- **Integration:** both services, every role against every target, cross-group refusals, idempotent replays, rename conflicts, cascades, and upload handling. Prior art: `conditionProviders.int.test.ts`, `syncRegistry.test.ts`, `roles.int.test.ts`.
- **Component:** the picker, chips and each list's filter. Prior art: `timelineFilters`, `todos`, `providers`, `medicationList` and `search` browser tests.
- **End to end:** one step in the existing `roundtrip` check: two clients add the same new tag to a record and converge. No new check.

## Out of scope

- Tags on conditions, allergies or care periods.
- Tags on a repeating series as a whole.
- Merging tags, tag colors, nested tags, and several tags in one filter.
- Tags in connectors, calendar feeds, emails, print views or the search index.
- Quick entry setting tags.
