## Problem Statement

`sync-safety` made sure a change the server refuses or fails on is kept and shown. Four gaps remain, found in code review and Codex review:

- **A screen's save can half-land.** Splitting a repeating event's series, ticking a repeating todo or skipping one writes several rows in one local transaction, but the server applies each row on its own. If it refuses one (a role changed offline, a conflict), the others still land: a series is cut short with no new series after it, or a chain loses its next occurrence.
- **A phone with its clock ahead dates the group's history wrong.** When a medication is stopped or a pass moved on that phone, the "Stopped …" entry is dated by its clock: a day ahead, it sits at the top of the history, tomorrow, and nobody can edit it.
- **Repeating todos go wrong under offline and concurrent use.** Reopening a todo whose next occurrence was moved to an earlier day leaves both open and repeating; two members ticking at once make two next occurrences; and a stale offline tick brings back a chain someone deliberately stopped.
- **Sign-ins and tabs can undo each other.** After an offline sign-out, signing in by a magic link or an invite is signed out again by the next page; and a tab left open while another tab switches user wipes the new user's data on its next navigation.

None of it was re-verified by the backlog session beyond what its notes say: each slice first reproduces its bug in a failing test.

## Solution

- **A device write lands whole or not at all.** The device uploads its writes whole, and the server applies each one in one transaction. A refusal anywhere refuses all of it; "Changes not saved" lists it once, with the reason.
- **Change entries never sit in the future:** the server dates them no later than its own clock.
- **Repeating todos keep one open occurrence per chain:** reopen finds the real successor, concurrent ticks make one next occurrence, and a stale tick never revives a stopped chain.
- **A sign-in is never undone by an older sign-out, and a stale tab never wipes someone else's data.**

## User Stories

1. As a caretaker splitting a repeating event's series offline, I want the change to save completely or not at all, so that the calendar is never left cut short. (B-294)
2. As a caretaker, I want a refused save shown once, with the reason, however many rows it touched, so that I know what to redo. (B-294)
3. As a caretaker, I want a save the server failed on retried and offered again as a whole, so that "Try again" never saves half of it. (B-294)
4. As a caretaker whose phone clock is wrong, I want "Stopped …" and other change entries dated no later than now, so that the history stays in order. (B-295)
5. As a caretaker, I want a change I make offline and the copy the server makes to stay one entry, so that history shows no duplicates. (B-295)
6. As a caretaker, I want reopening a repeating todo to take back its next occurrence even if someone moved it to an earlier day, so that the chain doesn't run twice. (B-383)
7. As a caretaker, I want two of us ticking the same todo at the same moment to make one next occurrence, so that it doesn't run twice. (B-384)
8. As a caretaker who stopped a repeating todo, I want it to stay stopped when a co-member's phone comes online with an old tick, so that my decision holds. (B-387)
9. As a caretaker who signed out offline, I want signing in again from a magic link or an invite to keep me signed in, so that I'm not thrown out on the next page. (B-730)
10. As a caretaker sharing a computer, I want a tab someone else left open not to wipe my data when I use the app in another tab, so that my local copy and its unsent changes stay. (B-296)

## Implementation Decisions

### A device write as one unit (`sync.upload`, the uploader)

- **An op names its device write.** Each op carries its device transaction's id (PowerSync's queue already records one for every write; a single-row write is a write of one). The request schema gains this optional field; ops without it are each their own write, as today.
- **The device sends whole writes.** The uploader fills a request with whole writes up to 100 ops; a write bigger than 100 goes alone. It never splits one across requests. The server accepts up to 100 ops, or up to 1,000 when they are all one write; anything else fails the request's schema (the existing 400 path, which resends one write per request, so the oversized write is refused alone and listed).
- **The server applies a write in one transaction.** Consecutive ops of one write run inside one database transaction, which every handler and service joins (they already take a transaction through their context; the upload registry's own transactions join it rather than start their own). At the first refusal the transaction rolls back and the server stops applying that write: the refused op is `rejected` with its own code and issues, and every other op of the write is `rejected` with a new `sync:writeRefused` code naming the refused op's id. The next write carries on.
- **A failure fails the write.** A throw or a non-4xx error rolls the write back and answers `failed` for the write's first op, with no results after it (the server's probe and 5xx rule are unchanged). The device acknowledges the ops before the write, counts the try against the write (keyed by its first op), and after the existing limit sets the whole write aside.
- **Results stay one per op**, so the result type is unchanged apart from the new code. Live-note compaction runs only for updates of committed writes.
- **The not-saved records name their write.** `unsaved_change` (local only) gains the write's id. "Changes not saved" groups a write's records as one line: the label of its first row that has one, the reason of the op that caused the refusal. Dismiss removes the whole line; "Try again" on a set-aside write resends all its records in one request as one write, and an `applied` write leaves the list.
- **Every multi-row device write is checked once.** The slice that builds it lists the device's multi-row writes (about 30 local transactions) and confirms none includes an op the server routinely refuses while the rest should land (a viewer's tick of their own todo, say, must still land whole). Any that does is split into two writes on the device, named in the hand-off.

### Change entries' time (the medication, pass and condition services)

- **One rule for a change's time**, beside the existing `toChangeTime`: from the device's `changedAt` it gives the **key** (the device's time, unchanged: the entry's derived id) and the **date** (the earlier of the device's time and the server's now: the entry's `occurredAt`). With no `changedAt`, both are now.
- The medication, medication pass and condition services (their change entries, and a condition manager unlink dated at the save's time) take both from it. A device's own copy of a change entry, uploaded as a timeline entry PUT, is satisfied by the server's row (create-if-absent) whatever order it arrives in; if it arrives first and creates the row, its `occurredAt` is clamped the same way.
- The device keeps writing its own clock locally; the server's copy replaces it at the next sync.

### Repeating todos (`todoService`, the device's todo module)

- **The todo row is locked** (`select … for update`, as other models already do) at the start of `complete`, `reopen`, `skip`, `removeUndoneNext` and `restoreOccurrence`, and the checks read the locked row. A second concurrent completion then sees it done and is a replay.
- **The successor is found by when it was made:** the live row of the same chain, other than this one, made at or after this todo was ticked, the earliest first; its due day plays no part. The server's `reopen` and the device's `reopenTodo` use the same rule, so both decide alike.
- **A tick's next occurrence is flagged on the upload** (the row's `_metadata`, as an Undo's delete already is): the device's tick writes its twin with the flag. The server's occurrence upload, flagged, never creates: it is satisfied by the row the server's tick made, or by nothing when the tick was a replay or the chain was stopped. Unflagged (a skip's), it keeps today's rule. The flag joins the device's other metadata constants in the todo rules.

### Sessions and tabs (`lib/auth`, `lib/sync`)

- **A pending sign-out remembers its session.** Each confirmed session check records the session's id on the device beside the confirmation it already records; an offline sign-out writes that id into the `caretook:sign-out-pending` marker. Finishing the sign-out first asks the server whose session the cookie holds: the same session is signed out (as today); a different one is a newer sign-in, so the marker is dropped and the session kept; none drops the marker. Offline it stays pending, as today. A marker with no id (no confirmed check on record) behaves as today. The sign-in page's own guard uses the same function.
- **A stale tab hands over instead of wiping.** When the tab's open database belongs to another user than the session now says, it closes its own handle without clearing (and forgets its in-memory caches, as `closeSync` does), then opens for the new user; the device's owner rule in `open` decides whether the file is wiped (another tab that already switched users has made the new user its owner, so nothing is wiped).

## Testing Decisions

- **The upload's integration tests** (the API package, prior art `syncFailures.int.test.ts`, `syncReplay.int.test.ts`): a write of three ops whose second is refused leaves nothing in Postgres and answers `rejected` with the codes above; the next write in the same request lands; a write whose op throws is rolled back and answered `failed`; a series split's real ops, uploaded as one write, land whole, and with its new series' insert refused land not at all. New files, never edits to another topic's cases.
- **The uploader's device tests** (prior art the uploader's stubbed-server tests): batches never split a write; a write over 100 goes alone; a failed write's tries are counted once and it's set aside whole; the records carry the write's id. **Component tests** for the not-saved page's one line per write and "Try again" on a write.
- **The change-time rule's unit tests** (pure: ahead, behind, equal, unreadable) and **integration tests** in the data package (prior art `conditionChange.int.test.ts`, `upsertReplay.int.test.ts`): a medication stopped with a `changedAt` a day ahead gets an entry dated now and the id of the device's time; replaying it writes no second entry; the same for a pass moved and a condition changed.
- **Todo integration tests** (prior art `syncTodos.int.test.ts` and the todo service's tests): a successor rescheduled to the same day and to an earlier day is taken away on reopen when untouched, and kept (with the reopened one stopping) when touched; two completions run concurrently on two connections with different `doneAt` days make exactly one next occurrence; a stopped chain (successor deleted) stays stopped when a stale tick and its flagged twin upload, while a skip's unflagged occurrence still creates. **Device tests** for `reopenTodo`'s successor rule and the twin's flag.
- **Session unit or device tests** (prior art `session.test.ts`, `sessionRules.test.ts`): a pending marker with the same session signs out; with a different session keeps it and drops the marker; offline stays pending; no id behaves as before. A device test (prior art `index.test.ts`) for the stale-tab handover: another user's session closes without clearing, and a file already owned by the new user isn't wiped.
- **No new browser check.** The browser checks the changed files map to run once per wave as usual (`roundtrip`, `session-end`, `sign-in` and the like); this topic adds no step to them, since the lean set has no room (see Notes).

## Out of Scope

- Rewriting `removePass` so it stops resending every medication's schedule from the device's copy (B-294's related note): a separate change-only-what-changed fix, not atomicity.
- Making a multi-row write the server makes itself (a connector's, a quick entry's) atomic: they already run in one service transaction.
- A field-level merge, conflict history or an "edited by someone else" notice.
- Per-group primary keys.
- A tab that stays on screen with the old user's data until its next navigation (it shows nothing new; its next navigation hands over).

## Notes

- **Nothing is live**, so there is no data migration and no compatibility with older devices to keep: the device and the server change together. No migration, no sync-config change, no new dependency, no seed change; the device's local-only `unsaved_change` table gains one column (local only, never synced: PowerSync applies the new schema on open, so no `datastore:reset`).
- **Atomic writes change what "refused" costs:** before, one refused row cost that row; now it costs the write. The audit of the device's multi-row writes (slice 1) is what keeps this from refusing more than it should.
- **The lean browser set has no headroom** (`sync-safety` left it at its ceiling), which is why the acceptance criteria use integration and device tests. Only the user raises the ceiling.
- **Hot files shared with other topics:** the upload registry and the device schema are shared with `symptom-catalog` (running), `planner-3` and `tags` (planned), which also hold `todoService` and the device's todo module. Edits to the shared registries stay additive (the rules across PRDs); the PRD table's hot files say what this topic holds, and whichever lands second syncs first.
