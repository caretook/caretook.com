## Problem

The symptom catalog fills up: names typed once, near-duplicates someone added on purpose, defaults a family never uses. Every one of them stays in the sheet's suggestions and in the similar-name check forever, and two names for one symptom split its history. Nobody can tidy it.

Quick entry, meanwhile, stops on a symptom that looks like one the group has and waits for a tap on "Use <name>" or "Add new". The person nearly always wants the existing one, so Enter should just take it.

## Solution

Group settings gets a Symptoms page listing the group's catalog with how much each symptom is used. Caretakers and up can archive a symptom: it disappears from suggestions and the similar-name check, its entries stay as they are, and it can be unarchived. Owners can delete a symptom by picking another to replace it: every entry of the old one moves to the new one, name included, on every device. The old name keeps pointing at the replacement afterwards, so an offline phone or a habit of typing it can't bring it back.

In quick entry, a symptom close to an existing one is saved as the existing one by default. The card says which, and one tap adds the typed name as new instead.

## User stories

1. As a caretaker, I want to see every symptom the group uses, with how often each is used, so that I can tell which ones are clutter.
2. As a caretaker, I want to archive a symptom we no longer log, so that it stops being suggested while its past entries stay as written.
3. As a caretaker, I want to unarchive a symptom, so that a mistake or a returning symptom is one tap to undo.
4. As an owner, I want to delete a duplicate symptom by choosing the one that replaces it, so that its history joins the right symptom.
5. As an owner, I want to see how many entries will move before I delete, so that I know what I'm changing.
6. As a member, I want moved entries to show the replacement's name on every device, so that the timeline, filters, summaries and visit prep all agree.
7. As a caretaker who was offline, or who types an old name out of habit, I want my entry to land on the replacement, so that a deleted symptom doesn't come back.
8. As a viewer or helper, I want the list read-only, or no way in, so that only the people trusted with setup can change the catalog.
9. As a caretaker typing an exact archived name, I want it logged without a question, so that archiving never blocks a log.
10. As a caretaker using quick entry, I want Enter to save a near-match as the existing symptom, so that I don't have to tap to confirm the obvious.
11. As a caretaker using quick entry, I want to see which name it will use and switch to adding mine as new, so that a real new symptom is still one tap away.

## Implementation decisions

- **The catalog row** gains two nullable, server-set columns, in one additive migration: `archived_at` (timestamptz) and `replaced_by_id` (uuid). A composite foreign key on `(group_id, replaced_by_id)` keeps a replacement inside the group, and a check stops a row replacing itself. A row is **active** with neither set, **archived** with only `archived_at`, and a **tombstone** with `replaced_by_id`. Both columns join the `symptom_type` sync query for every role and the device schema. The upload stays PUT-only, so a device can't set them.
- **The catalog rules** (`symptomCatalog`, pure, client-safe) learn the three states. `similarSymptoms` keeps matching `exact` on active and archived rows, but offers only active rows as `similar`. A new `resolveSymptom(name, catalog)` follows a tombstone to its replacement, so the device and the server share one rule.
- **The catalog service** gains `archive(ctx, { groupId, id })` and `unarchive(…)` (writers; idempotent; a tombstone is refused), and `replace(ctx, { groupId, id, replacementId })` (owners). `replace` runs in one transaction under advisory locks on both ids: it refuses the same id, another group's or a tombstone replacement. It moves every entry pointing at `id` (live and soft-deleted) to the replacement, setting `symptom_type_id`, `details.name`, `updated_at` and `updated_by`, and repoints older tombstones. Then it marks `id` as a tombstone and returns the number of entries moved. `ensure` returns the replacement for a tombstone's name. The entry write path (`timelineEntryService`) takes the resolved row and writes its name into `details.name`, so uploads, assistant actions and connectors all land on the replacement. The backfill points a null pointer at the resolved row.
- **API:** `timeline.symptomTypes.archive` and `.unarchive` (`symptom-catalog-2`) and `.replace` (`symptom-catalog-3`), each with `groupId` and `id` (`replace` also takes `replacementId`). They answer the row, or for `replace` the count moved; refusals come back as the usual errors. They join the procedure sweep.
- **Permissions:** `symptom_type` updates stay system-only in the permission map. The service checks the actor's group role (`WRITERS` to archive or unarchive, `OWNERS` to replace) and then writes past the system-only map, the way `add` checks `LOGGERS` today, recording the actor in `updated_by`. The settings page reads the same rule from a pure helper beside `groupSettingsAccess`.
- **On the device:** `useSymptomTypes` returns active and archived rows, each marked `archived`, and no tombstones. The sheet's and the Easy form's suggestion lists show active rows only. `addSymptomTypeIn` resolves a tombstone and returns the replacement's id and name, and the entry create and update writes (the timeline sheet and quick entry's batch) store that name. A device that hasn't synced the tombstone yet writes the old name, and the server rewrites it on upload.
- **The Symptoms page** (group settings, care-groups routes and `GROUP_SETTINGS_PAGES`) reads the local catalog with live-entry counts (a `.sync.ts` query), so it shows offline. Its writes are the oRPC calls above, with `NEEDS_CONNECTION` when offline. The controls come from the role rule: writers see Archive and Unarchive, owners also see Delete.
- **Quick entry** (`withSymptomGates`): an unanswered card with similar names now applies the closest one to its action and carries a `symptomDefault` (the typed name, the name in use, the other similar names) instead of a blocking gate, so `canSaveCards` and Enter go ahead. The card shows "Saves as <name>" with "Use <other>" buttons and "Add “<typed>” as new"; an answer is remembered per card as today. The sheet's gate (`useSymptomGate`, `SymptomGate`) doesn't change, and quick entry gets its own small notice component.

## Testing decisions

- **Unit:** `symptomCatalog`: the three states, `similarSymptoms` (archived exact, no archived similar), `resolveSymptom` (tombstone, one step). `quickEntryCards`: `withSymptomGates` defaults to the closest name, an answer overrides it, and the card no longer waits. Prior art: `symptomCatalog.test.ts`, `quickEntryCards.test.ts`.
- **Integration:** the service: archive and unarchive (roles, idempotent, a tombstone refused); `replace` (owners only, same-group and live replacement, every entry moved with name and `updated_by`, soft-deleted ones too, older tombstones repointed, count returned); `ensure` and the entry write resolving a tombstone; the backfill leaving archived defaults and tombstones alone. Sync: the new columns reach every role, a device PATCH of `symptom_type` is refused, and an upload naming a deleted symptom lands on the replacement. The procedures go in the sweep. Prior art: `symptomType.int.test.ts`, `syncSymptomTypes.int.test.ts`, `procedureSweep.int.test.ts`.
- **Component:** the Symptoms page (counts, the archived section, controls by role, archive and unarchive, the delete dialog with its count, offline refusal); the sheet's and the Easy form's suggestions without archived names; quick entry's default card (Enter saves the similar name; "Add new" saves the typed one). Prior art: `groupSettings.browser.test.tsx`, `timelineSymptomGate.browser.test.tsx`, `timelineQuickEntry.browser.test.tsx`.
- **End to end:** none. The move is one server transaction whose sync is ordinary row replication (the integration tests cover it), and `roundtrip.spec.mjs`, the check that owns two-device flows, is a running topic's hot file (`fixes-tooling`).

## Out of scope

- Renaming a symptom, or merging two without deleting one.
- Undoing a delete: entries stay moved, and a tombstone can only be cleared by hand.
- Changing the symptom sheet's or the Easy form's gate (B-898 is quick entry only).
- Symptom charts, trends, or categories.
