# Loop handbook

How PRDs, orchestrators and loops run: the `pnpm prd` commands, worktree isolation, the browser check budget, landing a wave, the browser checks and their gotchas. Moved out of AGENTS.md, whose core rules (working rules, branches, the backlog, _Rules across PRDs_ and _Loop rules_) still apply. [docs/orchestration.md](orchestration.md) is the human guide to the same system.

## Running loops

**`pnpm prd <command>`** is the one front door (`scripts/loops/prd.sh`; run it from any worktree, and `pnpm prd help` lists it):

| Command                                        | What it does                                                                                                                                          |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm prd status`                              | every worktree: branch, commits ahead, dirty or clean, containers, its dev server link, who holds the browser and check leases, and the load averages |
| `pnpm prd status-watch [seconds]`              | `status`, redrawn every few seconds (default 5) until Ctrl-C                                                                                          |
| `pnpm prd start <topic>`                       | create (or find) the PRD's worktree and stack, and print the command that opens its orchestrator                                                      |
| `pnpm prd queue <topic> [--manual]`            | wait for a free PRD slot (in queue order), then create the worktree and open a fully autonomous orchestrator in that terminal                         |
| `pnpm prd plan <topic> [--open] [B-n…]`        | a docs-only worktree for writing a PRD and plan; `--open` starts its planning session in that terminal                                                |
| `pnpm prd plan`                                | no topic: a backlog and inbox planning session in the main checkout, which helps decide what's next (`prompt.sh backlog`)                             |
| `pnpm prd slice <topic> <n>`                   | a slice's worktree; a stack only for `Stack: yes`                                                                                                     |
| `pnpm prd serve [name] [--restart]`            | run that worktree's dev server in the background (it outlives the session) and print the link; `--built` serves a check build instead                 |
| `pnpm prd check`                               | `pnpm check` under a machine-wide check lease (three at once, `CARETOOK_CHECK_SLOTS`), then record that this commit passed                            |
| `pnpm prd browser <check> [args…]`             | run one check under a machine-wide lease (four at once); `--changed` for what the diff needs; `--suite`; `--timeout <s>`                              |
| `pnpm prd sync`                                | merge `dev` into this PRD branch                                                                                                                      |
| `pnpm prd ready [topic]`                       | the ready-to-land report: the link, the backlog items it addresses, what changed, any blockers                                                        |
| `pnpm prd land <topic> [-m subject]`           | merge `prd/<topic>` into `dev` in the main checkout: **only when the user says to land it**                                                           |
| `pnpm prd rm <name>`                           | remove a worktree, its stack, its dev server and, if merged, its branch                                                                               |
| `pnpm prd stack up\|down [name]`               | add or remove a worktree's dev stack (containers, data, env files, slot), keeping the worktree                                                        |
| `pnpm prd gc [--list\|--yes]`                  | merged slice worktrees and stacks stopped for a day, removed after a yes                                                                              |
| `pnpm prd test-db status\|up\|down\|list\|use` | the shared test Postgres (:5436)                                                                                                                      |
| `pnpm prd prompt orchestrator\|plan\|slice`    | the first prompt for a session (`orchestrator <topic> --auto` for the run-through mode)                                                               |

### Isolation

**Isolation** (the scripts behind those commands, in `scripts/loops/`; `lib.sh` holds the shared parts):

- `new.sh <kind> …` makes a worktree in `.loops/`:
  - `new.sh prd <topic>`: `.loops/<topic>` on `prd/<topic>` from `dev`, with a stack. It prints the command that starts its orchestrator.
  - `new.sh slice <topic> <n>`: `.loops/<topic>-<n>` on `slice/<topic>/<n>` from `prd/<topic>`. It gets a stack **only when the plan says `Stack: yes`** (or `--stack`); a missing field means none. Add one later with `pnpm prd stack up [name]`, and remove it with `pnpm prd stack down [name]`, which takes away the containers, their data, the stack's env files and the slot lease, and keeps the worktree.
  - `new.sh plan <topic>`: `.loops/plan-<topic>` on `plan/<topic>` from `dev`, **without** a stack.
  - Options before the kind: `--slot N`, `--stack`/`--no-stack`, `--base B`. If the branch already exists it's checked out instead, which resumes a removed worktree.
- **Slots.** A stacked worktree **leases the lowest free slot (1–19)**: lock directories in `.loops/.slots/<N>`, taken atomically, so two orchestrators never get the same one. A slot is also busy while a worktree's `.env` names it or one of its ports listens.
  - Ports: slot N in 1–9 is web 6N73, Postgres 6N34, test Postgres 6N35, PowerSync 6N80. Slots 10–19 use 7(N−10) in place of 6N (7073 … 7980). CDP and proxy ports shift by N×1000. Compose projects are `caretook-loopN` and `caretook-loopN-test`.
  - The files it writes (all gitignored): the root `.env` (Compose's project name and ports), `packages/data/.env` and `.env.test.local` (database URLs and `PG_TEST_PORT`), `apps/web/.env` (auth and PowerSync URLs, `WEB_PORT`), and `.env.loop` (`SLOT`, `BASE_BRANCH`, `BASE`, `CDP_PORT_OFFSET`, `PG_CONTAINER`, `SEED_USER_PASSWORD`). Secrets are copied from the main checkout's `packages/data/.env` and `apps/web/.env`.
  - **The shared test Postgres** (`docker-compose.shared-test.yml`, `scripts/loops/test-db.sh`, `pnpm prd test-db`): one server on :5436 (Compose project `caretook-shared-test`; data in a tmpfs; the default bridge network, so it adds no Docker network). Every worktree, stacked or not, gets its own database there, `caretook_test_<name>`, named in `packages/data/.env.test.local` (`SHARED_TEST_DB=1`), so `pnpm check` runs everything, integration tests included, in a stackless worktree. The integration globalSetup starts the server and creates the database on first use, then clears and migrates only that database; `rm.sh` drops it. New stacks have no `-test` container; worktrees made before this keep theirs, or switch with `pnpm prd test-db use`. `test-db down` stops the server and deletes every worktree's test database. In a stackless worktree, never run `pnpm datastore:*:test`: without a root `.env` it targets the main checkout's `caretook-test` project.
  - `pnpm prd status` also shows the shared test Postgres and flags `merged:` slice worktrees (the slice's tip was merged into its PRD branch) and `stopped stack:` worktrees (stopped for over `CARETOOK_GC_STOPPED_HOURS`, default 24). `pnpm prd gc` lists the same and, after a yes (`--yes` skips the question, `--list` only lists), removes the merged ones with `rm.sh` and takes the stopped stacks down.
- `ls.sh` lists every worktree: slot, branch, commits ahead of the branch it merges into, dirty or clean, its stack, the PRD count against the cap, and stale leases.
- `rm.sh <name> [--force] [--keep-branch]` stops the worktree's containers, deletes its database files, removes the worktree and releases its slot. Then it **deletes the branch if it's merged** into its parent (`slice/…` into `prd/<topic>`; `prd/` and `plan/` into `dev`), and keeps it otherwise. It refuses uncommitted changes, and a PRD worktree whose slices still have worktrees, unless `--force`.
- `prompt.sh orchestrator <topic>` and `prompt.sh slice <topic> <n>` print the first prompt for those sessions.
- The main checkout keeps the default ports (5173, 5434, 5435, 8080).
- Every port, the Compose project name and the PowerSync audience come from env, defaulting to the main checkout's values. If you add a service, a port or a hardcoded container name, make it configurable the same way.

### Capacity and the browser check budget

**Capacity.** One stack uses about 250 MB idle (the Docker VM has 32 GB), so the limits are CPU and attention: `pnpm check`, Vite and Chrome on 10 cores, and each orchestrator's context. Three PRDs with two or three slices each, plus their integration worktrees, is about 12 slots. `pnpm prd check` waits for one of three check leases, so loops finishing together queue instead of piling up. Six busy stacks at once (three loops plus two other PRDs) pushed the load average past 500: `pnpm check` took 25 minutes, tests hit their 5 s timeouts, and sign-ins in browser checks timed out. Rerun a failure like that once the load drops before debugging it.

**Browser check budget.** Browser checks were 63% of all tool time across the first PRDs (850 runs, about 10 h), and about 30% of runs failed, mostly on timeouts and PowerSync 401s under load, which caused more reruns and more load. The orchestration PRD split the work in two:

- **Screens get component tests; cross-cutting flows get end-to-end checks.** What one device decides on its own (layout, menus, filters, sheets, role rules, focus, keyboard, widths, themes, local writes and the live queries they update) is a component test beside the screen (`*.browser.test.tsx`, Vitest browser mode on the test device: [components](domain/components.md#component-tests)), and runs in `pnpm check`. What needs the real server, sync or a production build is an end-to-end CDP check: sign-in and the session, first sync, the sign-out wipe, two devices converging, offline then reconnect, uploads refused by permissions, invites and email, the CSP and the check build. A new screen gets component tests, not CDP steps; a new check is only for a flow.
- **The lean set** is the manifest's `e2e yes` checks (`scripts/loops/checks`), and it is the suite (`--suite`, and `--changed`'s `@suite`): `phase2`, `roundtrip`, `live-notes`, `app-shell`, `layout-offline`, `sign-in`, `first-sync`, `signout-wipe`, `session-end`, `invites`, `ui`, `marketing`, about 5 minutes on a quiet machine. Every other check (`routing`, `settings-layout`, `providers`, `groups`, `medications`, `upcoming`, `search`, `profiles`, `profiles-contacts`, `care-periods`, `devices`, `admin`) is `e2e no`: still run by name and by `--changed` for its own area's files, but out of the suite until its screens move to component tests. Each has a backlog item for its move (B-114 to B-125, one per check), as do the screen steps left in `roundtrip` (B-126) and `invites` (B-127). No lean check yet asserts an upload refused by permissions (B-128); porting the lean set to Playwright Test is B-129. Moving one: write component tests for its screen steps, delete each covered step (the hand-off maps step → test), keep only its flows, then set it `e2e yes` if a flow is left, or delete it and its `check-areas` rules if none is.
- **While building:** `pnpm test:components --changed <base>` for the screens you change, and `pnpm prd browser <check>` only for a flow you touch (or an unmoved area's own check). Never the suite.
- **Before hand-off:** `pnpm check` (component tests included), then `pnpm prd browser --changed` once (it diffs against the PRD branch).
- **At landing** (step 1 of _Landing a wave_): `pnpm prd browser --suite`, the lean set once, against a freshly restarted server, plus, by name, any `e2e no` check that `pnpm prd browser --changed --base dev --list` names (an unmoved area the wave touched; `--suite` doesn't run those). A wave that changes no screens or flows (quick fixes, tooling, the data layer, docs) runs only `pnpm prd browser --changed --base dev`, which is often nothing.
- **The backstop:** the dev keeper runs the lean set on `dev` (`pnpm prd browser --suite` from any synced worktree, on a quiet machine) **before opening the PR to `staging`**.
- **This overrides any plan** that says "rerun every browser check after each merge". **Run each check once:** never rerun one that passed, and never run `--suite` twice for one landing. **No checks between merges:** an orchestrator merges a wave's slices without running `pnpm check` or browser checks in between; everything runs once, before landing.
- **Machine leases** (`scripts/loops/lease.sh`) are one library for every machine-wide limit: `browser` (4, `CARETOOK_BROWSER_SLOTS`), `check` (3, `CARETOOK_CHECK_SLOTS`), any other kind 1 (`CARETOOK_<KIND>_SLOTS`). A lease is a lock directory in the main checkout's `.loops/.lease/<kind>/<N>`, taken atomically, taken over from a dead holder, and released on every exit. Waits are bounded by `CARETOOK_<KIND>_WAIT` (browser 20 min, check 30 min); giving up exits 75. Shell: `lease.sh take|release|run|hold|holders`; Node: `takeLease(kind)` from `scripts/loops/lease.mjs` (component tests' Chromium takes a `browser` lease this way). `CARETOOK_LEASE_ROOT` (every kind) and `CARETOOK_BROWSER_LEASES` (browser only) move them, which tests do; `CARETOOK_LEASES=off` takes none. `pnpm prd status` shows the holders.
  - **The browser leases moved** from `.loops/.browser/<N>` to `.loops/.lease/browser/<N>` (orchestration slice 9). A worktree whose `browser.sh` predates it still takes the old path until it runs **`pnpm prd sync`**. Until then the new `lease.sh` counts every live holder under the old path against the four (`holders` lists them as "old path"), but an old copy can't see the new path, so the limit is exact only once every worktree has synced. `CARETOOK_BROWSER_OLD_LEASES` moves the old path (tests). Drop that counting once no worktree uses it.
- **Run every check through `pnpm prd browser`** (`scripts/loops/browser.sh`), never `node <check>.mjs` directly. It holds a `browser` lease, waiting while all four are taken (up to `CARETOOK_BROWSER_WAIT` s), sources the worktree's `.env.loop`, prints the load average at start and end, and logs to the worktree's git dir.
- **The diff picks the checks: `pnpm prd browser --changed`.** It maps every changed file (committed since the base, staged, unstaged and untracked) through `scripts/loops/check-areas`, the table below as globs, and runs only those checks, in the manifest's order, with a table. Screens with component tests map to none (or to the flows they reach), as do docs, plans, tests, tooling and the data layer below the upload switch; a lib module with a sibling unit test needs none. Build config, dependencies, sync rules and migrations need the lean set (plus any unmoved area's check another file names). A file no rule covers runs `sign-in`, `phase2` and `roundtrip`, with a warning: **add a rule to `check-areas`** when you add a screen, a check or a shared module. `--base REF` sets what it diffs against (default: the worktree's `BASE_BRANCH`, else `origin/dev`), `--head REF` a commit instead of the working tree, and `--list` shows each file's checks without running anything.
- **The manifest** `scripts/loops/checks` lists every check in suite order: usual seconds, cap, never-exits, and `e2e` (in the lean set). `checks.test.mjs` keeps it and `check-areas` in step, so a new check adds a line to both; `browser.sh` refuses to run without it. `CARETOOK_BROWSER_SUITE` overrides the suite.
- **Three limits end a check, each as TIMEOUT** (so the one retry applies): silence, no output for `CARETOOK_BROWSER_SILENCE` s (default 90); its cap, `--timeout`, else the manifest's, else 600 s; and for `--suite` and `--changed` the suite cap, `CARETOOK_BROWSER_SUITE_CAP` (default the sum of the selected caps), past which the running check is killed without a retry and the rest are listed `NOT-RUN` (a failing run). A kill stops node, Chrome and the proxies.
- **Output is trimmed:** the terminal shows the ▶ and ■ lines, FAIL, TIMEOUT and error lines with their diagnostics block, FLAKY lines and the table (a failure that printed none of those gets the log's last lines). `--verbose` prints everything; the full output is always in the log named on the ■ line.
- **One automatic retry.** A failed check is rerun once when the failure looks like contention: load above 40 at its start or end (`CARETOOK_BROWSER_BUSY`), a timeout, a 401 or PSYNC_S2101 in its log. It first waits up to 5 minutes for the load to drop. A pass on the retry is **FLAKY**: it counts as passing, and it's recorded in `.loops/.browser-flakes.log` (the date, worktree, check, why, and the first run's log). A FLAKY step in the lean set is a bug to fix, not to retry: file it. A failure that repeats, or one that doesn't look like contention, is a real failure: debug it. Don't rerun by hand on top of this.
- **Smoke mode** (for a quick look while building): `--smoke` (with one check, `--changed` or `--suite`) exports `SMOKE=1`, and each check runs only its core path. In a check, `step(name, { smoke: true }, fn)` (`cdp.mjs`) marks a smoke block; an unmarked block prints `SKIP <name> (smoke)` in smoke mode. Hand-offs and landings use full mode.
- **A browser step that asserts pure logic comes out once a unit test covers the same rule**, and one that asserts a single device's screen once a component test does. Checks keep the wiring across the server and sync.
- **Run long checks under `caffeinate -i`** (`caffeinate -i pnpm prd browser …`): the Mac sleeps at night and stalls them mid-run. **Don't run two checks at once in one worktree**; the lease already limits the machine.
- **Checks run on a check build.** `pnpm prd browser` serves a production build of the web target with `VITE_CHECK_BUILD=1` (5–7 s to build), which keeps `window.caretookSync` and `window.caretookModules` (the device modules, which `providers.mjs` loads). In a `.loops` worktree with a stack it starts one when no server is running, swaps it in for a dev server, and rebuilds and restarts it when the app source, `public/`, `.env`, a `package.json` or the lockfile is newer than the build (the main checkout's server is left alone). `--dev` runs against the dev server instead; `pnpm prd serve --built` serves a build by hand. A build has no Vite websocket, no dependency re-optimization reloads and no stale deps. It runs with `NODE_ENV=production`, so Better Auth's rate limits are on; `cdp.mjs` gives every page its own `x-forwarded-for`, so they apply per page. PowerSync's `[PowerSync]: Sync aborted` is the shared sync worker's teardown log for a page that closed, broadcast to the next page: the checks ignore exactly that warning.

### Starting and steering a PRD

**Starting a PRD (the user):** `pnpm prd start <topic>`, then run the command it prints in a new terminal (`cd .loops/<topic> && claude --remote-control prd-<topic> "$(scripts/loops/prompt.sh orchestrator <topic>)"`). From then on the user steers that PRD from its orchestrator's console. **The orchestrator first asks for a landing mode** (unless the plan's _Status_ records one): ask before each landing, run everything through (start every ready slice, land each green wave, clean up, ask only real questions), or land chosen waves or slices automatically; it records the answer in _Status_.

**Queueing a PRD (the user):** `pnpm prd queue <topic>` in a terminal of its own, left running. It waits until fewer than `CARETOOK_MAX_PRDS` PRD worktrees exist (a slot frees when a finished PRD is removed with `pnpm prd rm`), taking slots in queue order (tickets in `.loops/.queue/`, one lock around count-and-create in `.loops/.prd-start.lock`), then creates the worktree and opens its orchestrator there in run-through mode (`prompt.sh orchestrator <topic> --auto`; `--manual` for the asking prompt). Queueing is the user's go-ahead for every landing of that PRD.

**Waiting on another PRD:** an orchestrator whose next slice is blocked by another PRD's work asks that orchestrator (ListAgents, SendMessage) to message it when the work lands in `dev`, and sets a background check that exits when `git log dev` or `pnpm backlog list` shows it, then syncs and carries on. Both prompts say so.

**Keep each orchestrator's context small.** A session may run wave after wave; start a fresh one (the same command) whenever it gets slow or confused. The plan's _Status_ section makes that safe at any wave boundary.

- It works from its plan's _Status_ section, the backlog, the loops' hand-offs, `git diff --stat` and `pnpm check` output. It doesn't read whole diffs or debug inside a loop: it sends the problem back to that loop's agent with SendMessage.
- Before it ends, it updates its plan's _Status_ section (what's merged, with SHAs; what's ready; open issues) and its backlog items. Those are the hand-off to the next orchestrator.

### Running a wave

**PRD orchestrator, per wave:**

1. Read your plan and `pnpm backlog list --prd <topic>`. A slice is **ready** when every slice it's blocked by has been merged into `prd/<topic>`. Start only what the user asks for, and `claim` its items.
2. For each ready slice: `pnpm prd slice <topic> <n>`.
3. Spawn one background agent per slice (not with `isolation: worktree`; it already is one), with the prompt from `pnpm prd prompt slice <topic> <n>` plus anything the slice needs that the plan doesn't say.
4. As each loop hands off, review its branch: `git diff prd/<topic>...slice/<topic>/<n>`, its hand-off, and that the acceptance criteria are covered.
5. Merge **in plan order** into `prd/<topic>`, in your integration worktree, with `git merge --no-ff -m "feat(<topic>): <what it adds> (slice <n>, B-<n>)" slice/<topic>/<n>`. Resolve conflicts in the shared files yourself. Don't run checks between merges: they run once, before landing (step 1 of _Landing a wave_). A failure there goes back to the loop that caused it.
6. Once merged: `pnpm backlog done B-<n>` for its items, then `pnpm prd rm <topic>-<n>` (it deletes the merged branch). Start the slices it unblocked.
7. **Land the wave** when it's green. Don't wait for the whole PRD: small, frequent landings keep PRDs from drifting apart.

### Landing a wave

**Landing a wave in `dev`:**

1. **Sync and check.** In the integration worktree: `pnpm prd sync` (merges `dev`; resolve conflicts there, regenerate your migration if `dev` gained one, `pnpm datastore:reset`), `pnpm prd serve --restart`, the wave's browser checks (a wave that changes screens or flows: `caffeinate -i pnpm prd browser --suite`, the **lean set once**, one check at a time under one lease, with a pass/fail table, plus, by name, any `e2e no` check that `--changed --base dev --list` names; any other wave: `pnpm prd browser --changed --base dev`; see _Browser check budget_), then `pnpm prd check`. Backlog-only commits on `dev` don't count as drift, so `pnpm backlog` writes never force another sync.
2. **Serve it and report.** `pnpm prd serve --restart`, then show the user the output of `pnpm prd ready`: the dev server link and seed accounts, the backlog items this landing addresses (grouped as bugs fixed, features, changes), what's still open in the PRD, the commits, and warnings for a migration, seed, sync-config or dependency change. Add the browser checks you ran and two or three things worth trying by hand. If it lists blockers, fix them first.
3. **Wait for the user.** They may try it at the link, ask for changes (send those back to a loop, then repeat from step 1), or say to land it.
4. **Land on their word only:** `pnpm prd land <topic> -m "feat(<topic>): <what the wave adds> (B-<n>, …)"`. It refuses unless the branch is synced and `pnpm prd check` passed on its tip, so the code landing in `dev` is exactly the code that was checked; no recheck on `dev` is needed. It prints what the main checkout needs afterwards (`pnpm datastore:reset`, a PowerSync restart after a sync-config change, `pnpm install`) and never pushes: `git push origin dev` is the user's.
5. Other orchestrators run `pnpm prd sync` at their next wave boundary, not mid-wave.
6. When a PRD is finished and landed, `pnpm prd rm <topic>` removes its worktree and deletes `prd/<topic>`.

A go-ahead covers one landing, unless the user chose a landing mode that lands waves automatically (or queued the PRD), which covers those landings. An agent never lands on its own judgment, never with `--force` unless the user says so, and never for another PRD.

**Planning agents are the exception:** a `plan/<topic>` branch touches no code, so its agent may land it whenever its PRD or plan is ready, without waiting for a go-ahead, and may pass `--force` (`pnpm prd land plan/<topic> --force -m "docs(<topic>): …"`). Before landing, check that `git diff --stat dev...plan/<topic>` lists only `plans/` and `docs/` files; if anything else changed, it's not a planning branch, so ask first.

The _Rules across PRDs_ and _Loop rules_ are in [AGENTS.md](../AGENTS.md).

### Loop gotchas

**Gotchas:**

- **Dev server only (`--dev`):** the first visit to a route on a fresh loop can make Vite re-optimize dependencies and reload the page mid-check. If a browser check times out on its first run, run it once more before debugging.
- Merging two branches that each generated a migration conflicts in drizzle's `meta/_journal.json` and snapshots. Keep the one already in the target (`dev`'s, at a sync), then regenerate yours on top (`pnpm datastore:generate`) and recheck its SQL order.
- After a merge or sync that changes seeds or migrations, run `pnpm datastore:reset` in that worktree; the merged seeds can differ from either side's.
- **Docker runs out of networks at about 21** ("all predefined address pools have been fully subnetted"): every stack makes **one** network (two for worktrees made before the shared test Postgres). `new.sh` then fails at the test database; once another stack is removed, rerun `pnpm datastore:start && pnpm datastore:start:test` in the worktree. Never prune other projects' networks.
- **A check tab behind another tab gets no animation frames**, so taps and dialogs stall: bring it forward (`Page.bringToFront`, `medications.mjs`'s `toFront()`) before tapping. After Escape or a close, wait for the closed state and focus together (`ui.mjs`'s `settlesOn`), never a fixed sleep.
- **Running `new.sh` for several worktrees at once** can fail at migrate with "Connection terminated unexpectedly": a fresh Postgres restarts once after its first-boot init. The containers are fine; rerun `pnpm datastore:start && pnpm datastore:start:test` in each.
- **The first check run after a PowerSync restart** (`docker compose restart powersync`, after editing `sync-config.yaml`) can fail on slow first sync (`live-notes.mjs` timing steps). Rerun once before debugging. `pnpm datastore:reset` doesn't need this: it restarts PowerSync with empty bucket storage and waits until it's ready.
- **Merges can break another slice's browser check** without either slice being wrong (live notes slices 4 and 8 both filled the header's `actions`). The checks before landing catch it; a slice's own checks don't.
- **Long-running dev servers** (`--dev` only) can serve stale optimized deps after merges ("Invalid hook call"). Run merged checks against a freshly started server.

## Browser checks (`scripts/browser-checks/`)

End-to-end flows are verified in headless Chrome over CDP with plain Node scripts (no Playwright yet); screens are verified by component tests ([components](domain/components.md#component-tests)).

- **Run:** `pnpm prd browser <check> [args…]` from the worktree (`phase2`, `phase2.mjs` or a path). It uses Node 24 from `.nvmrc` (the checks need the global `WebSocket`), the worktree's `.env.loop` (`BASE`, `CDP_PORT_OFFSET`, `PG_CONTAINER`; the main checkout's defaults when there is none, and `BASE` then defaults to `http://localhost:5176`), runs from `scripts/browser-checks/`, and holds a machine-wide lease (at most four checks at once). `--changed` runs only what the diff needs (see _Browser check budget_). `--timeout <s>` kills a check, and its Chrome, after that long. `--suite` runs the lean set (the manifest's `e2e` checks), pausing 2 s between them (`CARETOOK_BROWSER_SUITE` and `CARETOOK_BROWSER_PAUSE` override), and exits non-zero if any failed.
- **Scripts:** `cdp.mjs` (the harness, with `tap()` for real CDP mouse taps; every DevTools command fails after 120 s (`CDP_TIMEOUT_MS`), so a stuck page fails instead of hanging; it collects uncaught errors, rejections, `console.error` and failed loads in `page.uncaught`, and a `waitFor` timeout prints `page.diagnose()`: the URL, those errors and the start of `main`; pass `{ quiet: true }` for an expected timeout); `proxy.mjs` (offline, because CDP network emulation doesn't cut PowerSync's stream; it tunnels CONNECT, so WebSockets work, and going offline leaves Vite's `vite-hmr`/`vite-ping` sockets open, so a proxied page still gets Vite's reload after a re-optimization instead of loading two copies of React and Yjs); `live-notes.mjs` (notes and events across devices: uploads as the member, a rename reaching the viewer, Live now and Join from another device, who's typing and concurrent edits converging over three devices, offline then reconnect, a time change and a delete reaching the others, a shared link opened signed out; the page itself is component tests); `roundtrip.mjs` (sheet entries: symptom add, edit, delete, validation, offline, viewer, sign-out wipe); `phase2.mjs` (the timeline end to end: the first page arriving by sync, a provider linked on the server showing and going on its row without a reload, and offline filtering then an entry from elsewhere arriving on reconnect; Chrome in America/Los_Angeles; the screen itself is component tests); `signout-wipe.mjs` (never exits on its own; `pnpm prd browser` stops it after its last line); `sign-in.mjs` (one sign-in request on a double click, by holding `/api/auth/token`); `layout-offline.mjs` (an offline layout change survives and reaches the server); `first-sync.mjs` (a slow first sync, held by its own proxy, shows the syncing state and never "no care groups"; `HOLD_MS`); `app-shell.mjs` (the frame's flows: the theme before first paint after a real reload, Sign out from the menu, the owner's rename reaching the server and coming back through sync, and members across two devices (role changes and removal reaching the other device); it restores the seeded names and memberships; the frame's screen is component tests); `ui.mjs` (the primitives on a real check build: built CSS, React Aria under the CSP, real taps and keys, at 420 dark and 1280 light); CDP ports 9601–9604; tags its rows `grp<run>`/`GR<run>` and deletes them).
  - **They're order-independent:** each run tags the entries it makes, asserts against its own entries (never global idle state or seed order), moves only its own documents' edit times back before "who's typing" steps, and soft-deletes what it made at the end. They exit non-zero on failure.
  - Sign out in a check with `page.signOut()` (`cdp.mjs`), which goes through the account menu.
  - `page.signIn` retries once (with a log line) when `/api/auth/token` answers 401.
  - **member@ has two groups.** `page.signIn(email, pw)` goes on from the group list to Dev Family's timeline (`page.openDevFamily()`); pass `{ home: true }` to stay where `/app` lands. A check that needs a one-group user's "straight to the timeline" signs in as caretaker@ or viewer@. psql queries that pick seeded rows filter on Dev Family's id (`0b6f3c1e-5d1a-4c2e-9a77-3f1d2b8c0001`).

Don't wrap them in `timeout` yourself.
  - Headless Chrome's clipboard needs `Emulation.setFocusEmulationEnabled`. Pin the zone (`Emulation.setTimezoneOverride`, America/Los_Angeles) for layout checks.
- **Patterns:**
  - Use a 420×900 window.
  - Sign in as the `@example.com` seeds (`SEED_USER_PASSWORD`).
  - React Aria buttons and menu items need a `pointerdown` before `.click()`.
  - Set inputs through the native value setter, then dispatch `input`.
  - Collect console errors, and take screenshots.
  - **Better Auth allows about 3 sign-ins per 10 s per page** on a check build (the dev server doesn't rate-limit). Past that it answers like a wrong password. The limit is per client IP, and `cdp.mjs` gives every page its own `x-forwarded-for`, so checks don't pause before a new page's sign-in; only sign-ins repeated on one page need spacing.
- **Afterwards:** nothing; the checks clean up after themselves, so no reset is needed between runs.

## Dev gotchas

- **The dev server on another port:** Better Auth trusts only `BETTER_AUTH_URL` and `AUTH_TRUSTED_ORIGINS`, so use `BETTER_AUTH_URL=http://localhost:5176 AUTH_TRUSTED_ORIGINS=http://localhost:5176 pnpm --filter @caretook/web dev --port 5176 --strictPort`. PowerSync's JWKS then needs `PS_JWKS_URL` set to match.
- **After `pnpm build:native`:** lint can report `no-unsafe-argument` in `routes/rpc.ts` and `routes/api/auth.ts`, because the native typegen overwrote the web route types. Run `pnpm typecheck`.
- **`/app` error handling:** `/app` has its own `ErrorBoundary`. It keeps the frame, and avoids React's "script tag" warning from the root boundary.
- **Route discovery is `initial`** (`react-router.config.ts`). With the default (lazy), navigating to a path not seen yet (a note just saved offline, `/entries/:id`) asks the server for `/__manifest` first, and fails offline.
