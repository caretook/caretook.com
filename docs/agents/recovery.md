# Recovery

For the recovery agent, and anyone bringing the machine back: what `pnpm prd down` and `pnpm prd recover` do. A resumed orchestrator then follows [orchestrator](orchestrator.md#recovery).

- **Before a planned restart:** `pnpm prd down` records what's up in `.loops/.down.json` (adding to an existing record, the dispatcher included) before stopping the dispatcher, servers, stacks (`compose stop`, data kept) and the shared test Postgres. `--stay [<why>]` first writes `.loops/.stay-down.json`: an unattended recover and the watchdog then do nothing; a recover by hand clears it.
- **After a restart, crash or usage limit:** `pnpm prd recover` takes `.loops/.recover.lock` (a second recover exits 75 and does nothing), starts Docker (`CARETOOK_DOCKER_WAIT_SECS`), keeps the dispatcher's intent (`.loops/.dispatch-intent.json`) before clearing stale locks, starts the test Postgres, brings stacks up one at a time (waits for Postgres, migrates, retries a failed migrate once), starts servers, then reopens the dispatcher in a background tab **only when every step above succeeded**, waiting for it to hold its lock (`CARETOOK_RECOVER_DISPATCH_SECS`, 60) before dropping the intent, so a failed reopen is retried next run. Then it lists cut-off landings, prints gc offers and opens the recovery agent (`--no-agent` stops before it; a failed step skips it). The record is deleted only when every step succeeded. Without a record, stacks come back for PRD and active slice worktrees, servers for PRDs. `--at HH:MM` or `--wait` (probes `claude -p ok` every 10 min) wait out a usage limit. `--unattended`: no terminal, the agent in a background tab, and one report (topic `recover`) on failure (`CARETOOK_RECOVER_REPORT=off` skips it). `--dry-run [--json]` only shows.
- **The migrate marker:** a stack writes `.loops/.migrate/<name>` while migrating; one a crash left is reported and the migrate reruns, even on a stack that's up.
- **A cut-off landing:** `land` journals each step in `.loops/.landing/<branch>.json` (`land-journal.mjs`, `decide` is pure; git and GitHub say what happened). `pnpm prd land --resume <branch>` finishes a merged one from its step (one merge, a synced dev), undoes an unmerged one (aborting a merge only when `MERGE_HEAD` is the recorded tip) so it goes through `land` again, or asks (exit 3, journal kept). Plain `land` refuses a branch with a journal. The recovery agent and a resumed orchestrator run it before anything else.
- **The usage reading:** the status line and a `StopFailure` hook (both settings files) run `usage.mjs`, writing `.loops/.usage/<session>.json` atomically and never failing the session. A window read over `CARETOOK_USAGE_STALE_MIN` (15) minutes ago or past its reset doesn't count (none left: unknown); within one reset the higher percent wins; `overage` is a plan window at 100%. A `rate_limit` stop marks the session stalled until its reset (from the input, else the readings). `pnpm prd usage [--json]`; status prints a `USAGE:` line.
- **The watchdog** (`watchdog.mjs`, `decide` pure; `pnpm prd watchdog [--dry-run [--json]]`) runs `recover --unattended` after a reboot past a down record, a stale dispatcher lock or kept intent, or a dead unended `prd`/`plan` record newer than the last good recover and its own first run (so closing a hand-opened tab counts as a crash, once). Stay-down, a running recover, paused, a down record with no reboot since, or a limited reading each mean nothing. Failures back off 10, 20, then 30 minutes with one report per incident; 75 is neither. State `.loops/.watchdog.json`; it prints only when its decision changes and always exits 0.
- **Autostart:** `pnpm prd autostart install|remove|status` writes the LaunchAgent `com.caretook.prd-watchdog` (the watchdog from the main checkout every 300 s and at login, `AbandonProcessGroup`, Node 24 and each tool's folder on its `PATH`, log `.loops/.watchdog.log`); install is idempotent; `status` names a tool that doesn't resolve and exits 1. Tests use `CARETOOK_LAUNCH_AGENTS_DIR` and `CARETOOK_LAUNCHCTL`.
- **The drain** (`drain.mjs`, pure; a step in the dispatcher's tick): `normal`, `draining` at `CARETOOK_USAGE_DRAIN` (85%) on the 5-hour or weekly window, `limited` at `CARETOOK_USAGE_STOP` (98%), overage, or a stall not yet reset. Draining: no start, plan or reopen (`--resume` doesn't override; `CARETOOK_USAGE_WATCH=off` does) and `pnpm prd slice` refuses with the reason; wait for the reset. Limited: each managed session is marked stalled (`error: limited`) and sent TERM, KILL a tick later, but never one running a landing; hand-opened sessions get one report and keep running; no claude opens (no `claude -p` probe, helper or rotation). An unknown reading never drains and files one report.
- **The inventory** (`inventory.mjs`, pure; facts from `inventory-facts.mjs`) alone classifies worktrees (`prd`, `plan`, `active`, `merged`, `stackless`) and orders the actions; it also reports `migrating`, `dispatcher.intent`, `recover` and `landings`. Stale means the holder is gone (a slot with no worktree, the dispatcher's lock with its pid gone, the backlog lock after 30 s); live locks are never touched.
- **The recovery agent** (main checkout, `prompt.sh recover`) messages each live `prd-`/`plan-` session to carry on, reopens the rest with `pnpm prd open <target>` (`--continue` on a saved conversation, else the resume prompt, plus `--auto` when _Status_ records run-through; an iTerm2 tab, or the printed command), reports and ends. While the dispatcher runs (`dispatcher.running` in `recover --dry-run --json`) it leaves `managed` sessions to it. It changes nothing. Slice worktrees are refused: their orchestrator respawns them. A record marked `rotating` (a rotation cut short) reopens fresh with the resume prompt, never `--continue`. The agent's own session is recorded as `recover` (kind `recovery`) and, like a backlog session, reopens fresh in the main checkout.
- **Bye:** a message of just 'bye' runs `pnpm prd bye` after the agent's own check: its report table is sent.
