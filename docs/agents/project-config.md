The orchestration tooling is split from Caretook (PRD: [`plans/orchestration-split-prd.md`](../../plans/orchestration-split-prd.md)): the **core** is Risa ([interrobangc/risa](https://github.com/interrobangc/risa)), a dev dependency pinned to a release's commit (`node_modules/risa`; the `risa` command is the machine's release, `~/.risa/releases/<tag>`), and **Caretook's** side is its config, hooks, role additions, checks and CI jobs. A change to the core is made in Risa's repo, released, and repinned here. Read this before changing a file under `scripts/ci`, `scripts/project` or `.githooks`, or `risa.json`.

## The config

- **`risa.json`** at the root holds every Caretook fact the core uses. The core's loader (`loops/config.mjs`: `get`, `dump`, `check`; an unknown or mistyped key is an error) finds it through `RISA_CONFIG`, which the `risa` command sets from the machine config's entry for the current checkout; else, for the installed package (imports, CI), the `risa.json` at the root of the current directory's checkout. `scripts/project/risa.mjs` is Caretook's plain read, with no core file.
- **Keys:** `tool` (the command names, below), `paths` (backlog, inbox, archive, plans, docs, `agentsDoc`, `preferences`, `promptGolden`, `browserChecks`, `checksManifest`, `checkAreas`, `brakeList`, `quarantine`, `tierData`, `checkPlanRules`, `tooling`), `roles` (each role's doc), `branches` (trunk, protected, prefixes), `backlog` (`prdsHeading`, `idPrefix`, `zoneOverflowItem`, `ciFailureTopic`), `commands`, `stack.portEnv`, `stack.checkBuild` (the check build `reclaim.sh` clears), `testProjects`, `hooks`, `boundary.appPaths`, `claude.configDir` (optional).
- **The machine config** (`~/.risa/machine.json`; `RISA_MACHINE_CONFIG` overrides the path): the repos Risa works in, here Caretook's main checkout and `~/git/risa` with `"work": false` (`RISA_WORK_SELF=1` lifts it for one process), each with an optional `claudeConfigDir`. With the switch off, the dispatcher starts and plans nothing in that repo and `start`, `queue`, `plan <topic>` and `slice` refuse; reads stay open.
- **The command names** come from `tool`: `risa` and `risa backlog`. The generic role docs' `{{prd}}`/`{{backlog}}` are filled from them by `risa doc <role>`. Caretook's own hints read `tool` themselves: `node scripts/project/risa.mjs tool prd`, or a few inline lines (`packages/data/test/globalSetup.ts`).
- **Backlog ids** are `B-n`. Risa's are `RISA-n`, and it reads an old `B-n` as its own (`formerIdPrefix`): items moved there kept their numbers.
- **The shared names** come from `name` (`caretook`): the backlog lock, the markers, the watchdog's launchd label `com.caretook.prd-watchdog`, the CI status context `caretook-ci`. `scripts/project/project-data.test.mjs` pins them.
- **The git hooks** keep their own protected-branch constant; a Caretook test checks it against the config.
- **Role docs** (`risa doc <role> [section]`): ten roles, each a generic doc in Risa's `loops/docs/<role>.md`. Caretook adds to each with `roles.<role>.additions` (`docs/agents/<role>.md` and `docs/orchestration.md`), a file printed after it, so it continues only the generic doc's last section; an opening `<!-- … -->` pointer is left out. Each additions file has a budget figure (`scripts/project/doc-budget.config.mjs`). Prompts name a doc only by this command.

## Hooks

Each is a command in `hooks`, run by the core from the project checkout's top; an unset one is skipped, but for `check`.

- **`check`** (`scripts/project/check-body.sh`): the check's body. The core's `check-hook.sh MODE BASE TOOLING [OWN…]` runs it, then the tooling tests (`testProjects.tooling`: `project:unit` and `project:tooling`, plus the browser harness when TOOLING is 2). In: the mode, base and own test files as arguments, a state directory and a counts file in the environment. Out: the exit code, the state files `step`, `failed`, `flaky`, `times` and `slowest`, and the counts; the contract is in `check-hook.sh`'s header. The core keeps the lease, load gate, log, limits and rerun rules.
- **`checkAreas`** (`scripts/project/check-areas.mjs`): `resolve --root --areas --base [--head]`, files on stdin (`risa browser --changed`).
- **`docBudget`** (`scripts/project/doc-budget.mjs`): `land <trunk> --head <branch> --repo <main>`. Exit 1 is a breach; any other failure is "failed to run".
- **The stack hooks** (`scripts/project/stack.sh`, `serve.sh`, `test-db.sh`): `stackUp`, `stackDown`, `stackStatus`, `stackReady` (`ready=` on every answer, exit 0 yes, 1 no; no `ready=` is a failed call, read as unknown; `containers=`; `stopped_secs=` with none running), `stackStop` (keeps the data), `stackStart` (migrates, never seeds; `migrating=yes` just before the migrate), `stackEngine` (`running=`, `name=`), `stackLeftovers` (repeated `volume=`, `image=` and `kept=` lines; `remove volume|image ID`), `serve`, `testDb` (`facts`: `running=`; `orphans`: `orphan=` lines; `use`: `database=`, `port=`, `summary=`). `risa rm` dies on a failed `stackDown`; recover keeps the migrate marker when the start fails.
- **`lease`** (`bash node_modules/risa/loops/lease.sh hold`): the project's own code takes a lease as `<command> <kind> --label L --watch P` (`apps/web/test/browserLease.ts`).
- **`browser`** (`scripts/project/browser-run.sh`, the plain runner): `list` prints `<check>\t<spec>`; `run [--output DIR] [--results FILE] [--timeout S] <check>… [-- ARG…]` runs them with Playwright and prints each check's lines (`N/M passed` is the tally the hang watchdog reads), exit 0 on a pass. It holds no lease. The core's gate (`risa browser`: the load wait, caps, retries, the hang watchdog, the lease) reaches checks only through it, and CI's browser job (`scripts/ci/browser-job.mjs`) spawns only the runner. Its test, `scripts/project/browser-run.test.mjs`, is the `tooling:browser` project. `serve … --built --fresh` tells the gate whether the check build is current.
- **`landing`** (`scripts/project/landing.mjs`): `try [MAIN]` prints what to try in a landing report; `notes`, with the changed files on stdin, prints the migration, seed and sync notes (in `risa land` and `risa ready`).

## The check plan and CI

- **The check plan:** the engine is the core's; the rules are Caretook's `scripts/project/check-plan-rules.json` (its shape is in the engine's header, Risa's `loops/check-plan.mjs`). `scripts/project/` and `risa.json` are tooling: a change only there asks for no tier.
- **The tier data** `scripts/ci/tiers.json` has two readers: Caretook's `tiers.mjs` (the workflow's plan job, `node:fs` only) and the core's `risa/ci/tier-data.mjs`; `tiers.test.mjs` compares them. Its `gates` key is the time gates' data (each measure's aim, cutoff and `armed`, and `quietLoadPerCore`), judged by the core's `risa/loops/time-gate.mjs`, which `scripts/ci/test-job.mjs` imports. Those two are the only core modules Caretook's CI runs.
- **`scripts/ci/`** is all Caretook's: the GitHub jobs (`browser-job`, `test-job`, `env`, `zones`, `verdict`, `quarantine-setup`, `progress-reporter`: a per-file watchdog, 300 s or `CARETOOK_CI_FILE_LIMIT`, so a hung file is named in the verdict's `failed.hung`; its output goes to the git-ignored `ci-results/`), `tiers.mjs`, `lists.mjs`, `release-jobs.mjs`, the tier data and the two lists. `risa ci` (runs, gates, candidates, promotion, filing) is the core's.
- **The verdict is a file contract:** the core reads it with its own reader (`ci/ci-runs.mjs`), never importing `verdict.mjs`. `VERDICT_VERSION` is in both; `verdict.test.mjs` ties them, and checks `buildVerdict` against Risa's `ci/verdict.fixtures/`, both reached by file URL from `risa/ci/tier-data.mjs`. Optional fields (a failed test's `message`, `hung`) keep version 1. `lists.test.mjs` fails on a brake or quarantine entry that names no test.
- **Tests** (`vitest.config.ts`): Caretook's tooling tests are `project:unit` and `project:tooling` (`pnpm test:project`) and `tooling:browser`; the core's run in Risa's repo. `pnpm test:tooling` runs the core's tooling lint and tests on Caretook's config. Run tooling tests with `RISA_*` and `CLAUDE*` unset (B-932).
