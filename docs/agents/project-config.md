The orchestration tooling is being split from Caretook (PRD: [`plans/orchestration-split-prd.md`](../../plans/orchestration-split-prd.md)): the **core** (Risa, later a tool of its own) and **Caretook's** scripts and data. Stage 1 drew the line in place; nothing moved out yet and the commands are still `pnpm prd` and `pnpm backlog`, named by the config. Read this before changing a file under `scripts/loops`, `scripts/backlog`, `scripts/ci`, `scripts/project` or `.githooks`.

## The config

- **`risa.json`** at the root holds every Caretook fact the core uses. The loader is `scripts/loops/config.mjs` (`get`, `dump`, `check`; an unknown or mistyped key is an error; `loadConfigOrExit(who)` prints one `<who>:` line and exits 2). Bash reads it once per process through `lib.sh`: `config_get KEY`. `RISA_CONFIG` overrides the path (tests). `scripts/project/risa.mjs` is Caretook's plain read, with no core file.
- **Keys:** `tool` (the command names, below), `paths` (backlog, inbox, archive, plans, docs, `promptGolden`, `checkAreas`, `brakeList`, `quarantine`, `tierData`, `checkPlanRules`, `tooling`), `roles` (each role's doc; `role_doc`, below), `branches` (trunk, protected, prefixes; `branchKinds()`), `backlog` (`idPrefix`, `formerIdPrefix`, `zoneOverflowItem`, `ciFailureTopic`), `commands`, `stack.portEnv`, `stack.checkBuild` (the check build `reclaim.sh` clears), `testProjects`, `hooks`, `boundary.appPaths`, `claude.configDir` (optional: the Claude config folder for this project's sessions), `tool.self` (optional: set only in Risa's own `risa.json`, so the work switch defaults off there).
- **The machine config** (`~/.risa/machine.json`, loader `scripts/loops/machine.mjs`; `RISA_MACHINE_CONFIG` overrides the path, empty for none, as `config-fixture.mjs` sets for tests): the repos Risa works in, each with `path`, an optional `work` switch and an optional `claudeConfigDir` (a path, or `{ <role>: <path>, default? }`). No file: today's behaviour. With the switch off, the dispatcher starts and plans nothing in that repo and `start`, `queue`, `plan <topic>` and `slice` refuse; reads stay open. Off by default only for the tool's own repo; `RISA_WORK_SELF=1` lifts it for one process. A `claude` the core starts gets `CLAUDE_CONFIG_DIR` from `host.mjs`: `RISA_CLAUDE_CONFIG_DIR`, then the machine config's entry for the role, then `claude.configDir`, else Claude Code's default; usage readings follow the account.
- **The command names** come from `tool`, never a literal: Node's `toolCmd.prd` and `toolCmd.backlog` (`config.mjs`, read at first use, not import), Bash's `${prd_cmd}` and `${backlog_cmd}` (`lib.sh`), and `{{prd}}`/`{{backlog}}` in the generic role docs, filled by `doc <role>` (`doc.mjs`'s `fillNames`). Caretook's own hints read `tool` themselves: `node scripts/project/risa.mjs tool prd`, or a few inline lines (`packages/data/test/globalSetup.ts`).
- **Backlog ids** come from `backlogIds()`: Caretook's are `B-n`. A project that sets `formerIdPrefix` reads an old id as its own (Risa: `B-772` is `RISA-772`).
- **Commands the core runs** (install, typecheck, datastore, hooks install, the tooling tests) go through `run_project`, in a subshell. `find_repo` finds the main checkout; `in_main` tells whether a script runs there.
- **The git hooks** keep their own protected-branch constant; a Caretook test checks it against the config.
- **Role docs** (`pnpm prd doc <role> [section]`, `doc.mjs`): ten roles, each a generic doc in `scripts/loops/docs/<role>.md` (the core's). A project adds to one with `roles.<role>.additions`, a file printed after it (so it continues only the generic doc's last section; a section mixing in the project's names stays whole in its half; an opening `<!-- … -->` pointer is left out), or swaps it whole with `replacement`. Caretook's: `docs/agents/<role>.md` and `docs/orchestration.md`, all additions. Each half has a budget figure (`doc-budget.config.mjs`), the two adding up to the role's. Prompts and core files name a doc only by this command.

## The line

- **The manifest** `scripts/loops/boundary.manifest`: `<path> core|project`, sorted, one line per tracked file under the five folders, tests included. **A new file there needs its line.**
- **The lint** `scripts/loops/boundary.mjs` (a test in `tooling:unit`): rules `project-env`, `project-name`, `app-path`, `core-to-project`, `project-to-core`, `host-call` (only `host.mjs` calls `osascript`, `launchctl`, `claude`, `codex`, `gh` or names Claude Code's folders) and `tool-command` (no core file outside tests holds the literal `pnpm prd` or `pnpm backlog`, comments included). The others read imports, spawns and path strings, not comments. Blind spots: paths built from pieces, bare names with no extension, paths in a regex group.
- **The allowlist** `boundary.allowlist`: `<path> <rule> <count> [# why]`, exact counts; shrink it with `--write`, never grow it. Since orchestration-split-3 it is stage 1's **residual list**: 22 lines, each with the why it waits for the move (the package scripts, the Vitest tooling projects, `ci.yml`'s tooling jobs and the deploy workflow test, the tier data and its test, the check-plan rules and their test, the doc-budget data, `hooks.lease`, CI's time-gate feed, the verdict test, the manifest's folders, the shared-names sample, `_global`).
- **Copied, not shared:** `package-diff.mjs`, `status-trim.mjs` and the CI lists parser `lists.mjs` each have a core copy and a Caretook copy.
- **The sample project** `scripts/loops/sample-project/` (`risa.json`, `repo.mjs`'s `makeRepo(main, { config, files })`, its own rules, check script and prompt golden; prefixes `topic/`, `part/`, `draft/`, `quick/`) is what the core's tests run on; their made-up paths use its folders (`web/`, `db/`, `handbook/`), and `config-fixture.mjs`'s `sampleFoldersConfig(dir)` gives tests a config whose check-plan rules name them. A test that copies `scripts/backlog` or `scripts/loops` into a throwaway repo copies `config.mjs` too.
- **The fixture project** `scripts/loops/fixture-project/` (project `fixture`) is the sample's twin with today's names (trunk `dev`, `prd/` `slice/` `plan/` `hotfix/`, ids `B`, `pnpm prd`/`pnpm backlog`), its own tier data, rules, quarantine, brake list and docs, so tests expecting those names never read the checkout's `risa.json`. Its folders are `app/` and `api/` (not Caretook's) so the boundary lint passes, and `boundary.mjs` counts it as a fixture for the tool-command rule. Every path its config names must exist (the project-data check passes on it).

## Hooks

Each is a command in `hooks`, run by `run_hook` from the checkout's top; an unset one is skipped, but for `check`.

- **`check`** (`scripts/project/check-body.sh`): the check's body. `check-hook.sh MODE BASE TOOLING [OWN…]` runs it, then the core's tooling tests (`check-tooling.mjs`, `testProjects.tooling`, plus `browserHarness` when TOOLING is 2). In: the mode, base and own test files as arguments, a state directory and a counts file in the environment. Out: the exit code, the state files `step`, `failed`, `flaky`, `times` (`<seconds> <step>` lines, the tooling step's too) and `slowest` (`<seconds> <file>`, each test step's ten slowest), and the counts. The contract is in `check-hook.sh`'s header. The core keeps the lease, load gate, log, limits and rerun rules (`check-run.sh`).
- **`checkAreas`**: `resolve --root --areas --base [--head]`, files on stdin (`browser.sh`'s `--changed`).
- **`docBudget`**: `land <trunk> --head <branch> --repo <main>`. Exit 1 is a breach; any other failure is "failed to run".
- **The stack hooks** (`scripts/project/stack.sh`, `serve.sh`, `test-db.sh`): `stackUp`, `stackDown`, `stackStatus`, `stackReady` (`ready=` on every answer, exit 0 yes, 1 no; no `ready=` is a failed call, read as unknown; `containers=`; `stopped_secs=` with none running), `stackStop` (keeps the data), `stackStart` (migrates, never seeds; `migrating=yes` just before the migrate), `stackEngine` (`running=`, `name=`), `stackLeftovers` (repeated `volume=`, `image=` and `kept=` lines; `remove volume|image ID`), `serve`, `testDb` (`facts`: `running=`; `orphans`: `orphan=` lines; `use`: `database=`, `port=`, `summary=`). Bash calls them through `lib.sh`'s `stack_hook`, Node through the core's `hooks.mjs` (`runHook`, 127 for an unset hook; `fact`, the last value; `factList`). `rm.sh` dies on a failed `stackDown`; recover keeps the migrate marker when the start fails. Tests use the sample project's stub hook (`tools/stack-hook.sh`), set up by `config-fixture.mjs`'s `stubHookConfig`.
- **`lease`** (the core's `lease.sh hold`): the project's own code takes a lease as `<command> <kind> --label L --watch P` (`apps/web/test/browserLease.ts`); the core's Node tools use `lease.mjs`.
- **`browser`** (`scripts/project/browser-run.sh`, the plain runner; orchestration-split-3 wave 1): `list` prints `<check>\t<spec>`; `run [--output DIR] [--results FILE] [--timeout S] <check>… [-- ARG…]` runs them with Playwright and prints each check's lines (`N/M passed` is the tally the hang watchdog reads), exit 0 on a pass. It holds no lease. The core's gate (`browser.sh`: the load wait, caps, retries, the hang watchdog, the lease) reaches checks only through it, and CI's browser job (`scripts/ci/browser-job.mjs`) spawns only the runner. The gate's tests run on the sample project (`tools/browser-hook.sh`); the runner's own test is `scripts/project/browser-run.test.mjs`, in the `tooling:browser` project, which holds both owners' harness tests until the move (`SHARED_PROJECTS`). `serve … --built --fresh` tells the gate whether the check build is current.
- **The host layer** (`scripts/loops/host.mjs`, core): the one core file that opens tabs, sends notifications and talks to launchd (`osascript`, `launchctl`), runs `claude`, `codex` and `gh`, picks Node (nvm), and knows Claude Code's own files (its config folder and `CLAUDE_CONFIG_DIR`, the project transcripts, the session settings and the status-line and `StopFailure` hook input). Shell callers use its CLI (`node host.mjs tab <line> <title> <0|1>`, exit 3: no tabs). The lint's `host-call` rule holds it.
- **`landing`** (`scripts/project/landing.mjs`): `try [MAIN]` prints what to try in a landing report; `notes`, with the changed files on stdin, prints the migration, seed and sync notes (`landing_hook`, in `land.sh` and `ready.sh`).

## The check plan and CI

- **The check plan:** the engine is the core's `check-plan.mjs` (`checkPlanFor(project)`, `proposedTiers()`); the rules are Caretook's `scripts/project/check-plan-rules.json` (its shape is in the engine's header). `scripts/project/` and `risa.json` are tooling: a change only there asks for no tier.
- **The tier data** `scripts/ci/tiers.json` has two readers: Caretook's `tiers.mjs` (the workflow's plan job, `node:fs` only) and the core's `tier-data.mjs` (`tierData()`; `tierDataOrExit("ci")` gives a broken file one clear line). A test compares them. Its `gates` key is the time gates' data (each measure's aim, cutoff and `armed`, and `quietLoadPerCore`; shape and defaults in `tier-data.mjs`'s header), judged by the core's `time-gate.mjs`; a measure arms with `armed: true`.
- **`scripts/ci/` by owner:** Caretook's are the GitHub jobs (`browser-job`, `test-job`, `env`, `zones`, `verdict`, `quarantine-setup`, `progress-reporter`: a per-file watchdog, 300 s or `CARETOOK_CI_FILE_LIMIT`, so a hung file is named in the verdict's `failed.hung`; its output goes to the git-ignored `ci-results/`), `tiers.mjs`, `lists.mjs`, `release-jobs.mjs`, the tier data and the two lists. The core's are `ci*.mjs`, `gate`, `release-gate`, `candidate`, `promote`, `release`, `outstanding`, `filing`, `blame`, `ci-lists.mjs`.
- **The verdict is a file contract:** the core reads it with its own reader (`ci-runs.mjs`), never importing `verdict.mjs`. `VERDICT_VERSION` is in both; a shape change regenerates `scripts/ci/verdict.fixtures/` from `buildVerdict`. Optional fields (a failed test's `message`, `hung`) keep version 1. `lists.test.mjs` fails on a brake or quarantine entry that names no test.
- **Tests by owner** (`vitest.config.ts`): `core:unit` and `tooling:unit` are the core's; `project:unit` and `project:tooling` are Caretook's and run alone with `pnpm test:project`. Every tooling test is in exactly one. `pnpm test`, `test:tooling` and `test:browser-harness` keep their sets until the move.
