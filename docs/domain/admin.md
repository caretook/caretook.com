# Staff and the admin panel

The admin area's rules and decisions (staff roles, `/admin`, audit log, settings, announcement). AGENTS.md's core rules still apply; an orchestrator folds a landing's decisions in here.

PRD: [`plans/admin-prd.md`](../../plans/admin-prd.md) (done; B-91). **Staff never see care data**: no entries, documents, providers, medications or recipient profile fields beyond name and preferred name; counts use `count(*)`.

- **Roles and capabilities** (`db/schema/admin/staffRules.ts`, client-safe; nothing else names `support`): `STAFF_CAPABILITIES`, `staffCan`, `isStaff`, `staffCapabilities`, and the guards `roleChangeRefusal` and `disableRefusal` (`self`, `lastAdmin`, `unknownRole`, `unchanged`; wording in `STAFF_REFUSAL_MESSAGES`). Support: `users.read`, `users.help`, `groups.read`, `accessCodes.write`, `staffGroups.create`, `waitlist.read`, `audit.read`, `settings.read`, `users.limits`. Admin: those plus `users.disable`, `users.setRole`, `groups.manage`, `settings.write`. `pnpm admin:grant <email> [--role admin|support]` sets a role (actor-less audit entry). Seed: `support@example.com`.
- **Guards:** every admin procedure is `staffProcedure(capability)`; services start with `staffRefusal(ctx, cap)` and `auditActorId(ctx)` (`services/staffAccess.ts`). `requireStaff(request, capability?)` returns `{ authUser, api, capabilities }`; pages render only the viewer's controls; no capability is the 404. The nav is `routes/admin/adminSections.ts` (`ADMIN_SECTIONS`, each with its capability); `/admin` opens the first the viewer may see (Users). Staff get an **Admin** item in the account menu (`lib/admin/adminLink.ts`; native opens `<VITE_API_ORIGIN>/admin`).
- **Audit** (`admin_audit_log`, `adminAuditService`): every staff write calls `record(tx, …)` in its own transaction, so a refusal or failed audit write leaves nothing; views (`user.view`, `group.view`) and `user.search` (`changes.query`) use an awaited `record`; a bare listing is unaudited. No one can update or delete rows: the roles SQL revokes UPDATE/DELETE on it from the app (`APP_APPEND_ONLY_TABLES`). Actions are `AUDIT_ACTIONS` (`db/schema/admin/adminAudit.ts`; no DB check, so adding one needs no migration); changed fields go through `auditChanges(before, after, fields)`. New changing actions require a reason (`staffReasonZSchema`, 1–500 chars); older access-code and staff-group ones record none. `/admin/audit` filters by actor, target, action and dates in the URL, 50 a page; user and group pages list theirs with `AuditEntryList`.
- **Users** (`accountAdminService`, `admin.users.*`, `/admin/users[/:userId]`): search by part of a name or email; the account page shows sign-in methods, sessions (device from the user agent), groups, the last 20 outbox rows (template, status, attempts, error code from `mailErrorCode`; never data or body) and recent audit entries. Help actions (`users.help`): resend verification, send reset (tokens made as Better Auth makes them, `staffAccountMailer` in `packages/auth/src/staffEmails.ts`, queued in the transaction), sign out one session or all (all also disconnects every assistant, in the same transaction). Care group limit (`groupLimitService.forUser`/`setForUser`, `admin.users.groupLimit`/`setGroupLimit`, `{ started, limit, override }`): read with `users.read`, set 1–1000 or null (default) with `users.limits` and a reason; `user.setGroupLimit` audits `{ groupLimit: [before, after] }`, unchanged records nothing. The Groups section shows "Started n of limit" ("(default)" without an override) and, with `users.limits`, Change limit (`GroupLimitControl`: blank for the default, a reason) through the page's `setGroupLimit` intent; tests build the page's loader data with `accountPageData` (`adminWorld.tsx`).
- **Disable** (`users.disable`; `user.disabled_at`, `disabled_by`, `disabled_reason`): one transaction sets it, deletes every session, disconnects every assistant, voids pending sign-in codes and links, audits. Enforced only in `packages/auth` (`disabled.ts`): a session-creation hook, a `hooks.before` on password and code sign-in (so an unverified disabled account can't learn its password was right), the JWT `definePayload`, `getAuthUser`, and the email senders (checked in the background, so answers match an unknown address). Every refusal answers as a wrong password or code, unknown address or no session. Help actions refuse a disabled account (`accountAdmin:disabled`). Not yourself, never the last enabled admin (admin rows locked).
- **Care groups** (`groupAdminService`, `groupDirectoryModel` (unscoped, named columns, after the capability check), `admin.groups.*`, `/admin/groups[/:groupId]`): search by group or recipient name, a No owner filter; the group page shows members, counts, last activity. Admin actions (`groups.manage`) act as `system` through `careGroupMemberService` (a group keeps an owner): Make owner, Change role, Remove, and Invite an owner (through `careGroupInviteService.createEmail`; `inviteOwner` refuses a group with an owner, `groupAdminService:hasOwner`). Each of these queues a `staffGroupChange` email in its transaction to the owners after the change plus an owner it demoted or removed: group and member names only, no health details, no staff name, a support address (`SUPPORT_EMAIL`).
- **Settings** (`app_setting`; the typed registry `APP_SETTINGS` in `db/schema/admin/appSettings.ts`, each key with a Zod schema, default, public flag): read only through `appSettingService.getSetting`/`getSettings` (30 s per-process cache, cleared in the writing process; defaults if the read fails); `setSetting` validates, locks, upserts and audits (`{ key: [before, after] }`) in one transaction, and a repeat records nothing. A setting cleared to null is stored as JSON `null`. Keys: `signup.accessCodes`, `signup.linkInvites`, `signup.emailInvites` (refused with `settings:signupClosed`, "not available right now", on `/join/:code`, `/invite/:token` and the Members page's invite controls, via `invite.options`; **staff owner invites ignore it** (B-106): `inviteOwner` and `createWithOwnerInvite` pass `createEmail`'s internal `staffInvite` option, and `kindRefusal` lets preview, accept and `ticketFor` through for an email owner invite created by `SYSTEM_USER`), `invites.linkDefaultDays`/`linkMaxDays`/`linkMaxUses`, `mail.allowlist` (null = `MAIL_ALLOWLIST`), `publicForms.perMinute`, `announcement`. Support reads `/admin/settings` only.
- **Suppressions** (`/admin/suppressions`, `users.read`; `emailSuppressionService`, `admin.suppressions.*`): active suppressed addresses (address, reason, date), searched by part of an address (`?q=`), 50 a page. **Clear** (`users.help`) needs a reason, keeps the row (cleared at, by, reason), records `mail.suppressionCleared` (`{ address, suppressed: [reason, null] }`, naming the account with that address if there is one). The account page's mail list shows "Not sent" (`suppressed`), "Bounced" and "Marked as spam". The route takes the API as a parameter (`suppressionsData.ts`) for component test stubs.
- **Database access** (`pnpm db:access`, the `db-access` Action; [data-layer](data-layer.md)) records `db.accessGranted`, `db.accessRevoked` (system actor, staff member as target).
- **Announcement** (`public.announcement`, a public procedure): the active banner (`activeAnnouncement`: text, not past `endsAt`), with an id from sha256(tone + text): moving the end keeps a dismissal, new text shows again. `/app`'s layout has an `announcement` region (`Announcement.tsx`, `useAnnouncement`, `components/shell/AnnouncementBanner`): fetched on mount, on `online` and at most once a minute on navigation, cached per device (`caretook:announcement`), shown from the cache offline and in native, hidden at its end by a timer; dismissals in `caretook:announcement-dismissed` (newest 20; storage that throws means it shows). Rule: `pickAnnouncement` (`lib/admin/announcement.ts`).
- **Tests:** no area check (B-125). Every `/admin` page has component tests (`routes/admin/*/…browser.test.tsx`, `openAdmin` in `adminWorld.tsx`, `adminFx` in `apps/web/test/adminFixtures.ts`); the staff menu item and banner: `routes/app/layout/staff.browser.test.tsx`. Queries and rules are integration tests (`usersAdmin`, `groupsAdmin`, `settingsAdmin`, `staffAdmin`, `accountAdmin`, `auditAdmin`, `announcement`). `app-shell` step 6 keeps the end-to-end part: member@ gets the 404 on every `/admin` page; an admin's announcement writes one audit row and reaches member@'s banner. Auth tests that hit `hooks.before` use `getAuth().handler(new Request(…))`.
