# Staff and the admin panel

The admin area's rules and decisions (staff roles, `/admin`, the audit log, app settings, the announcement banner). The core rules in AGENTS.md still apply; an orchestrator folds a landing's lasting decisions for this area in here.

PRD: [`plans/admin-prd.md`](../../plans/admin-prd.md) (done; B-91). Follow-ups: B-106 (the email-invite switch also blocks staff owner invites), B-113 (recheck its checks on the new suite). **Staff never see care data**: no entries, documents, providers, medications or recipient profile fields beyond name and preferred name; counts come from `count(*)`.

- **Roles and capabilities** (`db/schema/admin/staffRules.ts`, client-safe; nothing else names `support`): `STAFF_CAPABILITIES`, `staffCan`, `isStaff`, `staffCapabilities`, and the guards `roleChangeRefusal` and `disableRefusal` (`self`, `lastAdmin`, `unknownRole`, `unchanged`; wording in `STAFF_REFUSAL_MESSAGES`). Support: `users.read`, `users.help`, `groups.read`, `accessCodes.write`, `staffGroups.create`, `waitlist.read`, `audit.read`, `settings.read`. Admin: all of those plus `users.disable`, `users.setRole`, `groups.manage`, `settings.write`. `pnpm admin:grant <email> [--role admin|support]` sets a role (an actor-less audit entry). Seed: `support@example.com` (`seeds/staff.ts`).
- **Guards:** every admin procedure is `staffProcedure(capability)` (`adminProcedure` is gone); services start with `staffRefusal(ctx, cap)` and `auditActorId(ctx)` (`services/staffAccess.ts`). `requireStaff(request, capability?)` returns `{ authUser, api, capabilities }`; pages render only the controls the viewer may use, and a missing capability is the 404. The nav is `routes/admin/adminSections.ts` (`ADMIN_SECTIONS`, each with its capability); `/admin` opens the first the viewer may see (Users). Staff get an **Admin** item in the account menu (`lib/admin/adminLink.ts`; native opens `<VITE_API_ORIGIN>/admin`).
- **Audit** (`admin_audit_log`, `adminAuditService`): every staff write calls `record(tx, …)` in its own transaction, so a refusal or a failed audit write leaves nothing; page views (`user.view`, `group.view`) use `recordSoon`. Rows can't be updated or deleted by anyone, `system` included. Actions are `AUDIT_ACTIONS` (`db/schema/admin/adminAudit.ts`; no DB check, so adding one needs no migration); changed fields go through `auditChanges(before, after, fields)`. Every new changing action requires a reason (`staffReasonZSchema`, 1–500 chars); the older access-code and staff-group actions record none. The Audit page (`/admin/audit`) filters by actor, target, action and dates in the URL, 50 a page; user and group pages show their entries with `AuditEntryList`.
- **Users** (`accountAdminService`, `admin.users.*`, `/admin/users`, `/admin/users/:userId`): search by part of a name or email; the account page shows sign-in methods, sessions (device from the user agent), groups, the last 20 outbox rows (template, status, attempts, error code from `mailErrorCode`; never data or body) and recent audit entries. Help actions (`users.help`): resend verification, send reset (tokens made as Better Auth makes them, `staffAccountMailer` in `packages/auth/src/staffEmails.ts`, queued in the transaction), sign out one session or all.
- **Disable** (`users.disable`; `user.disabled_at`, `disabled_by`, `disabled_reason`): one transaction sets it, deletes every session, voids pending sign-in codes and links, and audits. Enforced only in `packages/auth` (`disabled.ts`): a session-creation hook, a `hooks.before` on password and code sign-in (so an unverified disabled account can't learn its password was right), the JWT `definePayload`, `getAuthUser`, and the email senders (checked in the background, so the answer matches an unknown address). Every refusal answers as a wrong password, wrong code, unknown address or no session. Staff help actions refuse a disabled account (`accountAdmin:disabled`). Not yourself, never the last enabled admin (admin rows locked `FOR UPDATE`). Auth tests that hit `hooks.before` go through `getAuth().handler(new Request(…))`.
- **Care groups** (`groupAdminService`, `groupDirectoryModel` (unscoped, named columns, called only after the capability check), `admin.groups.*`, `/admin/groups`, `/admin/groups/:groupId`): search by group or recipient name, a No owner filter; the group page shows members, counts and last activity. Admin actions (`groups.manage`) act as `system` through `careGroupMemberService` (a group keeps an owner): Make owner, Change role, Remove, and Invite an owner (through `careGroupInviteService.createEmail`).
- **Settings** (`app_setting`; the typed registry `APP_SETTINGS` in `db/schema/admin/appSettings.ts`, each key with a Zod schema, default and public flag): read only through `appSettingService.getSetting`/`getSettings` (a 30 s per-process cache, cleared in the writing process; defaults if the read fails); `setSetting` validates, locks, upserts and audits (`{ key: [before, after] }`) in one transaction, and a repeat records nothing. A setting cleared to null is stored as JSON `null`. Keys: `signup.accessCodes`, `signup.linkInvites`, `signup.emailInvites` (refused with `settings:signupClosed`, "not available right now", on `/join/:code`, `/invite/:token` and the Members page's invite controls, via `invite.options`; **staff owner invites ignore it** (B-106): `inviteOwner` and `createWithOwnerInvite` pass `createEmail`'s internal `staffInvite` option, and `kindRefusal` lets preview, accept and `ticketFor` through for an email owner invite whose `createdBy` is `SYSTEM_USER`), `invites.linkDefaultDays`/`linkMaxDays`/`linkMaxUses`, `mail.allowlist` (null = `MAIL_ALLOWLIST`), `publicForms.perMinute`, and `announcement`. `/admin/settings` is read-only for support.
- **Suppressions** (`/admin/suppressions`, `users.read`; `emailSuppressionService`, `admin.suppressions.*`): active suppressed addresses (address, reason, date), searched by part of an address in the URL (`?q=`), 50 a page. **Clear** (`users.help`) needs a reason, keeps the row (cleared at, by, reason) and records `mail.suppressionCleared` (`{ address, suppressed: [reason, null] }`, naming the account with that address if there is one). The account page's mail list shows "Not sent" (`suppressed` as the error), "Bounced" and "Marked as spam". The route takes the API as a parameter (`suppressionsData.ts`), so its component tests stub it.
- **Database access** (`pnpm db:access`, the `db-access` Action; [data-layer](data-layer.md)) records `db.accessGranted` and `db.accessRevoked` with the system actor and the staff member as target.
- **Announcement** (`public.announcement`, a public procedure): the active banner (`activeAnnouncement`: text, not past `endsAt`), with an id from sha256(tone + text), so moving the end keeps a dismissal and new text shows again. `/app`'s layout has an `announcement` region (`Announcement.tsx`, `useAnnouncement`, `components/shell/AnnouncementBanner`): fetched on mount, on `online` and at most once a minute on navigation, cached per device (`caretook:announcement`) and shown from the cache offline and in native, hidden at its end by a timer; dismissals in `caretook:announcement-dismissed` (newest 20; storage that throws means it shows). Pure rule: `lib/admin/announcement.ts` `pickAnnouncement`.
- **Tests:** no area check (`admin.mjs` was moved, B-125). Every `/admin` page is component tests on the test device (`routes/admin/*/…browser.test.tsx`, with `openAdmin` in `adminWorld.tsx` and the `adminFx` builders in `apps/web/test/adminFixtures.ts`); the staff menu item and the banner are `routes/app/layout/staff.browser.test.tsx`. The queries and rules are integration tests (`usersAdmin`, `groupsAdmin`, `settingsAdmin`, `staffAdmin`, `accountAdmin`, `auditAdmin`, `announcement`). `app-shell` step 6 keeps the end-to-end part: member@ gets the 404 on every `/admin` page, and an admin's announcement post writes one audit row and reaches member@'s banner.
