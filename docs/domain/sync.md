# Sync: PowerSync

The sync area's rules and decisions. An orchestrator folds a landing's lasting decisions for this area in here.

- Postgres is the source of truth. Each device keeps a SQLite copy, and writes upload through **our** API (`sync.upload`), so permissions, validation and audits all apply. Conflicts: last write wins per row; live notes merge through Yjs.
- **Hosting:** PowerSync Cloud in production; locally the `journeyapps/powersync-service:1.28.3` container on :8080, with bucket storage in its own Postgres (`.postgres/powersync-storage`).
- **Sync Streams** (`powersync/sync-config.yaml`, edition 3). **Queries list their columns explicitly**, so a new column must be added there too. The service reads the file at startup: `docker compose restart powersync` after editing.
  - `care_groups`: one bucket per group the user belongs to, carrying the care tables (soft-deleted rows included for `timeline_entry`, `provider`, `medication_pass`, `recipient_allergy`, `task` and similar; read the file for the list). `care_recipient` carries `no_known_allergies_at`, `note_document` carries `task_id`.
  - `member_profiles`: co-members' `id`, `name`, `image`.
  - `care_group_writers`: `care_recipient_details` for groups where the user's role is not `viewer`. PowerSync 1.28.3 rejects `role IN (...)`, so **a future read-only role must be excluded there too**. A demoted member loses the row on the next sync.
- **Publication** (`powersync`): the care tables plus `"user" (id, name, image)`. The column list keeps emails, roles and preferences out of replication.
- **Local JWKS:** the service fetches `PS_JWKS_URL` (default `http://host.docker.internal:5173/api/auth/jwks`). Vite binds `127.0.0.1` (Docker Desktop forwards only to the host's IPv4 loopback) and allows that Host header. `pnpm datastore:reset` ends with `pnpm datastore:powersync` (`packages/data/scripts/powersync.ts`): it stops this checkout's PowerSync (only its own compose project), drops its replication slot, empties its bucket storage (a dropped schema never reaches PowerSync as deletes), restarts it and waits up to 60 s for replication and the JWKS. It skips when PowerSync isn't running or belongs to another checkout. Devices synced before a reset re-sync once. Its admin token and port are copied from `powersync/service.yaml`: change both together.
- **Upload** (`packages/api/src/sync.ts`): up to 100 CRUD ops, in order, mapped onto **services**.
  - Rows with a soft delete (`timeline_entry`, `provider`, `medication`, `medication_pass`, `recipient_allergy`, `care_period`, `task`): PUT → `upsert` (idempotent on id), PATCH → `update` (or `remove` when it sets `deleted_at`), DELETE → `remove`. A changed group (or recipient) → `immutable`; an id in a group the actor can't see → `unauthorized`. Booleans arrive as 1/0 and `phones` as JSON text. A pass's retime and delete repeat their side effects idempotently.
  - `task` (`taskOp`): a PATCH of only `done_at`/`done_by` maps to `complete` or `reopen`, so a viewer's tick passes `taskService`'s completion rule ([tasks](tasks.md)).
  - `note_document`/`note_update`: PUT → `create`/`appendUpdate`; anything else → `sync:readOnlyTable`. A document PUT passes the device's `subject` (none means `entry`; also `provider`, `medication`, `task`).
  - `timeline_entry_provider`: PUT → link, DELETE → unlink, PATCH → `sync:readOnlyTable`.
  - `care_recipient`: read-only, except a PATCH of `no_known_allergies_at` alone (`recipientAllergyService.setNoKnownAllergies`). Other tables → `sync:readOnlyTable`.
  - 4xx outcomes are acknowledged as rejected, and the next sync restores the server's copy. Other errors throw, so the batch retries.
- **Timestamps:** PowerSync syncs timestamptz as `2026-11-17T21:45:25.229000Z`. Local writes use exactly that form (`toLocalTimestamp`) so strings sort; `fromLocalTimestamp` parses either.
- **Device:** the plumbing is `apps/web/app/lib/sync/`; each area's device queries and local writes are `lib/<area>/<name>.sync.ts` (guard: `libLayout.test.ts`; e.g. `lib/timeline/timeline.sync.ts`). Local writes validate with the shared Zod schemas, check the role locally, and update content columns only.
  - `schema.ts`: the Drizzle sqlite tables.
  - `client.ts`: the database and connector, **loaded lazily** (never imported statically).
    - One user's data per device: the owner is in localStorage, and the file is wiped when someone else opens it.
    - Sign-out runs `disconnectAndClear`, then `VACUUM` (so freed pages don't keep care data on disk), and **keeps the IndexedDB file**: a `deleteDatabase` blocked by PowerSync's shared worker stays queued and blocks the next sign-in for good. OPFS files are still removed.
    - `fetchCredentials` calls `/api/auth/token`. A 401 leaves the device local-only.
  - `pageCache.ts` (`releaseSyncLocksWhenCached`, called in `client.ts` before PowerSync opens): a full load can freeze the old page in the back/forward cache, and PowerSync 2.7's shared workers then wait on its database (the `tab-close-signal-*` and `shared-connection-*` Web Locks), so the next page's database never opens: a blank page with no error. It wraps `navigator.locks.request` for those locks, releases them on `pagehide` into the cache, and reloads on `pageshow` out of it (Back to a cached page reloads, which fails offline on the web). It depends on PowerSync's internal lock names: recheck on a PowerSync upgrade.
  - `index.ts`: `openSync`, `getSync`, `closeSync`, `waitForFirstSync`, `isFirstSyncDone`, `useFirstSyncDone`, `useLiveQuery`, `useSyncState`. `useLiveQuery` watches nothing when no database is open, so a component mounting during sign-out never throws.
  - **The first sync:** `waitForFirstSync(db)` waits at most 1 s (`FIRST_SYNC_WAIT_MS`) and resolves to `isFirstSyncDone(db)` (PowerSync's `hasSynced`, which persists with the local copy). `useFirstSyncDone()` is the hook (below the /app layout only).
    - A loader whose group isn't on the device throws `notOnDevice(db)` (`lib/sync/firstSync.ts`): a 404 once the first sync is done, otherwise a 503 "First sync pending" that `/app`'s `ErrorBoundary` shows as `FirstSyncPending`, which reruns the loaders when the sync lands. `home` shows the same state while `synced` is false.
  - **Session:** `lib/auth/session.ts` `requireSession(request)` is the one shared session check and DB open. Every confirmed online check records `caretook:session-confirmed:<userId>`. The server's answer is sorted by the pure `sessionOutcome` (`lib/auth/sessionRules.ts`):
    - A session is ok. No session, 401 or 403 is **signed out**: `wipeDevice()` (the one sign-out path, also used by `/sign-out`: close the sync database (cleared and vacuumed), then forget the cached user, settings, pending settings, last group and recent searches) and go to sign-in.
    - A 429 is **rate limited**: `askSession` retries once after `X-Retry-After` (capped at 2 s); still 429 with nobody cached → `/sign-in?reason=rate-limited`, never a silent sign-out.
    - Anything else (offline, 5xx), and a 429 with a cached user, is unknown: the cached user carries on only within 3 days of the last confirmed check (`offlineAllowed`), else `/sign-in?reason=offline` **without** wiping, so unsynced writes still upload after signing back in.
    - **The device answers first:** a session confirmed within 15 min (`sessionFreshness`) returns at once, rechecked in the background after a minute; the first check per page load or sign-in (`sessionEpoch.ts`) waits. Waits cap at 3 s (`NETWORK_ANSWER_MS`). It bypasses Better Auth's cookie cache.
    - The /app layout's `clientMiddleware` calls it once per navigation and sets `sessionContext`; every /app loader and action reads `context.get(sessionContext)`, never `requireSession` again.
  - **Tile cache** (`lib/sync/remembered.ts`, `useRememberedQuery`): in memory, keyed by user, group and name; returns `{ value, fresh }`; cleared by `closeSync`.
  - **Settings cache:** `lib/app-shell/me.ts` caches settings per user (they aren't synced). **Change them with `saveSettings(userId, change)`**: it caches at once, records the change as pending (`caretook:settings-pending:<userId>`), and calls `updatePreferences`, resolving `"saved"` or, on a network failure, `"pending"`. Other errors reject (a refused change is dropped). `loadSettings` is cache-first (`settingsPlan`): it returns the cache plus pending at once and refreshes in the background, publishing to `useMySettings`; with no cache it waits ≤ 3 s, then defaults. `forgetSettings` (sign-out) clears pending changes. `cachedSettings(userId)` reads cache plus pending without the network.
- ✅ **Production** (settings in `powersync/service.production.example.yaml`, setup in [`ops/runbook.md`](../../ops/runbook.md)): PowerSync Cloud (US) on Neon's direct URL with `sslmode: verify-full`, as `caretook_replication` (REPLICATION). Client auth is the JWKS at `<APP_URL>/api/auth/jwks` with the audience `POWERSYNC_URL`; no admin token in the service config. The deploy Action pushes `sync-config.yaml`.
  - **Grants come from `sync-config.yaml`** (`packages/data/src/db/roles/syncConfig.ts`): the replication role gets SELECT on exactly the columns the streams read (select lists plus `with`, join and filter columns), and the `powersync` publication gets the same lists. The parser refuses `*`, unknown columns and functions.
  - **The snapshot runs `SELECT *`**, so a synced table lists every column in its stream, or is in `REPLICATION_WHOLE_TABLES` (`user`, `note_document`, `timeline_entry`) with a table-level grant. The publication keeps the column lists, so those tables' other columns reach PowerSync's server-side storage in the snapshot, never devices. `roles.int.test.ts` runs the snapshot query on every synced table, and `rolesSql.test.ts` fails on a partly synced table not on the list.
- ✅ **Offline web reload:** a service worker ([app-shell](app-shell.md)) serves `/app/*` from a cached shell; the device database does the rest.
- 🟡 Not built:
  - Deleting a whole group dropping its buckets is untested end to end (losing a membership is covered).
