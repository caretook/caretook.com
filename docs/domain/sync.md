# Sync: PowerSync

The sync area's rules and decisions.

- Postgres is the source of truth. Each device keeps a SQLite copy, and writes upload through **our** API (`sync.upload`), so permissions, validation and audits apply. Conflicts: last write wins per row; live notes merge through Yjs.
- **Hosting:** PowerSync Cloud; locally the `journeyapps/powersync-service:1.28.3` container on :8080, with bucket storage in its own Postgres.
- **Sync Streams** (`powersync/sync-config.yaml`, edition 3). **Queries list their columns explicitly**, so a new column must be added there too. Restart after editing: `docker compose restart powersync`.
  - `care_groups`: one bucket per group the user belongs to, carrying the care tables (soft-deleted rows included for most tables), and the link tables `medication_condition` and `condition_manager` (hard deletes). `care_recipient` carries `no_known_allergies_at` and `no_known_conditions_at`, `note_document` `todo_id`, `care_group` `details_outside_allowed` ([calendars](calendars.md)).
  - `member_profiles`: co-members' `PUBLIC_PROFILE_FIELDS`.
  - `care_group_writers`: `care_recipient_details` for groups where the user's role is a writer. PowerSync 1.28.3 rejects `role IN (...)`, so the stream lists the roles it excludes (`viewer`, `easy_helper`, `easy_viewer`): **every new non-writer role must be excluded there too**.
- **Publication** (`powersync`): the care tables plus `user`'s public columns (no email, role, preferences). To change them, drop and re-add `user`; never `SET TABLE`.
- **Local JWKS:** the service fetches `PS_JWKS_URL` (default `http://host.docker.internal:5173/api/auth/jwks`). Vite binds `127.0.0.1` and allows that Host header. `pnpm datastore:reset` ends with `pnpm datastore:powersync` (`packages/data/scripts/powersync.ts`): it stops this checkout's PowerSync, drops its replication slot, empties its bucket storage, restarts it and waits up to 60 s for replication and the JWKS. Its admin token and port are copied from `powersync/service.yaml`: change both together.
- **Upload** (`sync.upload`, `packages/api/src/sync.ts`): up to 100 ops, in order, onto **services** through `UPLOAD_REGISTRY` (a `Map`, `syncRegistry.ts`); any other table, `__proto__` included, → `sync:readOnlyTable`.
  - One `softDelete(spec)` handler for `timeline_entry`, `provider`, `medication`, `medication_pass`, `recipient_allergy`, `recipient_condition`, `care_period`, `todo`, `appointment_series`: PUT → `upsert`, PATCH → `update` (`remove` when it sets `deleted_at`), DELETE → `remove`. A changed group or recipient → `immutable`; a reader who can't write → `permissions:unauthorized` on every op (one more read tells them from a missing row, `:notFound`). Booleans arrive as 1/0, JSON as text. A dose's PUT and PATCH have their own upload rules ([medications](medications.md)).
  - Each entry exports its column lists (`content`, `fixed`, `handled`, `serverSet`); a PATCH naming a column in none → `sync:unknownColumn`. `syncRegistry.test.ts` checks they agree with the device schema and the streams (local-only tables skipped). `via`, `connectors_enabled` sync down only.
  - `todo` hooks: a PATCH of only `done_at`/`done_by` is `complete`/`reopen` (a viewer's tick passes, [todos](todos.md)); the twin is `put`. Live notes: PUT → `create`/`appendUpdate` (the device's `subject`), else read-only. Link tables: PUT → link, DELETE → unlink. `condition_manager`: a PATCH of only `updated_at` is the unlink at that save's time (`changedAt`). `care_recipient`: only the no-known PATCHes.
  - A 4xx is acknowledged as rejected (the next sync restores the server's copy); other errors throw and the batch retries.
- **Timestamps:** PowerSync syncs timestamptz as `2026-11-17T21:45:25.229000Z`. Local writes use that form (`toLocalTimestamp`) so strings sort; `fromLocalTimestamp` parses either.
- **Device:** the plumbing is `apps/web/app/lib/sync/`; device queries and local writes are `lib/<area>/<name>.sync.ts` (guard: `libLayout.test.ts`). Local writes validate with the shared Zod schemas, check the role set (`canWrite`, `canLog`: a refused upload is never queued), and write only changed columns (`lib/core/changedColumns.ts`, JSON by value; device fixtures seed JSON as Postgres sends it, `pgJson`).
  - `schema.ts`: the Drizzle sqlite tables; `LOCAL_ONLY_TABLES` (`localOnly`, never synced, cleared with the copy): `unsaved_change`.
  - `uploader.ts` (`uploadQueued(db, upload)`): records each rejected op in `unsaved_change` (data, code, issues, a label) before completing the batch; Settings → "Changes not saved" lists them.
  - `client.ts`: the database and connector, **loaded lazily** (never imported statically).
    - One user's data per device: the owner is in localStorage; the file is wiped when someone else opens it.
    - Sign-out runs `disconnectAndClear`, then `VACUUM` (no care data on freed pages), and **keeps the IndexedDB file**: a `deleteDatabase` blocked by PowerSync's shared worker stays queued and blocks the next sign-in for good. OPFS files are removed.
    - `fetchCredentials` calls `/api/auth/token` (always the live session: auth.md). A 401 leaves the device local-only.
  - `pageCache.ts` (`releaseSyncLocksWhenCached`, called in `client.ts` before PowerSync opens): a page frozen in the back/forward cache holds PowerSync 2.7's `tab-close-signal-*` and `shared-connection-*` Web Locks, so the next page's database never opens (a blank page). It wraps `navigator.locks.request` for those locks, releases them on `pagehide` into the cache, and reloads on `pageshow` out of it. It depends on PowerSync's internal lock names: recheck on a PowerSync upgrade.
  - `index.ts`: `openSync`, `getSync`, `closeSync`, `waitForFirstSync`, `isFirstSyncDone`, `useFirstSyncDone`, `useLiveQuery`, `useSyncState` (also `waiting`, `notSaved`, `uploadFailed`). `useLiveQuery` watches nothing with no database open; new loader data for an already answered query keeps the live rows.
  - **The first sync:** `waitForFirstSync(db)` waits at most 1 s (`FIRST_SYNC_WAIT_MS`) and resolves to `isFirstSyncDone(db)` (PowerSync's `hasSynced`, which persists with the local copy). `useFirstSyncDone()` is the hook (below the /app layout only).
    - A loader whose group isn't on the device throws `notOnDevice(db)` (`lib/sync/firstSync.ts`): a 404 once the first sync is done, otherwise a 503 "First sync pending" that `/app`'s `ErrorBoundary` shows as `FirstSyncPending`, which reruns the loaders when the sync lands. `home` shows it while `synced` is false.
  - **Session:** `lib/auth/session.ts` `requireSession(request)` is the one shared session check and DB open. Every confirmed online check records `caretook:session-confirmed:<userId>`. The server's answer is sorted by the pure `sessionOutcome` (`lib/auth/sessionRules.ts`):
    - A session is ok. No session, 401 or 403 is **signed out**: `wipeDevice()` (the one sign-out path, also `/sign-out`: close the sync database (cleared, vacuumed), then forget the cached user, settings, pending settings, last group and recent searches) and go to sign-in.
    - A 429 is **rate limited**: `askSession` retries once after `X-Retry-After` (capped at 2 s); still 429 with nobody cached → `/sign-in?reason=rate-limited`, never a silent sign-out.
    - Anything else (offline, 5xx), and a 429 with a cached user, is unknown: the cached user carries on only within 3 days of the last confirmed check (`offlineAllowed`), else `/sign-in?reason=offline` **without** wiping, so unsynced writes still upload after sign-in.
    - **The device answers first:** a session confirmed within 15 min (`sessionFreshness`) returns at once, rechecked in the background after a minute; the first check per page load or sign-in (`sessionEpoch.ts`) waits. Waits cap at 3 s (`NETWORK_ANSWER_MS`).
    - The /app layout's `clientMiddleware` calls it once per navigation and sets `sessionContext`; every /app loader and action reads `context.get(sessionContext)`, never `requireSession` again.
  - **Tile cache** (`lib/sync/remembered.ts`, `useRememberedQuery`): in memory, keyed by user, group and name; returns `{ value, fresh }`; cleared by `closeSync`.
  - **Settings cache:** `lib/app-shell/me.ts` caches settings per user (they aren't synced). **Change them with `saveSettings(userId, change)`**: it caches at once, records the change as pending (`caretook:settings-pending:<userId>`), and calls `updatePreferences`, resolving `"saved"` or, on a network failure, `"pending"`. Other errors reject (a refused change is dropped). `loadSettings` is cache-first (`settingsPlan`): it returns the cache plus pending at once and refreshes in the background, publishing to `useMySettings`; with no cache it waits ≤ 3 s, then defaults. `forgetSettings` (sign-out) clears pending changes. `cachedSettings(userId)` reads cache plus pending without the network.
- ✅ **Production** (settings in `powersync/service.production.example.yaml`, setup in [`ops/runbook.md`](../../ops/runbook.md)): PowerSync Cloud (US) on Neon's direct URL with `sslmode: verify-full`, as `caretook_replication` (REPLICATION). Client auth is the JWKS at `<APP_URL>/api/auth/jwks` with the audience `POWERSYNC_URL`; no admin token in the service config. The deploy Action pushes `sync-config.yaml`.
  - **Grants come from `sync-config.yaml`** (`packages/data/src/db/roles/syncConfig.ts`): the replication role's SELECT and the `powersync` publication list exactly the columns the streams read. The parser refuses `*`, unknown columns and functions.
  - **The snapshot runs `SELECT *`**, so a synced table lists every column in its stream, or is in `REPLICATION_WHOLE_TABLES` (`user`, `note_document`, `timeline_entry`, `care_group`, `care_group_member`) with a table-level grant. The publication keeps the column lists, so their other columns reach PowerSync's storage in the snapshot, never devices. `roles.int.test.ts` runs the snapshot on every synced table; `rolesSql.test.ts` fails on a partly synced table not on the list.
- ✅ **Offline web reload:** a service worker ([app-shell](app-shell.md)) serves `/app/*`.
- 🟡 Not built:
  - Deleting a whole group dropping its buckets is untested end to end.
