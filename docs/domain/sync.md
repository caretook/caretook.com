# Sync: PowerSync

The sync area's rules and decisions. An orchestrator folds a landing's lasting decisions for this area in here.

- Postgres is the source of truth. Each device keeps a SQLite copy, and writes upload through **our** API (`sync.upload`), so permissions, validation and audits all apply.
  - Ruled out: Zero (offline writes), ElectricSQL (read-only sync), Convex (offline, lock-in), and InstantDB, Triplit and Jazz (control).
- **Hosting:** PowerSync Cloud in production; locally the `journeyapps/powersync-service:1.28.3` container on :8080, with bucket storage in its own Postgres (`.postgres/powersync-storage`).
- **Sync Streams** (`powersync/sync-config.yaml`, edition 3; Sync Rules are deprecated). **Queries list their columns explicitly**, so a new column must be added there too.
  - `care_groups`: one bucket per group the user belongs to. It carries `care_group`, `care_group_member`, `care_recipient` (names, `time_zone` and `date_of_birth`), `timeline_entry` (including soft-deleted rows), `note_document`, `note_update`, `provider` (including soft-deleted rows), `timeline_entry_provider`, `medication`, `care_period`, `medication_pass`, `recipient_allergy` and `task` (all five including soft-deleted rows); `care_recipient` also carries `no_known_allergies_at`, and `note_document` `task_id`.
  - `member_profiles`: co-members' `id`, `name` and `image`.
  - `care_group_writers`: `care_recipient_details` for groups where the user's role is not `viewer` (PowerSync 1.28.3 rejects `role IN (...)`, so **a future read-only role must be excluded there too**). A demoted member loses the row on the next sync.
  - The service reads the file at startup: run `docker compose restart powersync` after editing it.
- **Publication** (`powersync`): the care tables plus `"user" (id, name, image)`. The column list keeps emails, roles and preferences out of replication.
- **Local JWKS:** the service fetches `PS_JWKS_URL` (default `http://host.docker.internal:5173/api/auth/jwks`). Docker Desktop forwards only to the host's IPv4 loopback, so Vite binds `127.0.0.1` and allows that Host header. `pnpm datastore:reset` ends with `pnpm datastore:powersync` (`packages/data/scripts/powersync.ts`): it stops this checkout's PowerSync (through `docker compose` from the repo root, so only its own project), drops its replication slot, empties its bucket storage (dropping the schema never reaches PowerSync as deletes, so old rows such as `note_update`s with old user ids would stay), starts it, and waits up to 60 s for the first replication and the JWKS. It skips with a note when PowerSync isn't running or belongs to another checkout, and only warns on a timeout (the dev server may be down; PowerSync then fetches keys on its first request). Devices synced before a reset re-sync from scratch once. Its admin token and container port are copied from `powersync/service.yaml`: change both together.
- **Upload** (`packages/api/src/sync.ts`): up to 100 CRUD ops, in order, mapped onto **services**.
  - `timeline_entry`:
    - PUT → `upsert` (idempotent on id). A changed group, kind or recipient → `immutable`, and an id in a group the actor can't see → `unauthorized`.
    - PATCH → `update`, or `remove` when it sets `deleted_at`.
    - DELETE → `remove`.
  - `note_document`/`note_update`: PUT → `create`/`appendUpdate`. Anything else → `sync:readOnlyTable`. A document PUT passes the device's `subject` (none means `entry`). Subjects: `entry`, `provider`, `medication`, `task`.
  - `provider`: like `timeline_entry` (PUT upsert, PATCH update or soft remove, DELETE soft remove; a changed group → `immutable`). `is_primary` arrives as 1/0 and `phones` as JSON text.
  - `timeline_entry_provider`: PUT → link, DELETE → unlink, PATCH → `sync:readOnlyTable`.
  - `medication_pass` and `recipient_allergy`: like `medication` (PUT upsert, PATCH update or soft remove, DELETE soft remove; a changed group or recipient → `immutable`). A pass's retime and delete repeat their side effects idempotently (see _Medications_).
  - `care_recipient`: read-only, except a PATCH of `no_known_allergies_at` alone (`recipientAllergyService.setNoKnownAllergies`).
  - `care_period`: like `provider` (PUT upsert, PATCH update or soft remove, DELETE soft remove; a changed group or recipient → `immutable`). `date_only` arrives as 1/0.
  - `task` (`taskOp`): PUT upsert, PATCH update or soft remove, DELETE soft remove; a changed group or recipient → `immutable`. A PATCH of only `done_at`/`done_by` maps to `complete` or `reopen`, so a viewer's tick passes `taskService`'s completion rule (see [tasks](tasks.md)).
  - Other tables → `sync:readOnlyTable`.
  - 4xx outcomes are acknowledged as rejected, and the next sync restores the server's copy. Other errors throw, so the batch retries.
  - After each batch, touched documents are compacted when due (best effort).
- **Timestamps:** PowerSync syncs timestamptz as `2026-11-17T21:45:25.229000Z`. Local writes use exactly that form (`toLocalTimestamp`), so strings sort correctly; `fromLocalTimestamp` parses either form.
- **Device:** the plumbing is `apps/web/app/lib/sync/`; each area's device queries are `lib/<area>/<name>.sync.ts` (the layout guard `libLayout.test.ts`):
  - `schema.ts`: Drizzle sqlite tables → `DrizzleAppSchema`.
  - `client.ts`: the database and connector, **loaded lazily** (never imported statically).
    - One user's data per device: the owner is in localStorage, and the file is wiped when someone else opens it.
    - Sign-out runs `disconnectAndClear`, then `VACUUM` (so freed pages don't keep care data on disk), and **keeps the IndexedDB file**: a `deleteDatabase` blocked by PowerSync's shared worker stays queued and blocks the next sign-in's open for good. OPFS files are still removed. Checks assert the wipe with `cdp.mjs`'s `localCopyHolds(text)`.
    - `fetchCredentials` calls `/api/auth/token`. A 401 leaves the device local-only.
  - `pageCache.ts` (`releaseSyncLocksWhenCached`, called once in `client.ts` before PowerSync opens): a page frozen in the back/forward cache keeps PowerSync 2.7's shared-worker Web Locks (`tab-close-signal-*`, `shared-connection-*`), so the next page's database never opens (a blank page, no error). It releases those locks on a `pagehide` into the cache and reloads on a `pageshow` out of it (offline on the web, that reload fails until a service worker exists). It depends on PowerSync's internal lock names: recheck on an upgrade.
  - `index.ts`: `openSync`, `getSync`, `closeSync`, the first-sync helpers, `useLiveQuery` and `useSyncState`. `useLiveQuery`'s `watchLiveQuery` watches nothing with no database open, so a component mounting during sign-out never throws. Dev builds expose `window.caretookSync`.
  - **The first sync**: `waitForFirstSync(db)` waits at most 1 s (`FIRST_SYNC_WAIT_MS`) and resolves to `isFirstSyncDone(db)`. That's PowerSync's `hasSynced`, which persists with the local copy, so it's true at once on a synced device and offline. `useFirstSyncDone()` is the hook (below the /app layout only). Use it for anything that needs the local groups, such as a last-group redirect.
    - A loader whose group isn't on the device throws `notOnDevice(db)` (`lib/sync/firstSync.ts`): a 404 once the first sync is done, otherwise a 503 "First sync pending" that `/app`'s `ErrorBoundary` shows as `FirstSyncPending` ("Getting your care groups…"), which reruns the loaders when the sync lands. `home` shows the same state while `synced` is false, and never says "not in a care group" before then.
  - `timeline.ts`: local queries, row → API-shape mapping (unknown kinds are skipped), and local writes. Writes validate with the shared Zod schemas, check the role locally, and update content columns only.
  - `lib/auth/session.ts` `requireSession(request)`: one shared session check and DB open; the /app layout's `clientMiddleware` calls it once per navigation and sets `sessionContext`, which every /app loader and action reads. **The device answers first** (`lib/auth/sessionRules.ts`, pure): `sessionFreshness` is fresh within 15 min of the last confirmed check (`caretook:session-confirmed:<userId>`; a clock moved back counts as no time), and a fresh session returns at once, rechecking in the background once over a minute old (`shouldRecheck`, shared with any check in flight). The first check of each page load, and after a sign-in (`sessionChanged()`, `sessionEpoch.ts`), always waits. Every wait is capped at 3 s (`NETWORK_ANSWER_MS`, `withTimeout`), the 429 retry included. The request sets `disableCookieCache`. `sessionOutcome` sorts the answer: ok; **signed out** (none, 401, 403) runs `wipeDevice()` (the one sign-out path, also `/sign-out`: close and clear the sync database, forget the cached user, settings, pending settings, last group, recent searches and the tile cache) then a full navigation to sign-in; unverified → verify-email; **rate limited** (one retry after `X-Retry-After`, ≤ 2 s; nobody cached → `/sign-in?reason=rate-limited`, never a silent sign-out); anything else is unknown, and the cached user carries on within 3 days of the last confirmed check (`offlineAllowed`), else `/sign-in?reason=offline` **without** wiping. In the background, rate limited and unknown do nothing. `session-end.mjs` checks these.
  - `lib/app-shell/me.ts` caches settings per user (not synced). **Change them with `saveSettings(userId, change)`**: cached at once, recorded as pending (`caretook:settings-pending:<userId>`), then `updatePreferences` resolves `"saved"` or, offline, `"pending"`; other errors reject and drop it. **`loadSettings` is cache-first** (`settingsPlan`, pure): with a cache it returns it with pending changes on top at once, and one background refresh per user sends the pending change, reads `me.get` and publishes; with none it waits ≤ 3 s, then defaults. Screens read through the store, `useMySettings(userId, initial)` (`subscribeSettings`), seeded from the loader, so a refresh re-renders them. `forgetSettings` clears the store and pending changes.
  - **The tile cache** (`lib/sync/remembered.ts`, `useRememberedQuery(key, query)`): header tiles' live queries remember every answer in memory (never `localStorage`), keyed by user, group and a stable name, and return `{ value, fresh }`: the remembered value (`fresh: false`) until the first live answer. `closeSync` clears it. Writes that act on what a tile shows (Given all, quick entry's passes) wait for `fresh`.
- ✅ **Production** (Cloud settings in `powersync/service.production.example.yaml`, setup in [`ops/runbook.md`](../../ops/runbook.md)): PowerSync Cloud (US) on Neon's direct URL with `sslmode: verify-full`, as `caretook_replication` (REPLICATION). Client auth is the JWKS at `<APP_URL>/api/auth/jwks` with the audience `POWERSYNC_URL`; no admin token in the service config. The deploy Action pushes `sync-config.yaml` (`powersync deploy sync-config`).
  - **Grants come from `sync-config.yaml`** (`db/roles/syncConfig.ts`): the replication role gets SELECT on exactly the columns the streams read (select lists plus `with`, join and filter columns), and the `powersync` publication gets the same column lists. The parser refuses `*`, unknown tables or columns, and functions in a select list.
  - **The snapshot runs `SELECT *`**, so a synced table lists every column in its stream, or is in `REPLICATION_WHOLE_TABLES` (`user`, `note_document`, `timeline_entry`) with a table-level grant. The publication keeps the column lists, so those tables' other columns (user's email, role and preferences; the hand-written `search_vector`) reach PowerSync's server-side storage in the snapshot, never devices. `roles.int.test.ts` runs the snapshot query on every synced table, and `rolesSql.test.ts` fails on a partly synced table not on the list. The six groups tables stream their timestamps and audits too (the device schema ignores them). ❓ Whether PowerSync Cloud snapshots the same way.
- ✅ Settings pages load and save offline (pending, "Saved on this device…"); `cachedSettings(userId)` reads cache plus pending without the network.
- 🟡 Not built:
  - **Offline web reload** needs a service worker. Offline already works within a loaded session, and will in Capacitor.
  - Deleting a whole group dropping its buckets is untested end to end. (Losing a membership is covered: `app-shell.mjs` sees a removed member's timeline rows go without a reload.)
