# Tags

One shared tag list per care group; tags go on timeline entries (events included), todos, providers and medications. PRD: [`tags-prd`](../../plans/tags-prd.md). ✅ data and sync (wave 1); ✅ tagging timeline entries and events (wave 2); ✅ rename and delete, todos and the Planner, providers and medications (wave 3); ✅ the timeline and search filters (wave 4). [`tags-2`](../../plans/tags-2-prd.md): ✅ colors in data and sync, colored chips and seeds, `QuickTags` everywhere a record is tagged. [`tags-3`](../../plans/tags-3-plan.md): ✅ one tag control on list rows too, the Tags page with merge, search by tag.

## Data

- **Schema area `tags`** (`packages/data/src/db/schema/tags/`): `tag` (`name`, `name_key`, unique per group on each of `name_key` and `id`; hard delete, cascades with the group) and `record_tag` (`tag_id` plus one nullable column per target: `entry_id`, `todo_id`, `provider_id`, `medication_id`). Every foreign key is composite on `group_id`, so a link never crosses groups; a `num_nonnulls(…) = 1` check allows exactly one target. Hard-deleting a target or the tag removes its links; **a soft-deleted record keeps its links**, hidden from every list.
- **Colors:** `tag.color`, nullable, checked against `TAG_COLORS` (the avatar color ids, one palette); migration 0048 backfilled existing tags per group in creation order. `pickTagColor(used, random)` takes a color no group tag has, any once all ten are used. A null or unknown color renders neutral.
- **The rules module** `tagRules.ts` (client-safe) is the only place that folds a name or decides who tags: `tagKey` (case and spaces folded), the name schema (1–40 characters), `tagId(groupId, key, counter)` and `recordTagId(tagId, recordId)` (version 5 UUIDs), `nextTagId` (the first counter free locally, below `TAG_COUNTER_LIMIT` 1000), `targetOf`, `canCreateTag`, `canTagRecord`, and the `?tag=` helpers. **Ids are derived, never `randomUUID`:** two offline devices adding "Urgent" land on one tag and one link.
- **Who:** read any member. Create a tag: loggers. Tag and untag: writers on any target; an Easy helper only on a timeline entry they created, whoever made the tag. **Tagging never borrows a record's update permission** (viewers and Easy roles hold `update` on todos only to tick). Rename (`canRenameTag`): owners, admins, caretakers, and Easy helpers on tags they created (`groupOwn` on `created_by`); delete (`canDeleteTag`): owners only. `record_tag` update is `system`.
- **Services:** `tagService.create` is idempotent on id and returns the tag even after a rename; a name held by another id is `tagService:nameTaken` (with its dependent link, it shows in "Changes not saved"). It takes a group advisory lock, and picks the color inside it when none is given. `recolor` takes a palette id only (no clearing) under rename's update scope. `recordTagService.link`/`unlink` check both ends are live and in the group (cross-group is `recordTagService:immutable`) and read the target's `created_by` in SQL. `link` returns an existing link before the rule: its id is derived, so a match is the same row and nothing is written; a viewer's twin upload replays, while a new link or an unlink is still refused. `rename` writes `name_key` as the system (it stays system-only), then `name` as the actor, so the SQL scope decides and a refusal rolls back; `remove` hard-deletes and cascades the links. `recordTagService.copyLinks` (system) copies a ticked repeating todo's tags to the next occurrence.

## Sync

- Both tables are in the `care_groups` stream for every role and the device schema (`tags`, `recordTags`). Upload: `tag` PUT → `create`, PUT `color` → `create`'s (none: the server picks), PATCH `name` → `rename`, PATCH `color` → `recolor` (both: one transaction) (a sent `name_key` is ignored), DELETE → `remove` (`notFound` is a replay); `record_tag` has its own small handler: PUT → link with null targets as null, DELETE → unlink, PATCH `sync:readOnlyTable`.
- Device module `lib/tags/tags.sync.ts` (`caretookModules.tags`): `tagsQuery`, `recordTagsQuery`, `groupRecordTagsQuery` (live records only); `createTag` reuses a local tag with the same key, else takes `nextTagId` and writes a `pickTagColor` color, so device and server agree; `recolorTag` (`canRenameTag`); `tagRecord`/`untagRecord` check `canTagRecord` first; `renameTag`, `deleteTag` (links and tag in one transaction), `tagUsesQuery`, `groupTagUsesQuery` (live-record counts per tag, one query for the Tags page) and `mergeTags(from, into)` (owners, `canDeleteTag`, one group: in one transaction each live record carrying `from` gets `into` under its derived link id, then `from` and its links go; uploads are the plain `record_tag` PUTs and `tag` DELETE). A todo's twin copies its tags with the same link ids (a tick isn't tagging).
- `roundtrip` covers two offline devices adding the same tag to one entry; the sync matrix has device rows for both tables.

## Screens

- **Picker** (`components/tags/`): `useTagPicker` (an `ask`/`sheet` pair, like `useRemindMe`) opens `TagPickerSheet`: a filter box, one toggle per tag (tags or untags at once), and for loggers `Add "<name>"`; Enter adds the typed name or applies the tag it names exactly. Matching and exact-name reuse live in `lib/tags/tagPicker.ts` (folded through `tagKey` only). Live data: `useGroupTags`, `useRecordTags`, `useGroupRecordTags` (one query per list, mapped by record).
- **`QuickTags`** (`components/tags/QuickTags.tsx`, tags-2), the one tag control: chips with an × each (one tap untags, then a "Removed <name>" toast whose Undo re-tags with the same link id) and an icon-only `TagPlus` "Add tag" opening the picker, for whoever `canTagRecord` allows; anyone else sees chips only. Props: the record (`target`, `recordId`, `label`), `createdBy`, `max` (null: all; rows 2, "+N" opens the picker), optional `tags` (a list's one query; left out, it reads `useRecordTags`). It sits `relative z-10` over a row's stretched link, only as wide as its chips (`w-fit`, fixes-bug B-970) so a tap beside them opens the record; each tap is its own write, never part of Save. On the entry, todo, provider and medication pages, their edit sheets and the timeline's (symptom, vital, dose), and on rows: timeline rows and cards, Todos and Planner rows, providers and medications (`max` 2, the list's one tags query; a todo's `context` row is `readOnly`, so is the easy roles' Planner). No ⋯ has Tags. Tests tapping tags under a sheet scope to `[role=dialog]`.
- **Rename and delete** in the picker: a pencil per tag the person may rename opens `TagEditor` (inline errors; Enter never submits the picker); owners get Delete, `DeleteTagDialog` naming how many records carry the tag.
- **The Tags page** (group settings, last; `settings/tags/`): every tag A to Z as its colored chip and "n items" (`useGroupTagUses`); Rename (`TagEditor`) and Color (`Swatch`es over `TAG_COLORS`, `recolorTag` at once) for `canRenameTag`; owners Merge (`MergeTagDialog`: a native select of the other tags, the confirm names both and the count) and Delete. Local writes, so it works offline; anyone else sees the list alone.
- **Tag filters:** a Tag section (none when the group has no tags) on the Todos tab, Planner Upcoming (carried to Past as a chip), Providers and the Medications list; `?tag=` through `activeTag`, so a deleted tag is no filter. `lib/tags/tagFilter.ts` builds the Todos and Planner sections; providers and medications have their own copies (fold them in when one changes).
- **Chips** (`TagChips`), colored through `ui/tagLook.ts`'s `tagColorClass` (whole classes over the `--color-avatar-*` tokens; `Badge`'s `fill` takes them in place of the tone; null or unknown is the neutral chip), and the picker's toggles show a color dot: on Planner, todo, provider and medication rows, two then "+N" (`ROW_CHIPS`), for every role; pages show them all.
- **`EntryFilters.tag`** (`timeline.sync.ts`): a `record_tag` subquery ANDed before `match`, in every window, link and medication query.
- **Timeline filter:** `?tag=` lives in `timelineFilters` (`setTag`, `clearTag`, part of `clearFilters`; a tag change clears `?day=`), a Tag section in the filter sheet and a removable chip. It narrows the history only: the Next strip, Today card and Latest vitals ignore it, and `summariesOff` counts it as a filter.
- **Search** (`search.sync.ts`): the Tag field is colored link chips (`TagSwatch` dots; one on, a second tap clears; a filter box past 12). Typed text also names tags (`matchingTagIds`, `lib/search/tagMatch.ts`: every word a prefix of a word in the name, none for an exclusion-only search); `searchGroup`'s `namedTags` adds the items carrying them as title matches, exclusions still applied, and each result shows its named tags' chips. `?tag=` (`SEARCH_TAG_PARAM`) is a `record_tag` subquery per taggable type, so conditions drop out and the index never stores tags; a tag with no text lists each type's live records (`taggedItems`) without the index. The page reruns on `record_tag` changes, since they don't touch the index; recent searches hide while a tag is on.
- **Reschedule** copies the old event's tags to the new one in its one transaction, with derived link ids; the cancelled event keeps its own.

## Limits

- Connectors read tags ([connectors](connectors.md) _Tools_); no calendar feed, email, print view or search index does.
- Not tagged: conditions, allergies, care periods, a repeating series as a whole. One tag per filter; no nesting. A merge drops `from`'s links on soft-deleted records too. The timeline's `?q=` doesn't match tag names.
- Known limit: a device that never saw a rename can add the old name and land on the renamed tag.
- Seeds: `seeds/tags.ts`, fictional tags with a color each on every seed group, on every taggable kind, written by the group's owner (derived ids).
