# Auth: `packages/auth` (Better Auth)

The auth area's rules and decisions, moved out of AGENTS.md (whose core rules still apply). An orchestrator folds a landing's lasting decisions for this area in here.

- **Tables:** it adopts our `user` table, and `session`/`account`/`verification`/`jwks` live in `db/schema/auth/auth.ts`. These are exceptions to the table conventions:
  - **no audits**;
  - **date-mode timestamps** (Better Auth compares `Date`s, and string mode silently breaks expiry);
  - `system`-only permissions.
- **Ids and extra fields:** ids come from `generateId: "uuid"` (the Postgres default). `role`, `createdBy` and `updatedBy` are `additionalFields` with `input: false`, defaulting to `SYSTEM_USER`.
- **Settings:** `emailAndPassword` with `disableSignUp: true` and a 12-character minimum; telemetry off; `trustedOrigins` = `allowedOrigins()` (`packages/auth/src/host.ts`: `AUTH_TRUSTED_ORIGINS`, plus Capacitor's origins only with `NATIVE_APP_ORIGINS=1`); `advanced.ipAddress.ipAddressHeaders` = `[CLIENT_IP_HEADER]` when it's set, else Better Auth's default (`x-forwarded-for`).
- **Plugins:** `bearer()` (native), and `jwt()`: 15-minute EdDSA tokens with `sub` and `role`, JWKS at `/api/auth/jwks`, and `aud` = `POWERSYNC_URL`.
- **Secrets and key rotation** (hosting slice 9; the procedure is _Rotating `BETTER_AUTH_SECRET`_ in [`ops/runbook.md`](../../ops/runbook.md)):
  - The jwt plugin stores each key's private half in `jwks`, encrypted with the current secret; it signs with the newest unexpired key and makes one when none is left.
  - `BETTER_AUTH_SECRETS` (`<version>:<secret>,…`, current first; `parseAuthSecrets`, checked by `checkDeployEnv`) is Better Auth's versioned list: every listed version still decrypts, and `BETTER_AUTH_SECRET` stays as the legacy secret for data from before the list. Once the list is in use, keep it set.
  - Session cookies and bearer tokens are signed with the **current** secret only, so making a new one current signs everyone out. Listing a new secret behind the current one changes nothing.
  - `pnpm auth:rotate-jwks [--reason]` (`authKeysService.rotate`; also the manual _Rotate JWT keys_ Action, app role only) expires the live keys, deletes keys retired over `JWKS_GRACE_SECONDS` (1 h) ago, and records `auth.jwksRotated`. The old public key stays in the JWKS for that hour, so 15-minute tokens it signed still verify. ❓ Whether PowerSync refetches the JWKS on an unknown `kid`: confirm on staging (slice 7).
- **Exports:** `getAuth()` (lazy) and `getAuthUser(headers, { live })` → `AuthUser` with `groupRoles`, from one query (`userModel.getAuthFacts`: the user joined to their memberships; null for a missing or disabled account). `live: true` bypasses the cookie cache. `@caretook/auth/client` has `createCaretookAuthClient`. It passes `fetchOptions.customFetchImpl` that looks up the global `fetch` per request (Better Auth otherwise captures it at creation), so component tests can stub the network. **Rate limits** are on only with `NODE_ENV=production` (check builds): get-session allows 100 per 10 s per client IP, then 429 with `x-retry-after` (see sync, `requireSession`; B-130). They're stored in Postgres (`rateLimit.storage = "database"`, the `rate_limit` table), so every instance shares one count. `createAuth({ rateLimitEnabled, originCheck })` is exported for tests (`getAuth()` is one memoized instance; `NODE_ENV=test` skips the Origin check unless `originCheck`). apps/web imports through `app/.server/auth.ts` and `app/lib/auth/auth-client.ts`.
- **Routes:** `/api/auth/*` is web only. `/sign-in` and `/sign-out` are shared and client-only (sign-out is POST only). The /app layout (`routes/app/layout/route.tsx`) redirects to `/sign-in?redirectTo=…`, checked by `safeRedirect`. The sign-in button stays disabled ("Signing in…") while any navigation is non-idle, so it can't be pressed again during the redirect's loaders.
- **Dev:** seeds give every `@example.com` user a password from `SEED_USER_PASSWORD` (`packages/data/.env`), hashed with `better-auth/crypto` (a dev dependency). The env is in `apps/web/.env`; `vite.config.ts` also loads `packages/data/.env`.
- ✅ **Sign-in methods**: password, and **one email with both a link and a 6-digit code** (B-96: the sign-in page's two tabs are Password and Email, with no explanation above the email form, whose button is **Send email**; `sendSignInEmail` in `emails.ts` makes the code with `emailOTP`'s `createVerificationOTP`, stored hashed, and queues one `signInEmail` keyed on the link token; an unknown address gets nothing; `/email-otp/send-verification-otp` is blocked, so a code is never sent alone; after sending, the page shows a code box for a different device; `?with=link|code` open the email form), all with `disableSignUp: true`, plus password reset and **`requireEmailVerification: true`**. `packages/auth/src/emails.ts` sends every auth email through `notify` (never awaited in the request). Every message about an address reads the same whether or not an account exists. Seed users are `email_verified = true`.
  - Shared, client-only routes `/reset-password` and `/verify-email` (`routes/account/`, on `AuthCard`); their paths come from `lib/auth/accountUrls.ts`, their wording from `lib/auth/authMessages.ts`. `requireSession` sends a signed-in but unverified user to `/verify-email`.
  - **Every account form submits through `useSubmitOnce()`** (`routes/account/AuthCard.tsx`): it ignores further submits until the request settles, so a double tap sends one email (B-1). A new account form uses it too.
  - **Sign-up only with a ticket:** `signUpWithTicket` (`packages/auth/src/tickets.ts`, server only) checks an invite ticket (`{ kind: "invite" }`) and the matching address, then creates a verified user and its password account through Better Auth's `internalAdapter`; errors are `ticket:*`. A **link** ticket takes any address and creates the account **unverified** (owners approve a confirmed email), and an address that already has an account gets the same answer and no new account. Public sign-up stays off. An **access-code** ticket (`{ kind: "accessCode", code, group }`) creates the account (unverified: a code doesn't prove the address), its password, and the redemption (group, recipient, owner membership, use count) in **one transaction**; any refusal leaves nothing. An address that already has an account gets the **same answer** (B-67): nothing is created, the use count is untouched, and the `accessCodeExistingAccount` email ("If it was you, sign in and choose New care group"; no code, no health details) is queued in the background, keyed by address, code and UTC day. A refused code is refused alike for either case (`accessCodeService.refusal`). `accessCode.signUp` returns only `{ email }`. `ticket:accountExists` stays for email-invite sign-up.
- ✅ **Our own limiter** (`packages/api/src/rateLimit.ts`, B-141): `createRateLimiter({ limit, windowMs, store })` with an async `hit`; stores are `memoryStore()` (tests, dev), `postgresStore(scope)` and `defaultStore(scope)` (Postgres when `NODE_ENV=production`, check builds included). A sliding window on `rate_limit_hit` (`rateLimitService.hit`): count and insert in one statement under a per-key advisory lock (without the lock, two instances both pass the last slot). Windows are at most `RATE_LIMIT_LONGEST_WINDOW_MS` (1 h). A store error fails the request rather than passing it unlimited. `sweepOutbox` purges old rows.
- ❓ Before launch:
  - native bearer storage (secure storage) and `VITE_API_ORIGIN`.

## ⚠ The session cookie cache (B-140)

**Reconsider before launch, and whenever the threat model changes** (shared devices, staff access, a breach response). Better Auth keeps a signed copy of the session in a cookie (`session_data`) that stands in for the session table on ordinary `/rpc` calls for up to **3 minutes** (`session.cookieCache.maxAge: 180`, `packages/auth/src/auth.ts`). **The tradeoff:** for up to 3 minutes after a session is revoked (signed out elsewhere, removed on the Devices page, "sign out everywhere else", a password reset), ordinary `/rpc` calls carrying its cookie still succeed. **Still live at once:**

- the account and its memberships (role, disabled-at, group roles), read from the database on every authed call, and sync uploads, checked in SQL;
- `staffProcedure` and `/admin` (`requireStaff`), which read the live session;
- `/api/auth/token` (PowerSync's JWT), forced live by a before hook on the exact path (`liveSession.ts`; `/oauth2/token` and the like don't match), so a revoked session opens no new sync connection;
- the app's own session check (`disableCookieCache`), so `session-end` detects revocation on its usual schedule.

Sign-out on this device clears the cache cookie at once; bearer-token clients (native) never use it. The jwt plugin sets no `set-auth-jwt` header (`disableSettingJwtHeader`), which would cost a key read per lookup. `packages/api/src/rpcAuth.int.test.ts` pins all of this.
