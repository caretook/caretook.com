# Auth: `packages/auth` (Better Auth)

The auth area's rules and decisions (AGENTS.md's core rules still apply). An orchestrator folds in lasting decisions.

- **Tables:** it adopts our `user` table, and `session`/`account`/`verification`/`jwks` live in `db/schema/auth/auth.ts`. Exceptions to the table conventions: **no audits**; **date-mode timestamps** (Better Auth compares `Date`s; string mode breaks expiry); `system`-only permissions.
- **Ids and extra fields:** ids come from `generateId: "uuid"`; `role`, `createdBy`, `updatedBy` are `additionalFields` with `input: false`, defaulting to `SYSTEM_USER`.
- **Settings:** `emailAndPassword` with `disableSignUp: true` and a 12-character minimum; telemetry off; `trustedOrigins` = `allowedOrigins()` (`packages/auth/src/host.ts`: `AUTH_TRUSTED_ORIGINS`, plus Capacitor's origins only with `NATIVE_APP_ORIGINS=1`); `advanced.ipAddress.ipAddressHeaders` = `[CLIENT_IP_HEADER]` if set, else `x-forwarded-for`.
- **Plugins:** `bearer({ requireSignature: true })` (native; only the signed `set-auth-token` works), and `jwt()`: 15-minute EdDSA tokens with `sub` and `role`, JWKS at `/api/auth/jwks`, `aud` = `POWERSYNC_URL`. `oauthProvider` serves connectors' OAuth ([connectors](connectors.md)).
- **Secrets and key rotation** (procedure: _Rotating `BETTER_AUTH_SECRET`_ in [`ops/runbook.md`](../../ops/runbook.md)):
  - The jwt plugin stores each key's private half in `jwks`, encrypted with the current secret; it signs with the newest unexpired key, making one if none is left.
  - `BETTER_AUTH_SECRETS` (`<version>:<secret>,…`, current first; `parseAuthSecrets`, checked by `checkDeployEnv`) is Better Auth's versioned list: every listed version still decrypts; `BETTER_AUTH_SECRET` stays as the legacy secret for older data. Keep it set once in use.
  - Session cookies and bearer tokens are signed with the **current** secret only, so a new current one signs everyone out; listing a new one behind it changes nothing.
  - `pnpm auth:rotate-jwks [--reason]` (`authKeysService.rotate`; also the _Rotate JWT keys_ Action) expires the live keys, deletes keys retired over `JWKS_GRACE_SECONDS` (1 h) ago, records `auth.jwksRotated`. The old public key stays in the JWKS for that hour, so 15-minute tokens it signed still verify. ❓ Does PowerSync refetch the JWKS on an unknown `kid`? Confirm on staging.
- **Exports:** `getAuth()` (lazy) and `getAuthUser(headers, { live })` → `AuthUser` with `groupRoles`, from one query (`userModel.getAuthFacts(userId, sessionId)`: user joined to memberships and the live session row; null if missing, disabled or revoked). `live: true` bypasses the cookie cache. `@caretook/auth/client` has `createCaretookAuthClient`. Its `fetchOptions.customFetchImpl` looks up `fetch` per request, so component tests can stub the network. **Rate limits** are on only with `NODE_ENV=production` (check builds): get-session allows 100 per 10 s per client IP, then 429 with `x-retry-after` (sync, `requireSession`; B-130). Stored in Postgres (`rateLimit.storage = "database"`, `rate_limit` table), so instances share a count. `createAuth({ rateLimitEnabled, limits, originCheck })` is for tests (`limits` turns ours on, with lower counts; `getAuth()` is memoized; `NODE_ENV=test` skips the Origin check unless `originCheck`).
- **Routes:** `/api/auth/*` is web only. `/sign-in` and `/sign-out` are shared and client-only (sign-out is POST only). Sign-out wipes the device, then tells the server (`pendingSignOut.ts`); offline or on a 5xx it keeps `caretook:sign-out-pending`, finished first by `requireSession` and sign-in (which refuses meanwhile). The marker names its session, so a later sign-in isn't ended; with changes waiting, the user menu asks first ([sync](sync.md) _Session_). The /app layout redirects to `/sign-in?redirectTo=…` (`safeRedirect`). The sign-in button stays disabled during any navigation. A fresh session's recheck that answers signed out mid-navigation sends sign-in back to that navigation's target while the address hasn't moved (B-869).
- **Dev:** seeds give every `@example.com` user a password from `SEED_USER_PASSWORD` (`packages/data/.env`), hashed with `better-auth/crypto`; `vite.config.ts` loads it too.
- ✅ **Sign-in methods**: password, and **one email with both a link and a 6-digit code** (B-96: tabs Password and Email, button **Send email**; `sendSignInEmail` in `emails.ts` makes the code with `emailOTP`'s `createVerificationOTP` (stored hashed), queues one `signInEmail` keyed on the link token; an unknown address gets nothing; `/email-otp/send-verification-otp` is blocked, so a code is never sent alone; after sending, a code box for a different device; `?with=link|code` open the email form), all with `disableSignUp: true`, plus password reset and **`requireEmailVerification: true`** (seed users are verified). `packages/auth/src/emails.ts` sends every auth email through `notify` (not awaited); every message about an address reads the same whether or not an account exists.
  - Shared, client-only routes `/reset-password` and `/verify-email` (`routes/account/`, `AuthCard`); paths from `lib/auth/accountUrls.ts`, wording from `lib/auth/authMessages.ts`. Every `authClient` call there and on `/sign-in` ends `.catch(unreached)`: offline shows `authMessages.offline` (verify-email: `unchecked`, not expired). `requireSession` sends a signed-in unverified user to `/verify-email`.
  - **Every account form submits through `useSubmitOnce()`** (`routes/account/AuthCard.tsx`): further submits are ignored until the request settles, so a double tap sends one email (B-1).
  - **Sign-up only with a ticket:** `signUpWithTicket` (`packages/auth/src/tickets.ts`, server only) checks an invite ticket (`{ kind: "invite" }`) and its address, then creates a verified user and password account through Better Auth's `internalAdapter`; errors are `ticket:*`. A **link** ticket takes any address and creates the account **unverified** (owners approve a confirmed email); an address that already has an account gets the same answer and no new account. An **access-code** ticket (`{ kind: "accessCode", code, group }`) creates the account (unverified: a code doesn't prove the address), password and redemption (group, recipient, owner membership, use count) in **one transaction**; a refusal leaves nothing. An address that already has an account gets the **same answer** (B-67): nothing is created, the use count is untouched, and the `accessCodeExistingAccount` email ("If it was you, sign in and choose New care group"; no code, no health details) is queued in the background, keyed by address, code and UTC day. `accessCode.signUp` returns only `{ email }`. `ticket:accountExists` stays for email invites.
  - **Legal acceptance** (`legal_acceptance`, `legalAcceptanceService`, `db/schema/auth/legalRules.ts`): access-code and invite sign-up require `legal: true`; a row names the terms, privacy, health-data and wording versions and its source. Access code records in its transaction, invite sign-up right after the account; if that fails, `invite.accept` asks (`legalRequired`; `invite.legalNeeded` tells the screen). Already accepted, a member's link and a waiting request don't ask. Append-only, system-written, read only by the person, never synced, no IP or user agent; deleted with the account; existing accounts aren't asked. `legalVersions.test.ts` keeps the versions equal to the pages' dates.
- ✅ **Our own limiter** (B-141): `createRateLimiter({ limit, windowMs, store })` (`@caretook/data`, `services/rateLimiter.ts`; `packages/api/src/rateLimit.ts` re-exports it and holds the scopes) with an async `hit`; stores are `memoryStore()` (tests, dev), `postgresStore(scope)` and `defaultStore(scope)` (Postgres when `NODE_ENV=production`, check builds included). A sliding window on `rate_limit_hit` (`rateLimitService.hit`): count and insert in one statement under a per-key advisory lock (else two instances pass the last slot). Windows are at most `RATE_LIMIT_LONGEST_WINDOW_MS` (1 h). A store error fails the request, never passes it. `sweepOutbox` purges old rows. Limits are off outside production unless a test turns them on.
  - **Per address** (scope `auth.<name>`; address trimmed, lower-cased, sha256): sign-in emails 5 an hour (past it the answer is unchanged, nothing sent); code tries 10 an hour (every try counts, before checking; past it answers as a wrong code).
  - **Per IP:** every limiter keys through `clientIpKey(clientIp, procedure)` (`host.ts`). In production (check builds too) no client IP is refused and logged; elsewhere it keys on `DEV_CLIENT_IP_KEY`; no "unknown" bucket. `checkDeployEnv` requires `CLIENT_IP_HEADER`. `/oauth2/register` has `AUTH_LIMITS.connectorRegisterIp` ([connectors](connectors.md)).
  - **Link sign-up** hashes the password before the account lookup; 10 an hour per IP (no IP: `ticket:invalid`) and 30 per link (past either: `ticket:invalid`).
  - `/update-user` is in `disabledPaths`.
- ❓ Before launch: native bearer storage (secure storage) and `VITE_API_ORIGIN`.

## The session cookie cache (B-140, B-339)

Better Auth keeps a signed session copy in a cookie (`session_data`, `session.cookieCache.maxAge: 180`, `auth.ts`), but `getAuthUser` joins the session row on every call, so a revoked session (signed out elsewhere, removed device, password reset) is refused on the next `/rpc` call. Still read live: the account and memberships, sync uploads (SQL), `staffProcedure` and `/admin` (`requireStaff`), `/api/auth/token` (a before hook on the exact path, `liveSession.ts`; a revoked session opens no new sync connection), and the app's own session check (`disableCookieCache`, so `session-end` sees revocation on schedule).

Sign-out clears the cache cookie at once; bearer clients (native) never use it. The jwt plugin sets no `set-auth-jwt` header. `/reset-password` revokes connector grants in `onPasswordReset` (the after hook can't see whose password changed). `rpcAuth.int.test.ts` pins all of this.
