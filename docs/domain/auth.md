# Auth: `packages/auth` (Better Auth)

The auth area's rules and decisions (AGENTS.md's core rules still apply). An orchestrator folds a landing's lasting decisions in here.

- **Tables:** it adopts our `user` table, and `session`/`account`/`verification`/`jwks` live in `db/schema/auth/auth.ts`. Exceptions to the table conventions:
  - **no audits**;
  - **date-mode timestamps** (Better Auth compares `Date`s, and string mode silently breaks expiry);
  - `system`-only permissions.
- **Ids and extra fields:** ids come from `generateId: "uuid"` (the Postgres default); `role`, `createdBy`, `updatedBy` are `additionalFields` with `input: false`, defaulting to `SYSTEM_USER`.
- **Settings:** `emailAndPassword` with `disableSignUp: true` and a 12-character minimum; telemetry off; `trustedOrigins` = `allowedOrigins()` (`packages/auth/src/host.ts`: `AUTH_TRUSTED_ORIGINS`, plus Capacitor's origins only with `NATIVE_APP_ORIGINS=1`); `advanced.ipAddress.ipAddressHeaders` = `[CLIENT_IP_HEADER]` if set, else `x-forwarded-for`.
- **Plugins:** `bearer()` (native), and `jwt()`: 15-minute EdDSA tokens with `sub` and `role`, JWKS at `/api/auth/jwks`, `aud` = `POWERSYNC_URL`. `oauthProvider` serves connectors' OAuth, opaque tokens ([connectors](connectors.md)).
- **Secrets and key rotation** (slice 9; procedure: _Rotating `BETTER_AUTH_SECRET`_ in [`ops/runbook.md`](../../ops/runbook.md)):
  - The jwt plugin stores each key's private half in `jwks`, encrypted with the current secret; it signs with the newest unexpired key, making one if none is left.
  - `BETTER_AUTH_SECRETS` (`<version>:<secret>,…`, current first; `parseAuthSecrets`, checked by `checkDeployEnv`) is Better Auth's versioned list: every listed version still decrypts; `BETTER_AUTH_SECRET` stays as the legacy secret for older data. Once in use, keep it set.
  - Session cookies and bearer tokens are signed with the **current** secret only, so a new current one signs everyone out. Listing a new secret behind the current one changes nothing.
  - `pnpm auth:rotate-jwks [--reason]` (`authKeysService.rotate`; also the _Rotate JWT keys_ Action) expires the live keys, deletes keys retired over `JWKS_GRACE_SECONDS` (1 h) ago, records `auth.jwksRotated`. The old public key stays in the JWKS for that hour, so 15-minute tokens it signed still verify. ❓ Does PowerSync refetch the JWKS on an unknown `kid`? Confirm on staging (slice 7).
- **Exports:** `getAuth()` (lazy) and `getAuthUser(headers, { live })` → `AuthUser` with `groupRoles`, from one query (`userModel.getAuthFacts`: user joined to memberships; null if missing or disabled). `live: true` bypasses the cookie cache. `@caretook/auth/client` has `createCaretookAuthClient`. Its `fetchOptions.customFetchImpl` looks up the global `fetch` per request (Better Auth otherwise captures it at creation), so component tests can stub the network. **Rate limits** are on only with `NODE_ENV=production` (check builds): get-session allows 100 per 10 s per client IP, then 429 with `x-retry-after` (sync, `requireSession`; B-130). Stored in Postgres (`rateLimit.storage = "database"`, `rate_limit` table), so instances share one count. `createAuth({ rateLimitEnabled, originCheck })` is for tests (`getAuth()` is one memoized instance; `NODE_ENV=test` skips the Origin check unless `originCheck`).
- **Routes:** `/api/auth/*` is web only. `/sign-in` and `/sign-out` are shared and client-only (sign-out is POST only). Sign-out wipes the device, then tells the server (`pendingSignOut.ts`); offline or on a 5xx it keeps `caretook:sign-out-pending`, finished first by `requireSession` and sign-in (which refuses meanwhile). The marker names its session, so a magic-link or invite sign-in made meanwhile isn't ended; with changes waiting, the user menu asks first ([sync](sync.md) _Session_). The /app layout redirects to `/sign-in?redirectTo=…`, checked by `safeRedirect`. The sign-in button stays disabled ("Signing in…") during any navigation. A fresh session's background recheck that answers signed out mid-navigation sends sign-in back to that navigation's target while the address hasn't moved (B-869).
- **Dev:** seeds give every `@example.com` user a password from `SEED_USER_PASSWORD` (`packages/data/.env`), hashed with `better-auth/crypto` (a dev dependency); `vite.config.ts` also loads that env.
- ✅ **Sign-in methods**: password, and **one email with both a link and a 6-digit code** (B-96: tabs Password and Email, no explanation above the email form, button **Send email**; `sendSignInEmail` in `emails.ts` makes the code with `emailOTP`'s `createVerificationOTP` (stored hashed) and queues one `signInEmail` keyed on the link token; an unknown address gets nothing; `/email-otp/send-verification-otp` is blocked, so a code is never sent alone; after sending, a code box for a different device; `?with=link|code` open the email form), all with `disableSignUp: true`, plus password reset and **`requireEmailVerification: true`** (seed users are verified). `packages/auth/src/emails.ts` sends every auth email through `notify` (never awaited in the request); every message about an address reads the same whether or not an account exists.
  - Shared, client-only routes `/reset-password` and `/verify-email` (`routes/account/`, on `AuthCard`); paths from `lib/auth/accountUrls.ts`, wording from `lib/auth/authMessages.ts`. Every `authClient` call there and on `/sign-in` ends `.catch(unreached)`: offline shows `authMessages.offline` (verify-email says `unchecked`, not expired). `requireSession` sends a signed-in unverified user to `/verify-email`.
  - **Every account form submits through `useSubmitOnce()`** (`routes/account/AuthCard.tsx`): it ignores further submits until the request settles, so a double tap sends one email (B-1); new account forms use it.
  - **Sign-up only with a ticket:** `signUpWithTicket` (`packages/auth/src/tickets.ts`, server only) checks an invite ticket (`{ kind: "invite" }`) and its address, then creates a verified user and password account through Better Auth's `internalAdapter`; errors are `ticket:*`. A **link** ticket takes any address and creates the account **unverified** (owners approve a confirmed email); an address that already has an account gets the same answer and no new account. An **access-code** ticket (`{ kind: "accessCode", code, group }`) creates the account (unverified: a code doesn't prove the address), password and redemption (group, recipient, owner membership, use count) in **one transaction**; a refusal leaves nothing. An address that already has an account gets the **same answer** (B-67): nothing is created, the use count is untouched, and the `accessCodeExistingAccount` email ("If it was you, sign in and choose New care group"; no code, no health details) is queued in the background, keyed by address, code and UTC day. `accessCode.signUp` returns only `{ email }`. `ticket:accountExists` stays for email invites.
  - **Legal acceptance** (`legal_acceptance`, `legalAcceptanceService`, `db/schema/auth/legalRules.ts`): access-code and invite sign-up require `legal: true`; a row names the terms, privacy, health-data and wording versions and its source. Access code records in its transaction, invite sign-up right after the account; if that write fails, `invite.accept` asks (`legalRequired`; `invite.legalNeeded` tells the screen). Already accepted, a member's link and a waiting request don't ask. Append-only, system-written, read only by the person, never synced, no IP or user agent; deleted with the account; existing accounts aren't asked. `legalVersions.test.ts` keeps the versions equal to the pages' dates.
- ✅ **Our own limiter** (B-141): `createRateLimiter({ limit, windowMs, store })` (`@caretook/data`, `services/rateLimiter.ts`; `packages/api/src/rateLimit.ts` re-exports it and holds the scopes) with an async `hit`; stores are `memoryStore()` (tests, dev), `postgresStore(scope)` and `defaultStore(scope)` (Postgres when `NODE_ENV=production`, check builds included). A sliding window on `rate_limit_hit` (`rateLimitService.hit`): count and insert in one statement under a per-key advisory lock (else two instances both pass the last slot). Windows are at most `RATE_LIMIT_LONGEST_WINDOW_MS` (1 h). A store error fails the request, never passes it unlimited. `sweepOutbox` purges old rows. Limits are off outside production unless a test turns them on.
  - **Per address** (scope `auth.<name>`; address trimmed, lower-cased, sha256): sign-in emails 5 an hour (past it the answer is unchanged, nothing sent); code tries 10 an hour (every try counts, before checking; past it answers as a wrong code).
  - **Link sign-up** hashes the password before the account lookup; 10 an hour per IP and 30 per link (past either: `ticket:invalid`).
  - `/update-user` is in `disabledPaths`.
- ❓ Before launch: native bearer storage (secure storage) and `VITE_API_ORIGIN`.

## ⚠ The session cookie cache (B-140)

**Reconsider before launch and when threats change.** Better Auth keeps a signed session copy in a cookie (`session_data`) that stands in for the session table on ordinary `/rpc` calls for up to **3 minutes** (`session.cookieCache.maxAge: 180`, `packages/auth/src/auth.ts`). **The tradeoff:** for up to 3 minutes after a session is revoked (signed out elsewhere, removed device, password reset), ordinary `/rpc` calls carrying its cookie still succeed. **Live at once:**

- the account and its memberships (role, disabled-at, group roles), read from the database on every authed call, and sync uploads, checked in SQL;
- `staffProcedure` and `/admin` (`requireStaff`), which read the live session;
- `/api/auth/token` (PowerSync's JWT), forced live by a before hook on the exact path (`liveSession.ts`; `/oauth2/token` etc. don't match), so a revoked session opens no new sync connection;
- the app's own session check (`disableCookieCache`), so `session-end` sees revocation on schedule.

Sign-out here clears the cache cookie at once; bearer-token clients (native) never use it. The jwt plugin sets no `set-auth-jwt` header (`disableSettingJwtHeader`). `packages/api/src/rpcAuth.int.test.ts` pins all of this.
