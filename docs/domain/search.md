# Search

The search area's rules and decisions, moved out of AGENTS.md (whose core rules still apply). An orchestrator folds a landing's lasting decisions for this area in here.

PRD: [`plans/search-prd.md`](../../plans/search-prd.md).

- **One query language** (`db/schema/search.ts`, client-safe; the only place a match string is built): `parseSearch`, then `toFtsMatch` (device) or `toTsQuery` (server). Words all match, each as a prefix; `"phrases"` match in order; `-word` and `-"phrase"` exclude; anything else is plain text, never a syntax error. Only exclusions, or nothing, is an empty search (`isEmptySearch`). Case and accents fold; input is capped at 200 characters and 12 terms. A partial word past its stem is also tried with common endings (`prefixForms`: "walki" → `walking*`), because FTS5 stores stems.
- **What is searchable** (`db/schema/searchDocument.ts`, one builder for device and server): `entrySearchDocument`, `providerSearchDocument`, `medicationSearchDocument` → `{ id, type, groupId, title, body }`, title-like fields weighted above body-like ones. Deleted rows get no document. **A new searchable field goes here, plus a `SEARCH_INDEX_VERSION` bump.**
- **The device index** (`lib/sync/searchTables.ts`, `lib/sync/search.ts`): FTS5 (`porter unicode61 remove_diacritics 2`; PowerSync web 2.7.0's wa-sqlite has it) in `search_fts`, with `search_item`, `search_meta` (the format version) and `search_dirty`, created with raw SQL outside PowerSync's schema. Triggers on PowerSync's `ps_data__<table>` storage tables record changed ids (`INSERT OR IGNORE` only, so they can't fail a sync write); the indexer re-indexes them, debounced 150 ms, in one transaction, and a changed provider, medication or user re-indexes the entries naming it. Document text comes from `previewText`, so unsynced typing is searchable. `openSync` starts it (lazy import); a missing index or a changed `SEARCH_INDEX_VERSION` rebuilds it (about 140 ms for 2,000 entries on desktop). **`dropSearchTables` runs before every `disconnectAndClear`** (sign-out and a different user), so the index never outlives the data.
- **Queries are always scoped to one group:** `entryMatchCondition(column, groupId, parsed)` (an `id IN (…)` condition for the timeline's windows), `searchEntryIds`, and `searchGroup` (ids, ranks, `titleMatch`, `occurredAt` per type, the first few plus totals; title matches first, then bm25 weights 4 and 1, then newest). Status for "Preparing search…": `searchIndexStatus` and `subscribeSearchIndexStatus` (`preparing | ready | unavailable`). Queries take 2–15 ms.
- **Highlights and snippets** (`db/schema/searchHighlight.ts`, client-safe, tested): `highlightRanges` and `highlightParts` (whole words only, the parser's folding and prefixes plus a light `wordStem`; phrases as one stretch; exclusions never marked), `searchSnippet` (about 120 characters around the first match, on word boundaries, with "…"), `snippetIfHidden` (only when the match is past `CLAMP_VISIBLE`, 80 characters or two lines) and `notesSnippet` (a line from a provider's or medication's notes when the match isn't in what's shown). `EntryBody` takes an optional parsed `search` (never the URL) and marks the heading, readings, "with …" names, a dose's note and the text, with a `[data-snippet]` line for a clamped note or event; Upcoming passes none.
- **The timeline's search** (`?q=` in `lib/timelineFilters`: `QUERY_PARAM`, `normalizeQuery` (trimmed, one space, 200 characters), `setQuery`, `clearQuery`; `clearFilters` clears it): `EntryFilters.match` (an `EntryCondition` the caller builds, so `lib/sync/timeline.ts` never imports the search module) is ANDed into the history, Upcoming and past windows and the lookups that share them; the Next strip keeps the search but not kind or author. `timelineSearch.ts` (beside the route) turns `q` and the index status into a state (`none | ready | empty | preparing | unavailable`) and the condition (`NO_MATCH` while preparing, unavailable or exclusion-only), with "Preparing search…", the polite announcement ("3 entries match …", "30+ …") and "That's every match." A reload with `?q=` waits up to 1 s for the index (`settledSearchIndexStatus`). The field (`useSearchField`, `FilterChips`): a magnifier `IconButton` at the start of the chips opens it (over the chips below `sm`, beside them from `sm`); typing updates the URL after 250 ms with `replace` and `preventScrollReset`, Enter at once, Escape closes and returns focus; a search shows as a "Matching “…”" chip whose ✕ clears only it. Latest vitals ignores it. "See all in Upcoming" doesn't carry `q`.
- **The search page** (`/app/groups/:groupId/search`, `routes/app/groups/search/`, `appUrls.search(groupId, q?, { all? })`; not a section): a magnifier `IconButton` link ("Search this care group", `data-region="search"`) in the `/app` header on group routes, before the sync status. An autofocused field writes `?q=` after 200 ms; providers, then medications, then entries (`lib/searchResults.ts`: title matches first, then rank, newest; 5 each, `?all=<type>` for one section in full), a polite count, "See all N in timeline". Results open what they are through `lib/entryOpen.ts` (the timeline's open rule; `SHEET_LINK_STATE` re-exported from `lib/timelineSheet`, so an edit sheet closes back to the search). Past providers and stopped medications are marked. Display fields are joined on the page (`loadSearch.ts`), with note and event text from `previewText`.
- **Recent searches** (`lib/recentSearches.ts`, tested): the last five distinct (case ignored, newest spelling kept) per user in `caretook:recentSearches:<userId>`; `recordSearch` when a search is used (leaving or submitting a field, closing the timeline's, opening a result), never on keystrokes; storage that throws means none; `forgetRecentSearches()` at sign-out. The empty search page lists them (one tap runs one) with a tips line about quotes and `-word`.
- **Server search** (`searchService.search(ctx, { groupId, q, scopes?, kinds?, from?, to?, authorId?, limit?, cursor? })`, oRPC `search.query`; the app doesn't call it): the shared parser's `toTsQuery` over **stored generated `tsvector` columns** (`timeline_entry.search_vector`: title and symptom name A, body, dose note, stop note and place B; `note_document.search_vector` over the compacted text), because building the text at query time took 245–430 ms against the 200 ms budget. Medication names, linked providers, authors and vital labels are matched at query time. Migration `0016_search` is hand-written (`unaccent`, an immutable `immutable_unaccent` wrapper, the two columns): **regenerate it as a custom migration** if `dev` gains one first. The columns aren't in Drizzle's schema (models never select them) and aren't published to PowerSync (generated columns aren't). No GIN indexes: the match joins two vectors, and a group's scan is about 10 ms for 10,000 entries (29–42 ms per search). Snippets are plain `ts_headline`; entries page by (rank, occurredAt, id), providers and medications come on the first page only; a non-member gets `searchService:notFound`. English stop words in exclusions can exclude more than the device would (an accepted difference).
- **Browser check:** `search.mjs` (in the suite; CDP 9711–9714, proxy 9721): the device module through `window.caretookModules().search`, the timeline's search, the page and the magnifier, highlights and snippets, recent searches and sign-out, offline, viewers and the other group. `cdp.mjs`'s `waitFor` wraps its expression in `!!(…)`, so an async expression is true at once: poll with `evaluate`. Headless Chrome fires no blur without `Emulation.setFocusEmulationEnabled`.
