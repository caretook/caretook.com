# Search

The search area's rules and decisions, moved out of AGENTS.md (whose core rules still apply). An orchestrator folds a landing's lasting decisions for this area in here.

PRD: [`plans/search-prd.md`](../../plans/search-prd.md).

- **One query language** (`db/schema/search/search.ts`, client-safe; the only place a match string is built): `parseSearch`, then `toFtsMatch` (device) or `toTsQuery` (server). Words all match, each as a prefix; `"phrases"` match in order; `-word` and `-"phrase"` exclude; anything else is plain text, never a syntax error. Only exclusions, or nothing, is an empty search (`isEmptySearch`). Case and accents fold; input is capped at 200 characters and 12 terms. A partial word past its stem is also tried with common endings (`prefixForms`: "walki" → `walking*`), because FTS5 stores stems.
- **What is searchable** (`db/schema/search/searchDocument.ts`, one builder for device and server): `entrySearchDocument`, `providerSearchDocument`, `medicationSearchDocument`, `todoSearchDocument` (title, then assignee and notes), `conditionSearchDocument` (name; note as body; resolved ones too) → `{ id, type, groupId, title, body }`, title-like fields weighted above body-like ones. Deleted rows get no document. **A new searchable field goes here, plus a `SEARCH_INDEX_VERSION` bump.** `SEARCH_ITEM_TYPES` ends with `condition`; `SERVER_SEARCH_ITEM_TYPES` leaves out `todo` and `condition`, which are device only (`searchService` and `search.query`'s scopes). Condition change entries are indexed by the condition's names (and a rename's old and new). `SEARCH_INDEX_VERSION` is 5. `medicationSearchDocument`'s body starts with the type label (null adds nothing); server `searchMedications` doesn't match on type.
- **The device index** (`lib/search/searchTables.sync.ts`, `lib/search/search.sync.ts`): FTS5 (`porter unicode61 remove_diacritics 2`; PowerSync web 2.7.0's wa-sqlite has it) in `search_fts`, with `search_item`, `search_meta` (the format version) and `search_dirty`, created with raw SQL outside PowerSync's schema. Triggers on PowerSync's `ps_data__<table>` storage tables record changed ids (`INSERT OR IGNORE` only, so they can't fail a sync write); the indexer re-indexes them, debounced 150 ms, in one transaction, and a changed provider, medication or user re-indexes the entries naming it. Todos are indexed from `todo` (`readTodos`), their notes from the todo's document; conditions from `recipient_condition`. Document text comes from `previewText`, so unsynced typing is searchable. `openSync` starts it (lazy import); a missing index or a changed `SEARCH_INDEX_VERSION` rebuilds it (about 140 ms for 2,000 entries on desktop). **`dropSearchTables` runs before every `disconnectAndClear`** (sign-out and a different user), so the index never outlives the data.
- **Queries are always scoped to one group:** `entryMatchCondition(column, groupId, parsed)` (an `id IN (…)` condition for the timeline's windows), `searchEntryIds`, and `searchGroup` (ids, ranks, `titleMatch`, `occurredAt` per type, the first few plus totals; title matches first, then bm25 weights 4 and 1, then newest). Status for "Preparing search…": `searchIndexStatus` and `subscribeSearchIndexStatus` (`preparing | ready | unavailable`). Queries take 2–15 ms.
- **Highlights and snippets** (`db/schema/search/searchHighlight.ts`, client-safe, tested): `highlightRanges` and `highlightParts` (whole words only, the parser's folding and prefixes plus a light `wordStem`; phrases as one stretch; exclusions never marked), `searchSnippet` (about 120 characters around the first match, on word boundaries, with "…"), `snippetIfHidden` (only when the match is past `CLAMP_VISIBLE`, 80 characters or two lines) and `notesSnippet` (a line from a provider's or medication's notes when the match isn't in what's shown). `EntryBody` takes an optional parsed `search` (never the URL) and marks the heading, readings, "with …" names, a dose's note and the text, with a `[data-snippet]` line for a clamped note or event; Upcoming passes none.
- **The timeline's search** (`?q=` in `lib/timeline/timelineFilters`: `QUERY_PARAM`, `normalizeQuery` (trimmed, one space, 200 characters), `setQuery`, `clearQuery`; `clearFilters` clears it): `EntryFilters.match` (an `EntryCondition` the caller builds, so `lib/timeline/timeline.sync.ts` never imports the search module) is ANDed into the history, Planner and past windows and the lookups that share them; the Next strip keeps the search but not kind or author. `timelineSearch.ts` (beside the route) turns `q` and the index status into a state (`none | ready | empty | preparing | unavailable`) and the condition (`NO_MATCH` while preparing, unavailable or exclusion-only), with "Preparing search…", the polite announcement ("3 entries match …", "30+ …") and "That's every match." A reload with `?q=` waits up to 1 s for the index (`settledSearchIndexStatus`). The field (`useSearchField`, `FilterChips`): a magnifier `IconButton` at the start of the chips opens it (over the chips below `sm`, beside them from `sm`); typing updates the URL after 250 ms with `replace` and `preventScrollReset`, Enter at once, Escape closes and returns focus; a search shows as a "Matching “…”" chip whose ✕ clears only it. Latest vitals ignores it. "See all in Upcoming" doesn't carry `q`.
- **The search page** (`/app/groups/:groupId/search`, `routes/app/groups/search/`, `appUrls.search(groupId, q?, { all? })`; not a section): a magnifier `IconButton` link ("Search this care group", `data-region="search"`) in the `/app` header on group routes, before the sync status (in easy mode too; `/search` is on the easy roles' allow-list). An autofocused field writes `?q=` after 200 ms; providers, then medications, then conditions (`ConditionResultItem`: a resolved one is marked; they open its sheet over the profile), then todos (`TodoResultItem`: a Done badge, a notes snippet; they open the todo page), then entries (`lib/search/searchResults.ts`: title matches first, then rank, newest; 5 each, `?all=<type>` for one section in full), a polite count, "See all N in timeline" (hidden for easy roles).
  - **Easy roles** open a provider, medication or condition result in a read-only sheet over the page (`EasyResultSheet.tsx`: its facts and contact details, no editing; it keeps only `{ type, id }` and reads the row live through `useEasyOpened`, showing a removed state once it's deleted); notes, events and todos open as usual. Results open what they are through `lib/timeline/entryOpen.ts` (the timeline's open rule; `SHEET_LINK_STATE` re-exported from `lib/timeline/timelineSheet`, so an edit sheet closes back to the search). Past providers and stopped medications are marked. Display fields are joined on the page (`loadSearch.ts`), with note and event text from `previewText`.
- **Tags** ([tags](tags.md), tags-3): typed text also matches tag names at query time (`matchingTagIds`; `searchGroup`'s `namedTags` adds the tagged items as title matches, exclusions applied), so the index never stores tags and `SEARCH_INDEX_VERSION` doesn't move; the page reruns on links of the named tags. The timeline's `?q=` doesn't match tags.
- **Recent searches** (`lib/search/recentSearches.ts`, tested): the last five distinct (case ignored, newest spelling kept) per user in `caretook:recentSearches:<userId>`; `recordSearch` when a search is used (leaving or submitting a field, closing the timeline's, opening a result), never on keystrokes; storage that throws means none; `forgetRecentSearches()` at sign-out. The empty search page lists them (one tap runs one) with a tips line about quotes and `-word`.
- **Recently viewed** (`lib/core/recentlyViewed.ts`, the todo Link to box's suggestions): per user, device only, at most 10, forgotten at sign-out; `useRecordView(userId, type, id | null)` on provider, medication, entry pages.
- **Server search** (`searchService.search(ctx, { groupId, q, scopes?, kinds?, from?, to?, authorId?, limit?, cursor? })`, oRPC `search.query`; the app doesn't call it): the shared parser's `toTsQuery` over **stored generated `tsvector` columns** (`timeline_entry.search_vector`: title and symptom name A, body, dose note, stop note and place B; `note_document.search_vector` over the compacted text), because building the text at query time took 245–430 ms against the 200 ms budget. Medication names, linked providers, authors and vital labels are matched at query time. Migration `0016_search` is hand-written (`unaccent`, an immutable `immutable_unaccent` wrapper, the two columns): **regenerate it as a custom migration** if `dev` gains one first. The columns aren't in Drizzle's schema (models never select them) and aren't published to PowerSync (generated columns aren't). No GIN indexes: the match joins two vectors, and a group's scan is about 10 ms for 10,000 entries (29–42 ms per search). Snippets are plain `ts_headline`; entries page by (rank, occurredAt, id), providers and medications come on the first page only; a non-member gets `searchService:notFound`. English stop words in exclusions can exclude more than the device would (an accepted difference).
- **Tests:** no area check (`search.mjs` was moved, B-120). Component tests cover the device index on wa-sqlite (`lib/search/search.sync.browser.test.tsx`, including the 2,000-entry timing), the search page and magnifier (`groups/search/search.browser.test.tsx`) and the timeline's search, highlights and period chip (`timeline/timelineSearch.browser.test.tsx`). `renderWithDevice({ search: true })` builds the index, and `device.settle()` then waits for it to take in changes. `session-end` asserts recent searches and the index tables are gone when the session ends. Server search is integration tests only.
