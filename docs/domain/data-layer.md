# Data layer: `packages/data` (`@caretook/data`)

The data layer area's rules and decisions (AGENTS.md's core rules still apply).

- **Entry points:**
  - `@caretook/data` is **server only**: never import the root from client code.
  - `/schema`, `/errors` and `/permissions` are client-safe; `/series` too (rrule: loaded only where a series is written or previewed, not in the schema index or first load).
  - apps/web's server code imports through `app/.server/data.ts`.
- **Layers, bottom up:**
  - `errors/`: typescript-errors; each area's codes are a part, `errors/<area>.ts`, composed in `errors/constants.ts` (unique across parts: `errors.test.ts`). Errors are **returned, not thrown**; narrow with `isError()`. Wrap db calls as `dbMayFail(() => …, code)`.
  - `permissions/`: `PERMISSIONS[table][create|read|update|delete|list][role] = all | owned | none | { group: [...], groupOwn?: [...] }`, plus `ownerField`, field-level write restrictions and **`groupFields`**: a read reached only through a group rule returns just those fields (`user`: `PUBLIC_PROFILE_FIELDS`, id, name, image). Enforced in SQL (each hidden column is `CASE WHEN <the other rules> THEN col END`; filters and orders on it match whole rows only). User reads return `publicOnly`; code that needs a co-member's email reads `userModel.getWhole*`/`listWhole` as `SYSTEM_USER` (else `userModel:notWhole`).
    - Roles are `admin`, `support` and `member` (`user.role`), `system` and `unauthenticated`. `support` gets `owned` wherever members do; staff-only tables use `STAFF_PERMISSION_ENTRY`. A resolved scope is `all` or an OR of `owned`, `group`, `groupOwn` and `groupUser` rules. **`groupOwn`** (`PermissionEntry`; needs `groupField`) lists group roles whose permission holds only on rows with `created_by` = the actor: `queryHelpers.ts` ANDs `created_by` into the group rule; `hasPermission` takes the row's creator.
    - `hasPermission()` is for UI checks.
  - `models/`: `baseModel.getFunctions(...)` gives `create/get/getById/list/update/remove/upsert`, with **RBAC enforced in SQL**.
    - Every query is ANDed with the actor's scope; group rules become subqueries on `care_group_member`.
    - Writes must land inside the scope.
    - Update and remove refuse an empty filter.
    - Filters are serializable (`{ field: { type: "eq", value } }`) and checked against the table's columns.
  - `services/`: `getService(model)` with `ServiceContext = { authUser, tx? }`. Business rules, side effects and transactions go here. Services never read requests; internal work uses `SYSTEM_USER`.
- **`withTransaction(fn)` rolls back when `fn` returns an AppError.** `afterCommit(tx, fn)` runs work after the outermost commit (e.g. starting a Google push with `waitUntil`).
- **Arg types use `WithoutProtected<T>`:** a generic `Omit<DbInsert<K>, …>` silently drops optional columns such as `id`.
- **Table conventions:**
  - UUID PKs via `id()`: clients create rows offline, so `create`/`upsert` accept a caller-supplied id.
  - Every table spreads `timestamps` (timestamptz, string mode) and `audits` (`created_by`/`updated_by`, set by models, not FKs).
- **Adding a table:**
  1. Write `db/schema/<area>/<name>.ts` (table, types, Zod) and export it from that folder's `index.ts`; a new area adds a folder and a line in `db/schema/index.ts`.
  2. Add its `PERMISSIONS` entry to `permissions/<area>.ts` (required; a test checks every table has one); its errors go in `errors/<area>.ts`.
  3. Add `models/<name>/` and `services/<name>Service.ts`, and register both.
  4. If it syncs: `ALTER PUBLICATION powersync ADD TABLE …` in a migration, plus a stream query and a device schema entry.
- **Migrations:** generated into `src/db/migrations/` and applied in-process (`src/db/migrate.ts`). There are 0000–0036 so far.
  - **`0034` is a copy, not a rename** (simple becomes easy): `care_group.easy_tiles` and `user.preferences.easyMode` are filled from `simple_tiles` and `simpleMode`. Retired but kept unread until a contract migration: `simple_tiles` (schema `simpleTiles`), the old preference key, and `care_group_member.simple_mode` and `simple_mode_locked` (`0036` converted locked members to easy roles: [care-groups](care-groups.md)).
  - **drizzle-kit can emit a unique constraint after the FK that needs it.** Read the generated SQL and reorder by hand.
  - Until the first deploy it's fine to delete and regenerate migrations.
  - **`0032_todos` is a one-step rename** (tasks to todos), the user's one exception to additive migrations (production isn't live). Hand-edited: it renames the table, `note_document.task_id`, indexes and constraints (a `DO` block renames Postgres 18's named NOT NULL constraints), and rewrites stored values that spelled the old word (note subject, `calendar_sync_job.reason`, `google_event_link.item_uid`, reminder outbox keys, `taskDue` → `todoDue`). Deploy: [runbook](../../ops/runbook.md#rollback).
- **DB client:** the pool is created lazily (importing never needs `DATABASE_URL`). Only the **pool** survives HMR (`utils/remember.ts`); the drizzle wrapper is rebuilt, so new tables work without a restart.
- **Env:** `loadEnv.ts` loads `.env.<NODE_ENV>`, then `.env`, from `packages/data` (Node's `process.loadEnvFile`). Real env vars win. `.env.test` is committed; `.env` isn't (copy `.env.example`).
- **Local Postgres:** Docker `postgres:18.7-alpine` with `wal_level=logical`, dev on :5434 and test on :5435, data in `.postgres/`.
  - Integration tests: the main checkout's test database is on :5435, a `.loops` worktree's `caretook_test_<worktree>` on the shared test Postgres (:5436, [loops](../loops.md)). The guard, `src/db/testDatabase.ts`, refuses a non-local host, another port or (shared) another name. **`createWorld`** (`test/fixtures.ts`): a group, members by role, its recipient. Role matrices are tested at the services; routers and connectors keep one pass-through test.
  - **A database per worker:** `CARETOOK_INT_WORKERS` (default 3; `1` runs in order on the database itself). The global setup migrates the test database and copies it to `<name>_w<n>` as a template; `test/setup.ts` picks a worker's copy by `VITEST_POOL_ID`. `pnpm prd test-db drop` and `pnpm prd rm` drop them.
  - `datastore:clear` refuses a non-localhost database, and drops the publication.
  - `datastore:seed` uses `@example.com` accounts only, behind `seedRefusal(env)` (`seeds/guard.ts`): `APP_ENV=production` is refused (`db:seed:production`), staging needs a set, non-default `SEED_USER_PASSWORD` (`db:seed:password`), an unknown `APP_ENV` is refused, and with no `APP_ENV` so are `NODE_ENV=production` and any non-localhost database (`db:seed:notLocal`). On staging the seed then moves every `@example.com` password account whose hash doesn't match the current `SEED_USER_PASSWORD` to it (`rotateStagingPasswords`, `seeds/accounts.ts`; a rerun changes nothing), so rotating the password is: change the secret, rerun the seed. On staging the seed also makes every real (not `@example.com`) account an owner of each seeded group (`seeds/realOwners.ts`).
  - `datastore:reset:staging` (`db/resetStaging.ts`, the Reset staging Action) starts staging over: only with `APP_ENV=staging` (`db:reset:notStaging`) and a seed that would run, it deletes every row of every public table except `KEPT_TABLES` (sign-ins, signing keys, staff settings, suppressions, the OAuth resource) in foreign-key order as the app role, then the `@example.com` users, then seeds. Rows are deleted, never truncated, so PowerSync replicates it. A new table is wiped without an edit; add it to `KEPT_TABLES` only if it holds configuration, not care data.
- ✅ **The hosted database** (Neon, `aws-us-east-2`, beside Vercel's `cle1`; set up by [`ops/runbook.md`](../../ops/runbook.md)) has three roles, made idempotently by `pnpm db:roles` (`db/roles/`, `rolesSql`) without passwords (Neon sets them):
  - `caretook_migrations` owns the schema (DDL); migrations and `db:roles` use its direct URL, `MIGRATIONS_DATABASE_URL`, held only in GitHub. `datastore:migrate` refuses a deployed `APP_ENV` without it (`migrationsDatabaseUrl`).
  - `caretook_app` (Neon's pooled `DATABASE_URL`): read and write on every table, no `CREATE`; default privileges cover later tables.
  - `caretook_replication`: see [sync](sync.md), _Production_.
  - `db:roles` runs after every migration (it narrows the publication migrations widen). Integration tests that create roles use unique names and drop them.
- **Personal access** (`pnpm db:access grant <email> --hours N | revoke <email> | list`, `dbAccessService`): a `staff_<slug>` LOGIN role, read-only (`default_transaction_read_only`), with SELECT on every table **except the secrets** (`PERSONAL_ACCESS_EXCLUDED` in `db/roles/personalAccess.ts`: the feed token hash, Google's sealed refresh and sync tokens and OAuth state, Better Auth's `account`, `session`, `verification` and `jwks`, the rate-limit tables, and column grants that leave out invite token hashes and ciphertext, `access_code.code` and email bodies; a unit test fails on a new column or table matching `token|secret|hash|password|private` that isn't listed or allowed; `grant` starts with `REVOKE ALL`, so a re-grant narrows an older role, and `revoke` removes the column grants too), `VALID UNTIL` at most 24 h, the password sent only as a SCRAM verifier and printed once. Staff accounts only. Audited `db.accessGranted` / `db.accessRevoked` (system actor, the staff member as target). `revoke` ends its sessions and is safe twice. `VALID UNTIL` stops new sign-ins only. The procedure is [`ops/break-glass.md`](../../ops/break-glass.md).
- **Sealing:** `utils/seal.ts` is AES-256-GCM with a key and associated data (Google refresh tokens; the `linkToken.ts` pattern, with `createHmac` `linkSubkey` for derived link tokens).
- **System-only tables written directly** (no model, no audits): the `google_*` and `calendar_sync_job` tables (`googleConnectionService`, `calendarSyncService`), `rate_limit_hit` and Better Auth's `rate_limit` (`rateLimitService`, Better Auth), and `email_suppression` (`emailSuppressionService`).
