# Care groups

The care groups area's rules and decisions.

The shared space for one care recipient's caretakers. Always "care group" (never "care circle").

- **Tables** (`packages/data/src/db/schema/care-groups/`):
  - `care_group` (`name`); `care_group_member` (`group_id`, `user_id`, `role`, unique per pair; `invited_by` FK to `user`, set null).
  - `care_recipient`: a profile, not an account; 1:1 through a unique `group_id`. **`time_zone`** (IANA, required, no database default) is where the recipient lives: medication schedules are in it. Every way of creating a group sends the device's zone (`newGroupFromForm`); services fall back to `FALLBACK_TIME_ZONE` (UTC); an unknown zone is `careRecipientService:invalidTimeZone`. Owners, admins and caretakers change it in group settings Details through `careGroup.updateRecipient`; `GroupContext.recipient.timeZone` carries it to group screens.
  - `care_group_invite` (`kind` `email|link`, `email` required for email invites, role, SHA-256 `token_hash`, status `pending|accepted|declined|revoked`, `expires_at`, `accepted_by`, `max_uses`/`use_count`, the inviter's attestation `consent_attested_by`/`_at` with `consent_version`). A link invite keeps its token sealed in `token_ciphertext` (AES-256-GCM, `utils/linkToken.ts`, keyed by sha256 of `INVITE_LINK_KEY`, the invite id as associated data); an email invite's token is never stored. Production without a key refuses `createLink` (`linkKeyMissing`); dev and tests use a fixed key. Set `INVITE_LINK_KEY` the same in `apps/web/.env` and `packages/data/.env`; reminder unsubscribe tokens derive from it (`linkSubkey`).
  - `care_group_consent` the joiner's recorded consent.
  - `care_group_join_request` (`group_id`, `user_id`, `invite_id`, `role` caretaker or viewer only (a DB check), status `pending|approved|declined|withdrawn`, `decided_by`; at most one pending request per group and user).
  - `access_code` (`code` unique, `XXXX-XXXX-XXXX` from an alphabet without 0/O/1/I/L, **stored plain** so staff can reprint it; `label`, `expires_at`, `max_uses` (null = unlimited), `use_count`, `revoked_at`) and `access_code_redemption` (`group_id` set null on group delete). Global admins and `system` only; a code is a sign-up ticket.
  - **Not synced:** invites and consent rows are managers' data with addresses, read through oRPC. Only the member's `invited_by` and `created_at` sync.
  - Deleting a group cascades to everything in it; deleting a user, to their memberships.
- **Two role systems:** global (`admin`, `support`, `member`) covers account and staff access only (see [admin](admin.md)). Group roles on the membership are `owner`, `admin`, `caretaker` and `viewer`. **Writers** = owner, admin and caretaker.
- **Permissions** (`PERMISSIONS[table][action][role]`; "any member" reads, "writers" = owner, admin, caretaker):
  - `care_group`: read any member; create any signed-in user (becomes owner); update owner, admin; delete owner.
  - `care_group_member`: read any member; create owner, admin; update owner, admin (role only); delete owner, admin, or yourself (leave).
  - `care_recipient`: read any member; create and delete owner, admin; update owner, admin, caretaker.
  - `care_group_invite`: owner and admin for everything (update: status only).
  - `care_group_consent`, `care_group_join_request`: read owner, admin, yourself; writes `system`.
  - `access_code`: staff for everything (update: not the code or use count). `access_code_redemption`: read staff; writes `system`.
  - `user`: read self, staff and co-members (id, name, image); create staff; update self (no role or email); delete self, staff.
  - `timeline_entry`, `provider`, `medication`, `care_period`, `medication_pass`, `recipient_allergy`, `recipient_condition`: read any member; create, update and (soft) delete writers.
  - `medication_condition`, `condition_manager` (`medicationConditionSchema`, `conditionManagerSchema`): read any member; create and delete writers; update `system`. Written through their services, which check both ends.
  - `task`: as above, but update also for viewers ¹. `appointment_series`: as above (writers).
  - `member_calendar_setting`, `reminder_override`: the member's own rows only (staff too); the feed hash is `system`. `google_*`, `calendar_sync_job`: `system` only ([calendars](calendars.md)).
  - `note_document`: read any member; create writers (snapshot and text: `system`); update and delete `system`. `note_update`: read any member; create writers; update and delete `system`.
  - `timeline_entry_provider`: read any member; create and delete writers; update `system`.
  - `care_recipient_details`: read, create and update writers (viewers none; outside contacts: owner, admin); delete `system`.
  - `user_contact`: yourself only for everything (not staff). `member_contact_share`: read any member; writes `system`.
- ¹ `todoService` limits a viewer and both easy roles to ticking or unticking a todo assigned to them (`todoService:completionOnly`, one rule and one error for all three); see [todos](todos.md).
- `system` has `all` everywhere. Ids that point at the group can't be changed except by `system`.
- **Staff get no default access to care data.** Any support access will be an explicit, audited grant.
- **Write memberships and invites through the services**, because they enforce what the map can't:
  - `careGroupService.create` makes the creator the first owner.
  - Only owners add, promote, demote or remove owners. A group keeps at least one owner (owner rows lock `FOR UPDATE`).
  - Removing or leaving a membership, in the same transaction: hands that user's open todos to a free-text assignee (their display name; `todoService.releaseAssignee`) and deletes their calendar settings, overrides and feed and disconnects their Google (`calendarSettingService.removeForMember`, `googleConnectionService`).
  - `careGroupInviteService` (rules in the pure, client-safe `inviteRules.ts`, with the consent and attestation texts and versions):
    - `createEmail` requires the inviter's attestation, only owners invite owners, refuses current members and a second waiting invite, and replaces an expired one (7-day expiry). `resend` rotates the token and resets the expiry; `revoke` withdraws it. No procedure returns a token.
    - `preview(token)` (public; closed invites never name the group), `ticketFor(token)` (for sign-up), `accept` (the signed-in, verified email must match; one transaction as `system`: the membership with `invitedBy`, the consent row, email verified, the invite accepted; idempotent) and `decline(token)` (anyone holding the link).
    - **Links:** `createLink` (owners and admins; caretaker or viewer only; 1-90 days, default 7; optional `max_uses`) and `copyLink` (active links only; an email invite gets `notLink`). `accept` with a link goes to `askWithLink`: a member passes, anyone else gets one pending join request (asking again returns it, even after the link closes); `accept` returns `{ status: "joined" | "requested" }`. `invite.decline` refuses links (`wrongKind`).
  - `joinRequestService`: `requestWithLink`, `approve` (the membership with `invitedBy` = the link's maker), `decline`, `withdraw`; every write as `system`, row locked `FOR UPDATE`; non-members get `notFound`, non-manager members `notAllowed`. Its emails (to every owner and admin on a request; the outcome to the requester) go through an injected `JoinMailer` in the transaction and carry no health details. `groupDisplayName` lives in `services/groupNames.ts`.
  - `accessCodeService` (staff `list`, `getById`, `create`, `revoke`; public `preview` (state only); `redeem(tx, …)` as `system`, the code locked `FOR UPDATE`) and `staffGroupService.createWithOwnerInvite` (a group and recipient with no members, `created_by` the staff member, then an owner invite through `createEmail` as `system` with the staff member as attester; the `ownerInvite` email). `careGroupModel.createWithoutOwner` is staff and system only.
  - The `groupInvite` email (no health details) goes through an injected `InviteMailer` in the service's transaction (the invite and its outbox row commit together), then `deliverSoon`.
- **Seeds** (`packages/data/src/db/seeds/`): "Dev Family" (Grandma Pat) has member@ as owner, caretaker@ and viewer@. `secondGroup.ts` gives member@ a second group, so `/app` is the group list on a fresh device; `moreGroups.ts` adds multi-role users (trio@, groupadmin@, viewer2@, owner2@, solo@ as sole owner so the invite card shows) in four time zones; `accessCodes.ts` adds `CARE-DEMO-0001`; `invites.ts` adds `joiner@example.com` with a pending join request, an email invite and a viewer link. admin@ is no member. Each has its own ids.
- **Easy mode columns:** `care_group_member.simple_mode` and `simple_mode_locked` (booleans, default false), `care_group.easy_tiles` jsonb (`easyTilesZSchema` in `db/schema/app-shell/easyMode.ts`: `{ mode: learned | fixed | custom, tiles? }`, custom carries exactly 4; null = learned; it replaced `simple_tiles`, which is kept unread until a contract migration, and `user.preferences.easyMode` replaced `simpleMode` the same way). Synced through the `care_groups` stream and the device schema, **not** in the upload switch: written online through `careGroup.setMemberMode({ groupId, userId, simpleMode?, locked? })` and `careGroup.update` (`easyTiles`). `careGroupMemberService.setMode`: owners and admins set them (`memberAccess().simpleMode`); only owners change an owner's row (`ownerOnly`); nobody changes their own lock (`careGroupMemberService:ownLock`, 403, including unlocking by turning one's own default off); locking turns the default on and turning the default off unlocks. Both are system-only on member create.
- **The assistants switch:** `care_group.connectors_enabled` (default false; Dev Family seeded on), owners only through `careGroup.update`. Off revokes every connector grant in the same transaction; removing or leaving revokes that member's. Synced, not in the upload switch ([connectors](connectors.md)).
- **UI:** the Members page's Easy mode and Locked switches (`memberAccess().lock`, never your own row) are online-only, send only what changed, and show the server's rules optimistically. The tiles card in Details (`EasyTilesCard`) saves through `parseEasyTilesChoice` (`groupSettings.ts`: refuses fewer than four, repeats and unknown tiles).
