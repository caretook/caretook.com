# Care groups

One care recipient's caretakers' shared space: "care group", never "care circle".

- **Tables** (`packages/data/src/db/schema/care-groups/`):
  - `care_group` (`name`); `care_group_member` (`group_id`, `user_id`, `role`, unique per pair; `invited_by` to `user`, set null).
  - `care_recipient`: a profile, not an account; 1:1 via unique `group_id`. **`time_zone`** (IANA, required, no default) is where the recipient lives: schedules use it. Group creation sends the device's zone, else `FALLBACK_TIME_ZONE` (UTC); an unknown one is `careRecipientService:invalidTimeZone`. Writers edit it in Details (`careGroup.updateRecipient`); `GroupContext.recipient.timeZone` carries it.
  - `care_group_invite` (`kind` `email|link`, `email`, role, SHA-256 `token_hash`, status `pending|accepted|declined|revoked`, `expires_at`, `accepted_by`, `max_uses`/`use_count`, inviter attestation `consent_attested_by`/`_at`, `consent_version`). A link invite seals its token in `token_ciphertext` (AES-256-GCM, `utils/linkToken.ts`, key `INVITE_LINK_KEY`); an email invite's token isn't stored. Production or staging without it refuses `createLink` (`linkKeyMissing`) and the seed (`db:seed:linkKey`; a reseed reseals); dev and tests use a fixed key. Same key in both `.env`s; unsubscribe tokens derive from it.
  - `care_group_consent`: the joiner's consent.
  - `care_group_join_request` (`group_id`, `user_id`, `invite_id`, `role` caretaker or viewer (DB check), status `pending|approved|declined|withdrawn`, `decided_by`; one pending per group and user).
  - `access_code` (`code`, `XXXX-XXXX-XXXX` without 0/O/1/I/L, **stored plain** for reprinting; `label`, `expires_at`, `max_uses` (null = unlimited), `use_count`, `revoked_at`) and `access_code_redemption` (`group_id` nulled on group delete). Admins and `system` only.
  - **Not synced:** invites and consent rows (addresses; oRPC); of a member, only `invited_by` and `created_at`.
  - Deleting a group cascades to all in it; a user, to their memberships.
- **Two role systems:** global (`admin`, `support`, `member`) is account and staff access only ([admin](admin.md)). Group roles on the membership are `owner`, `admin`, `caretaker`, `viewer` and the two easy roles, `easy_helper` (logs care, edits only own entries) and `easy_viewer` (reads; ticks own todos); each has `group: regular | easier` for the picker. Role sets live in client-safe `constants/roles.ts` (re-exported from permissions): `WRITERS` (owner, admin, caretaker), `LOGGERS` (`WRITERS` + `easy_helper`), `EASY_ROLES`, `OWN_ROW_LOGGERS` (loggers who aren't writers), `MANAGERS`, `OWNERS`; never compare a role string outside them.
- **Permissions** (`PERMISSIONS[table][action][role]`; **`groupOwn`**: held only on rows the actor created, in SQL, see [data-layer](data-layer.md)):
  - `care_group`: read any member; create any signed-in user (the owner); update owner, admin; delete owner.
  - `care_group_member`: read any member; create owner, admin; update owner, admin (role only); delete owner, admin, yourself.
  - `care_recipient`: read any member; create, delete owner, admin; update owner, admin, caretaker.
  - `care_group_invite`: owner and admin for everything (update: status only).
  - `care_group_consent`, `care_group_join_request`: read owner, admin, yourself; `system` writes.
  - `access_code`: staff for everything (update: not the code or use count). `access_code_redemption`: read staff; `system` writes.
  - `user`: read self, staff, co-members (`PUBLIC_PROFILE_FIELDS`); create staff; update self (no role or email); delete self, staff.
  - `timeline_entry`: read any member; create loggers; update and (soft) delete writers, and an Easy helper on own entries (`groupOwn`), never a setup field, even to clear it. `provider`, `medication`, `care_period`, `medication_pass`, `recipient_allergy`, `recipient_condition`: read any member; writers write (soft delete).
  - `medication_condition`, `condition_manager`: read any member; create and delete writers; update `system`. Their services check both ends.
  - `todo`: as above, but update also for viewers (`todoService` limits a viewer and both easy roles to ticking a todo assigned to them, `todoService:completionOnly`; [todos](todos.md)). `appointment_series`: as above (writers).
  - `member_calendar_setting`, `reminder_override`: the member's own rows; the feed hash is `system`. `google_*`, `calendar_sync_job`: `system` ([calendars](calendars.md)).
  - `note_document`: read any member; create loggers (snapshot, text: `system`); update, delete `system`. `note_update`: the same, without the snapshot.
  - `timeline_entry_provider`, `timeline_entry_todo`: read any member; create and delete writers; update `system`.
  - `care_recipient_details`: read, create, update writers (others none; outside contacts: owner, admin); delete `system`.
  - `user_contact`: yourself only (not staff). `member_contact_share`: read any member; `system` writes.
- `system` has `all` everywhere; only it can change an id pointing at the group.
- **Staff get no default care-data access;** support access will be an audited grant.
- **Write memberships and invites through the services**; they enforce what the map can't:
  - `careGroupService.create` makes the creator the first owner, after `groupLimitService.refusal` (non-system actors): groups started and still owned (user row locked) vs `user.group_limit` (system-only) or `limits.groupsStarted` (read pre-transaction); `groupLimitService:atLimit` (409).
  - Only owners change owners; a group keeps one. `updateRole` and `remove` lock the target and the group's owner rows first (`careGroupMemberModel.lockForChange`, id order).
  - Leaving, removal and a demotion below manager revoke the member's waiting invites and links in the same transaction; an owner who becomes admin loses only their owner invites.
  - Removing or leaving, in one transaction: hands their open todos to a free-text assignee, their name (`todoService.releaseAssignee`), deletes their calendar settings, overrides, feed, disconnects Google (`calendarSettingService`).
  - `careGroupInviteService` (pure rules, consent and attestation texts in `inviteRules.ts`):
    - `createEmail` requires the inviter's attestation, only owners invite owners, refuses members and a second waiting invite, replaces an expired one (7 days). `resend` rotates token and expiry; `revoke` withdraws it. No procedure returns a token.
    - `preview(token)` (public; closed invites never name the group), `ticketFor(token)` (sign-up), `accept` (verified email must match; one `system` transaction: membership with `invitedBy`, consent, email verified, accepted; idempotent), `decline(token)` (anyone holding the link).
    - Accept, link ask, preview and ticket recheck the invite's maker (an owner invite needs a current owner, others a manager); staff/system invites are exempt; a failed recheck reads as revoked.
    - **Links:** `createLink` (managers; caretaker or viewer; 1-90 days, default 7; optional `max_uses`) and `copyLink` (active links; email invites get `notLink`). `accept` with a link goes to `askWithLink`: a member passes, anyone else gets one pending join request (asking again returns it; a declined or withdrawn requester asking within 7 days gets `requested`, no new row or email); `accept` returns `{ status: "joined" | "requested" }`. `invite.decline` refuses links (`wrongKind`). Link sign-up counts one use toward `max_uses` (a `verification` marker, `linkSignUpUses.ts`), so the later join request doesn't count again; a used-up link still reads usable to the person whose sign-up took its use.
  - `joinRequestService`: `requestWithLink`, `approve` (membership with `invitedBy` = the link's maker), `decline`, `withdraw`; writes as `system`, row locked `FOR UPDATE`; non-members get `notFound`, non-managers `notAllowed`. Emails (`JoinMailer`: to owners and admins, then the requester) carry no health details.
  - `accessCodeService` (staff `list`, `getById`, `create`, `revoke`; public `preview`; `redeem(tx, …)` as `system`, code locked) and `staffGroupService.createWithOwnerInvite` (a memberless group, then an owner invite via `createEmail` as `system`, staff attesting; the `ownerInvite` email). `careGroupModel.createWithoutOwner` is staff and system only.
  - The `groupInvite` email (no health details): an injected `InviteMailer`, in the transaction with the invite.
- **Seeds** (`packages/data/src/db/seeds/`): "Dev Family": member@ owner, caretaker@, viewer@, an Easy helper and viewer; `moreGroups.ts`, `accessCodes.ts` (`CARE-DEMO-0001`), `invites.ts`.
- **Easy mode:** `care_group.easy_tiles` jsonb (`easyTilesZSchema`, `db/schema/app-shell/easyMode.ts`: `{ mode: learned | fixed | custom, tiles? }`, custom has exactly 4; null = learned), synced in `care_groups`, written online by `careGroup.update` (`easyTiles`). Unread until a contract migration: `simple_tiles`, `care_group_member.simple_mode`, `simple_mode_locked`. Easy roles get no connectors ([connectors](connectors.md)).
- **Assistants settings** (owners, via `careGroup.update`): `connectors_enabled` (default off; Dev Family on; off revokes all grants, leaving or removal that member's; synced, not uploaded) and `connectors_read_only` (default off; revokes nothing) ([connectors](connectors.md)).
- **Member looks:** only the pure `lib/care-groups/memberLooks.ts` assigns default colors (never stored): chosen ones reserved, then join order, hashed or next free; past ten, repeats. `MemberAvatar` reads `MemberLooksProvider`.
- **UI:** the role picker (`settings/members/RoleOptions.tsx`): regular roles, then "Easier to use" (optgroups). A "What can each role do?" link (`RoleHelp`, a native dialog) sits by the Role label in `InviteSheet`, `InviteLinks` and Manage members (`GROUP_ROLES`). Member cards (`MemberItem.tsx`): identity on its own line, untruncated; role and actions below; managers see email confirmed and last sign-in (`careGroup.memberStatuses`, online only); your own card's "What this group sees" form: a disclosure, closed. `EasyTilesCard` saves via `parseEasyTilesChoice` (no repeats, unknowns or < 4). **Symptoms** subpage: the catalog with entry counts, then Archived; writers archive, owners delete.
