# Care groups

A care recipient's caretakers' shared space: "care group", never "care circle".

- **Tables** (`packages/data/src/db/schema/care-groups/`):
  - `care_group` (`name`); `care_group_member` (`group_id`, `user_id`, `role`, unique per pair; `invited_by` to `user`, set null).
  - `care_recipient`: a profile, not an account; 1:1 via unique `group_id`. **`time_zone`** (IANA, required, no default) is where the recipient lives: schedules use it. Creation sends the device's zone, else `FALLBACK_TIME_ZONE` (UTC); unknown: `careRecipientService:invalidTimeZone`. Writers edit it in Details (`careGroup.updateRecipient`).
  - `care_group_invite` (`kind` `email|link`, `email`, role, SHA-256 `token_hash`, status `pending|accepted|declined|revoked`, `expires_at`, `accepted_by`, `max_uses`/`use_count`, inviter attestation `consent_attested_by`/`_at`, `consent_version`). A link seals its token in `token_ciphertext` (AES-256-GCM, `utils/linkToken.ts`, key `INVITE_LINK_KEY`); an email one's isn't stored. Without it, production and staging refuse `createLink` (`linkKeyMissing`) and the seed (`db:seed:linkKey`); dev and tests: a fixed key. Same key in both `.env`s (unsubscribe tokens derive from it).
  - `care_group_consent`: the joiner's consent, plus the invite's attestation (`consent_attested_by`/`_at`/`_version`; a link's at `requestWithLink`).
  - `care_group_join_request` (`group_id`, `user_id`, `invite_id`, `role` caretaker or viewer (DB check), status `pending|approved|declined|withdrawn`, `decided_by`; one pending per group and user).
  - `access_code` (`code` `XXXX-XXXX-XXXX`, no 0/O/1/I/L, **stored plain** to reprint; `label`, `expires_at`, `max_uses` (null: unlimited), `use_count`, `revoked_at`) and `access_code_redemption` (`group_id` nulled on group delete). Admins and `system` only.
  - **Not synced:** invites and consent rows (addresses; oRPC); of a member, only `invited_by` and `created_at`.
  - Deleting a group cascades to all in it; a user, to their memberships and connector grants. **Evidence stays** (bare ids, no FKs): consent, legal acceptance, the audit log.
- **Two role systems:** global (`admin`, `support`, `member`) is account and staff access only ([admin](admin.md)). Group roles are `owner`, `admin`, `caretaker`, `viewer` and the easy roles, `easy_helper` (logs care, edits only own entries) and `easy_viewer` (reads; ticks own todos); each has `group: regular | easier` for the picker. A role's access is one row of `GROUP_ROLE_CAPABILITIES` (client-safe `constants/roles.ts`); a new role fills a row (and the sync config's non-writer chain). Tests tie its sets and copies (`LINK_ROLES`, staff list, sync config, emails) to it; use its checks (`isOwnerRole`, …), never a role string.
- **Permissions** (`PERMISSIONS[table][action][role]`; **`groupOwn`**: held only on rows the actor created, in SQL, see [data-layer](data-layer.md)):
  - `care_group`: read any member; create any signed-in user (the owner); update owner, admin; delete owner.
  - `care_group_member`: read any member; create owner, admin; update owner, admin (role only); delete owner, admin, yourself.
  - `care_recipient`: read any member; create, delete owner, admin; update owner, admin, caretaker.
  - `care_group_invite`: owner and admin for everything (update: status only).
  - `care_group_consent`, `care_group_join_request`: read owner, admin, yourself; `system` writes.
  - `access_code`: staff for everything (update: not the code or use count). `access_code_redemption`: read staff; `system` writes.
  - `user`: read self, staff, co-members (`PUBLIC_PROFILE_FIELDS`); create staff; update self (not role, email); delete self, staff.
  - `timeline_entry`: read any member; create loggers; update and (soft) delete writers, and an Easy helper on own entries (`groupOwn`), never a setup field, even to clear it. `provider`, `medication`, `care_period`, `medication_pass`, `recipient_allergy`, `recipient_condition`: read any member; writers write (soft delete).
  - `medication_condition`, `condition_manager`: read any member; create and delete writers; update `system`. Services check both ends.
  - `todo`: as above, but update also for viewers (`todoService` limits a viewer and both easy roles to ticking a todo assigned to them, `todoService:completionOnly`; [todos](todos.md)). `appointment_series`: as above (writers).
  - `member_calendar_setting`, `reminder_override`: the member's own rows; the feed hash is `system`. `google_*`, `calendar_sync_job`: `system` ([calendars](calendars.md)).
  - `note_document`: read any member; create loggers (snapshot, text: `system`); update, delete `system`. `note_update`: the same, without the snapshot.
  - `timeline_entry_provider`, `timeline_entry_todo`: read any member; create and delete writers; update `system`.
  - `care_recipient_details`: read, create, update writers (outside contacts: owner, admin); delete `system`.
  - `user_contact`: yourself only (not staff). `member_contact_share`: read any member; `system` writes.
- `system` has `all` everywhere; only it can change an id pointing at the group.
- **Staff get no default care-data access;** support access will be an audited grant.
- **Write memberships and invites through the services**; they enforce what the map can't:
  - `careGroupService.create` makes the creator the first owner, unless `groupLimitService.refusal` (non-system): groups started and still owned (user locked) vs `user.group_limit` or `limits.groupsStarted`; `atLimit` (409).
  - Only owners change owners; a group keeps one. `updateRole` and `remove` lock the target and owner rows first (`lockForChange`, id order).
  - Leaving, removal and a demotion below manager revoke the member's waiting invites and links; an owner made admin loses only owner invites.
  - Removing or leaving, in one transaction: their open todos go to a free-text assignee, their name (`releaseAssignee`); their calendar settings, overrides and feed go; Google is disconnected.
  - **Deleting a group:** `careGroupService.remove` (owners, the typed name, `confirmsGroupName`; `careGroup.delete`, online). As `system`, `deleteGroup(tx, …)` (reused by account deletion) revokes grants, disconnects Google, skips waiting mail (`groupDeleted`: reminder key, a `/app/groups/<id>` link or its invites' keys), audits `group.deleted`, hard-deletes. Details' last card.
  - **A last owner deleting their account** waits until each shared group is handed over or deleted; a sole-member one goes with it.
  - `careGroupInviteService` (pure rules, consent and attestation texts in `inviteRules.ts`):
    - `createEmail` needs the inviter's attestation, only owners invite owners; refuses members and a second waiting invite, replaces an expired one (7 days). `resend` rotates token and expiry; `revoke` withdraws it. No procedure returns a token.
    - `preview(token)` (public; a closed invite never names the group), `ticketFor(token)` (sign-up), `accept` (verified email must match; one idempotent `system` transaction: membership with `invitedBy`, consent, email verified), `decline(token)` (anyone holding the link).
    - Accept, link ask, preview and ticket recheck the maker (an owner invite needs a current owner, others a manager; staff and system exempt); a failed recheck reads as revoked.
    - **Links:** `createLink` (managers; caretaker or viewer; 1-90 days, default 7; optional `max_uses`) and `copyLink` (active links; email invites get `notLink`). `accept` with a link goes to `requestWithLink`: a member passes; anyone else gets one pending join request (asking again returns it; declined or withdrawn within 7 days: `requested`, no new row or email): `{ status: "joined" | "requested" }`. `invite.decline` refuses links (`wrongKind`). Link sign-up takes one use (a `verification` marker, `linkSignUpUses.ts`); its join request none, and the link still reads usable to them.
  - `joinRequestService`: `requestWithLink`, `approve` (membership with `invitedBy` = the link's maker), `decline`, `withdraw`; as `system`, row locked; non-members `notFound`, non-managers `notAllowed`. Emails (`JoinMailer`: to owners and admins, then the requester) carry no health details.
  - `accessCodeService` (staff `list`, `getById`, `create`, `revoke`; public `preview`; `redeem(tx, …)` as `system`, code locked) and `staffGroupService.createWithOwnerInvite` (a memberless group, then an owner invite via `createEmail`, staff attesting; `ownerInvite` mail). `careGroupModel.createWithoutOwner` is staff and system only.
  - The `groupInvite` email (no health details): an injected `InviteMailer`, in the invite's transaction.
- **Seeds** (`packages/data/src/db/seeds/`): "Dev Family": member@ owner, caretaker@, viewer@, an Easy helper and viewer; `moreGroups.ts`, `accessCodes.ts` (`CARE-DEMO-0001`), `invites.ts`.
- **Easy mode:** `care_group.easy_tiles` jsonb (`easyTilesZSchema`, `app-shell/easyMode.ts`: `{ mode: learned | fixed | custom, tiles? }`, custom exactly 4; null: learned), synced, set online by `careGroup.update`. Unread, awaiting contract: `simple_tiles`, `simple_mode`, `simple_mode_locked`. Easy roles: no connectors.
- **Assistants settings** (owners, via `careGroup.update`): `connectors_enabled` (default off, Dev Family on; off revokes all grants, leaving that member's; synced, not uploaded) and `connectors_read_only` (default off; revokes nothing) ([connectors](connectors.md)).
- **Member looks:** only the pure `lib/care-groups/memberLooks.ts` assigns default colors (never stored): chosen ones reserved, then by join order; past ten, repeats. `MemberAvatar` reads `MemberLooksProvider`.
- **UI:** the role picker (`settings/members/RoleOptions.tsx`): regular roles, then "Easier to use" (optgroups). `RoleHelp` ("What can each role do?") sits by Role in the invite sheets and Manage members. Member cards (`MemberItem.tsx`): identity untruncated, role and actions below; managers see email status and last sign-in (`memberStatuses`, online); your own card's "What this group sees": a closed disclosure. `EasyTilesCard` saves via `parseEasyTilesChoice` (no repeats, unknowns or < 4). **Symptoms** subpage: the catalog with entry counts, then Archived; writers archive, owners delete.
