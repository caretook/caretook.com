# Care groups

The care groups area's rules and decisions.

The shared space for one care recipient's caretakers: always "care group", never "care circle".

- **Tables** (`packages/data/src/db/schema/care-groups/`):
  - `care_group` (`name`); `care_group_member` (`group_id`, `user_id`, `role`, unique per pair; `invited_by` to `user`, set null).
  - `care_recipient`: a profile, not an account; 1:1 through a unique `group_id`. **`time_zone`** (IANA, required, no database default) is where the recipient lives: medication schedules are in it. Group creation sends the device's zone (`newGroupFromForm`); services fall back to `FALLBACK_TIME_ZONE` (UTC); an unknown zone is `careRecipientService:invalidTimeZone`. Writers change it in Details through `careGroup.updateRecipient`; `GroupContext.recipient.timeZone` carries it to screens.
  - `care_group_invite` (`kind` `email|link`, `email` for email invites, role, SHA-256 `token_hash`, status `pending|accepted|declined|revoked`, `expires_at`, `accepted_by`, `max_uses`/`use_count`, the inviter's attestation `consent_attested_by`/`_at` with `consent_version`). A link invite keeps its token sealed in `token_ciphertext` (AES-256-GCM, `utils/linkToken.ts`, keyed from `INVITE_LINK_KEY`); an email invite's token is never stored. Production without a key refuses `createLink` (`linkKeyMissing`); dev and tests use a fixed key. Set `INVITE_LINK_KEY` the same in `apps/web/.env` and `packages/data/.env`; reminder unsubscribe tokens derive from it.
  - `care_group_consent`: the joiner's consent.
  - `care_group_join_request` (`group_id`, `user_id`, `invite_id`, `role` caretaker or viewer (a DB check), status `pending|approved|declined|withdrawn`, `decided_by`; one pending per group and user).
  - `access_code` (`code`, `XXXX-XXXX-XXXX` without 0/O/1/I/L, **stored plain** so staff can reprint it; `label`, `expires_at`, `max_uses` (null = unlimited), `use_count`, `revoked_at`) and `access_code_redemption` (`group_id` set null on group delete). Admins and `system` only; a code is a sign-up ticket.
  - **Not synced:** invites and consent rows (managers' data with addresses; oRPC). Only a member's `invited_by` and `created_at` sync.
  - Deleting a group cascades to everything in it; deleting a user, to their memberships.
- **Two role systems:** global (`admin`, `support`, `member`) covers account and staff access only (see [admin](admin.md)). Group roles on the membership are `owner`, `admin`, `caretaker`, `viewer` and the two easy roles, `easy_helper` (logs care, edits only own entries) and `easy_viewer` (reads; ticks own todos); each has `group: regular | easier` for the picker. Role sets live in `constants/roles.ts` (client-safe) and are re-exported from permissions: `WRITERS` (owner, admin, caretaker), `LOGGERS` (`WRITERS` + `easy_helper`), `EASY_ROLES`, `OWN_ROW_LOGGERS` (loggers who aren't writers), `MANAGERS`, `OWNERS`. Never compare a role string outside them.
- **Permissions** (`PERMISSIONS[table][action][role]`; "any member" reads; **`groupOwn`**: the permission holds only on rows the actor created, in SQL, see [data-layer](data-layer.md)):
  - `care_group`: read any member; create any signed-in user (becomes owner); update owner, admin; delete owner.
  - `care_group_member`: read any member; create owner, admin; update owner, admin (role only); delete owner, admin, or yourself.
  - `care_recipient`: read any member; create and delete owner, admin; update owner, admin, caretaker.
  - `care_group_invite`: owner and admin for everything (update: status only).
  - `care_group_consent`, `care_group_join_request`: read owner, admin, yourself; writes `system`.
  - `access_code`: staff for everything (update: not the code or use count). `access_code_redemption`: read staff; `system` writes.
  - `user`: read self, staff and co-members (id, name, image); create staff; update self (no role or email); delete self and staff.
  - `timeline_entry`: read any member; create loggers; update and (soft) delete writers, and an Easy helper on own entries (`groupOwn`), never changing a setup field, even to clear it. `provider`, `medication`, `care_period`, `medication_pass`, `recipient_allergy`, `recipient_condition`: read any member; create, update and (soft) delete writers.
  - `medication_condition`, `condition_manager` (`medicationConditionSchema`, `conditionManagerSchema`): read any member; create and delete writers; update `system`. Written through their services, which check both ends.
  - `task`: as above, but update also for viewers ¹. `appointment_series`: as above (writers).
  - `member_calendar_setting`, `reminder_override`: the member's own rows only; the feed hash is `system`. `google_*`, `calendar_sync_job`: `system` only ([calendars](calendars.md)).
  - `note_document`: read any member; create loggers (snapshot and text: `system`); update and delete `system`. `note_update`: read any member; create loggers; update and delete `system`.
  - `timeline_entry_provider`: read any member; create and delete writers; update `system`.
  - `care_recipient_details`: read, create and update writers (others none; outside contacts: owner, admin); delete `system`.
  - `user_contact`: yourself only for everything (not staff). `member_contact_share`: read any member; writes `system`.
- ¹ `todoService` limits a viewer and both easy roles to ticking or unticking a todo assigned to them (`todoService:completionOnly`, one rule and one error for all three); see [todos](todos.md).
- `system` has `all` everywhere. Ids that point at the group can't be changed except by `system`.
- **Staff get no default access to care data;** any support access will be an explicit, audited grant.
- **Write memberships and invites through the services**; they enforce what the map can't:
  - `careGroupService.create` makes the creator the first owner.
  - Only owners add, change or remove owners. A group keeps at least one owner (rows lock `FOR UPDATE`).
  - Removing or leaving, in the same transaction: hands the user's open todos to a free-text assignee (their name; `todoService.releaseAssignee`), deletes their calendar settings, overrides and feed, and disconnects their Google (`calendarSettingService.removeForMember`, `googleConnectionService`).
  - `careGroupInviteService` (rules in the pure, client-safe `inviteRules.ts`, with the consent and attestation texts and versions):
    - `createEmail` requires the inviter's attestation, only owners invite owners, refuses current members and a second waiting invite, and replaces an expired one (7-day expiry). `resend` rotates the token and resets the expiry; `revoke` withdraws it. No procedure returns a token.
    - `preview(token)` (public; closed invites never name the group), `ticketFor(token)` (for sign-up), `accept` (the signed-in, verified email must match; one transaction as `system`: membership with `invitedBy`, consent row, email verified, invite accepted; idempotent) and `decline(token)` (anyone holding the link).
    - **Links:** `createLink` (managers; caretaker or viewer only; 1-90 days, default 7; optional `max_uses`) and `copyLink` (active links only; an email invite gets `notLink`). `accept` with a link goes to `askWithLink`: a member passes, anyone else gets one pending join request (asking again returns it); `accept` returns `{ status: "joined" | "requested" }`. `invite.decline` refuses links (`wrongKind`).
  - `joinRequestService`: `requestWithLink`, `approve` (the membership with `invitedBy` = the link's maker), `decline`, `withdraw`; every write as `system`, row locked `FOR UPDATE`; non-members get `notFound`, non-manager members `notAllowed`. Its emails (owners and admins on a request; the outcome to the requester) go through an injected `JoinMailer`, with no health details.
  - `accessCodeService` (staff `list`, `getById`, `create`, `revoke`; public `preview`; `redeem(tx, …)` as `system`, code locked `FOR UPDATE`) and `staffGroupService.createWithOwnerInvite` (a memberless group and recipient, then an owner invite through `createEmail` as `system` with the staff member as attester; the `ownerInvite` email). `careGroupModel.createWithoutOwner` is staff and system only.
  - The `groupInvite` email (no health details) goes through an injected `InviteMailer` in the service's transaction (invite and outbox row commit together), then `deliverSoon`.
- **Seeds** (`packages/data/src/db/seeds/`): "Dev Family" (Grandma Pat) has member@ as owner, caretaker@, viewer@, an Easy helper and an Easy viewer. `secondGroup.ts` gives member@ a second group (`/app` lists groups on a fresh device); `moreGroups.ts` adds multi-role users (trio@, groupadmin@, viewer2@, owner2@, solo@ as sole owner) in four time zones; `accessCodes.ts` adds `CARE-DEMO-0001`; `invites.ts` adds `joiner@example.com` with a pending join request, an email invite and a viewer link. admin@ is no member.
- **Easy mode data:** `care_group.easy_tiles` jsonb (`easyTilesZSchema` in `db/schema/app-shell/easyMode.ts`: `{ mode: learned | fixed | custom, tiles? }`, custom carries exactly 4; null = learned), synced through the `care_groups` stream and the device schema, written online by `careGroup.update` (`easyTiles`). Unread until a contract migration: `simple_tiles`, `care_group_member.simple_mode` and `simple_mode_locked`, the old preference key. There are no Members switches (`setMemberMode` is deleted); migration 0036 turned locked caretakers into Easy helpers and locked viewers into Easy viewers (locked owners, admins keep theirs) and dropped a stored `group` setting. Connectors are refused for easy roles ([connectors](connectors.md)).
- **The assistants switch:** `care_group.connectors_enabled` (default false; Dev Family seeded on), owners only through `careGroup.update`. Off revokes every connector grant in the same transaction; removing or leaving revokes that member's. Synced, not uploaded ([connectors](connectors.md)).
- **UI:** the role picker (`settings/members/RoleOptions.tsx`) lists the four regular roles, then "Easier to use", as native optgroups, with each role's description. The tiles card in Details (`EasyTilesCard`) saves through `parseEasyTilesChoice` (`groupSettings.ts`: refuses fewer than four, repeats and unknown tiles).
