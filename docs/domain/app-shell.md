# The `/app` frame

The `/app` frame area's rules and decisions, moved out of AGENTS.md (whose core rules still apply). An orchestrator folds a landing's lasting decisions for this area in here.

**The `/app` frame** (`routes/app/layout/route.tsx`, a hot file): fixed regions that slices and PRDs fill through their components, never by restructuring the layout:

- header `group` (left): the Caretook link (`Wordmark` from `components/brand/`; mark only below `sm` on group routes, the word kept as screen-reader text so the link's name stays "Caretook"), then `GroupMenu` on group routes. The header matches the marketing header's look (`h-16`, `border-b border-base-300`, `bg-base-100/95 backdrop-blur`, `px-4 sm:px-6`), full width, and is deliberately not sticky (the timeline's day headers stick at the top);
- header `sections` (`hidden sm:flex`): `SectionNav` on group routes;
- header `status`: `SyncIndicator`;
- header `user`: `UserMenu`;
- the outlet, then `TabBar` (phones, group routes).
- The `groupId` comes from `useParams()`; screens outside a group (`/app`, `/app/settings`) get the header only.
- **Routes are a nested tree** in `routes.ts` (explicit config, no file-system routing): the `app` layout → `home`, `settings`, and the `group` layout (`/app/groups/:groupId`) → an index that redirects to the timeline, `timeline`, `entries/:entryId` and `settings`. **A folder per route:** `routes/app/<area>/<page>/route.tsx`, with the components and helpers only that route uses beside it; a file moves to `components/` only when a second route uses it.
- **The group route** (`routes/app/groups/layout/route.tsx`): its `clientMiddleware` loads the group once per navigation, before any child loader. **Client middleware works in both builds** (React Router 8.5.1, no flag). `lib/group.tsx`: `setGroup` records the group, or the `notOnDevice` error, and **never throws**, because a middleware throw on native's first load renders the root boundary, not /app's. Every loader and action under the group route calls `getGroup(context)` first (it throws the recorded error into /app's boundary). Components read `useGroup()`: a typed, read-only `GroupContext` (`lib/groupContext.ts`: `userId`, `id`, `name`, `displayName`, `role`, `canWrite`, `recipient`), live through `myGroupQuery`, keeping the last value if the group leaves the device. Screens never query the group, role or membership themselves.
- **`appUrls`** (`lib/appUrls.ts`, pure, tested) builds every `/app/…` path and carries search params through (`home`, `settings`, `groupHome`, `timeline(groupId, search)`, `entry`, `newEntry`, `groupSettings`). **Nothing else writes an `/app/…` string**; a new route adds its builder there.
- **`UserMenu`:** a RAC menu on the avatar ("Account menu for …"): a name and email header, Settings, a **Theme** section (System, Light, Dark; its own `MenuSection` with `selectionMode="single"`, so its items are `menuitemradio`), and Sign out (POST to `/sign-out`).
- **Theme** (`lib/theme.ts`): per device in `caretook:theme`, never sent to the server, and kept at sign-out. Light and Dark set `data-theme` on `<html>`; System removes it (and stores nothing), so daisyUI follows `prefers-color-scheme`. `THEME_SCRIPT`, inline first in `root.tsx`'s `<head>` (both targets), applies it before first paint; `<html>` has `suppressHydrationWarning` for it. Storage that throws falls back to System. (With storage blocked, React Router's own `ScrollRestoration` script throws a `SecurityError`; not ours.)
- **`GroupMenu`:** the current group's display name (recipient's preferred name or name, then the group name) as a RAC menu ("…: switch care group") listing every local group (live, offline), the current one checked (`menuitemradio`); choosing one opens its timeline. The trigger shows the current care period's type icon after the name (its name in the button's label, "Grandma Pat, Hospital: switch care group", and its `title`; `data-period-icon`). After a separator, "Now: In hospital · day N" (only with a period; opens it), "<Name>'s profile" (profiles), "Group settings" opens `/app/groups/:groupId/settings`, "Care periods" opens the periods page, then "New care group" opens `/app/groups/new` (with `NEW_GROUP_LINK_STATE`, so closing the sheet comes back). It reads the user id from the layout's loader data (`useRouteLoaderData`), not `getSync()`, which throws while signing out.
- **Last group** (`lib/lastGroup.ts`): a group route you're a member of is saved as `caretook:lastGroup:<userId>`; sign-out runs `forgetGroups()` (and `forgetRecentSearches()`). `/app`'s loader redirects by the pure `resolveHomeGroup({ groups, remembered })`: the remembered group if you're still in it, else the only group, else the list.
- **Group sections** (`lib/groupSections.ts`): `GROUP_SECTIONS`, an ordered `{ id, label, icon, path(groupId), match(subpath) }` list (Timeline, Providers, Medications, Upcoming; Timeline's `match` also claims `/entries/*`). **A later PRD adds a section by appending one entry and its route**; the shell needs no edit. `SectionNav` (header links) and `TabBar` (a daisyUI `dock`, `sm:hidden`, `z-40`) render it with `aria-current` (`"page"` on the section's page, `"true"` inside it). Both navs are named "Group sections"; only one shows. The bar is hidden on `/entries/*`; elsewhere it renders an in-flow spacer of `--tab-bar-height` (`app.css`), so screens never offset for it. Anything else fixed to the bottom of a group screen offsets by that variable. Modals (`z-50`) cover it.
- **Group settings** (`/app/groups/:groupId/settings`, `routes/app/groups/settings/`; not a section, so the tab bar shows with nothing current): the same `SettingsFrame` as account settings, with the registry `groupSettingsPages(groupId)` (`layout/settingsPages.ts`) and `appUrls.groupSettings(groupId, page?)`. Subpages: **Details** (`details`; the `group-details` card and a `care-recipient` card with only the recipient's **time zone** (`RecipientTimeZoneForm`, intent `updateRecipient` with `timeZone` only; read-only text for viewers and offline) and a link to the recipient's profile, where everything else about them is edited) and **Members** (`members`, `data-section="members"`; intents `changeRole` and `removeMember`). **Writes are online only**: each subpage's `clientAction` calls oRPC. Offline, or without the role, a card is a read-only `<dl>` with no controls, and the page says "Needs a connection to edit" (`SettingsPage` from `components/settings`; `api.ts` has `loadRecipientProfile` and `failedSave`). `groupSettings.ts` beside them has the pure parts: `groupSettingsAccess` (through `hasPermission`), `parseGroupName`, `parseRecipientTimeZone`, `timeZoneOptions` and `timeZoneLabel` (the shared Zod schemas, with the field messages).
  - **Members:** every member (avatar, name with "(you)", role), live from local data, sorted by role then name (`sortMembers`, `memberAccess`, `roleLabel`). Online, owners and admins get a native role `<select>` and Remove; everyone gets Leave on their own row; both go through one `ConfirmDialog`. Only owners are offered Owner or controls on an owner's row. The service's owner-only and last-owner messages are shown as they are (`memberRefusal`).
  - **Invites** (beside `members/route.tsx`: `InviteSheet.tsx`, `PendingInvites.tsx`, `invites.ts`, `inviteApi.ts`, all on the `ui/` primitives): owners and admins get **Invite by email** (email, role, the attestation checkbox) and a **Pending** list (role, sender, expiry, Resend, Revoke behind a `ConfirmDialog`). Offline the button is disabled with "Needs a connection to invite." Hooks are `data-invite-controls` and `data-pending-invites` (`app-shell.mjs` expects `members` as the page's only `data-section`).
  - **Links and requests** (`InviteLinks.tsx`, `JoinRequests.tsx`, `linkApi.ts`, the pure `linkRules.ts`): "Create a link" (role, expiry, uses), active links with Copy and Share (Web Share, else clipboard; each row fetches its URL through `copyLink` when it appears, so the tap itself can copy), uses and Revoke; and a **Requests** list (name, email, role, Approve, Decline behind a confirm). `app-shell.mjs` scopes its member assertions to `li[data-member]`, because these rows show addresses. The requester's `/app` home shows "Waiting for approval: <group>" or "Not approved: <group>" (`home/PendingRequests.tsx`), hidden once the group is on the device; their device holds no group data until then. A waiting request has **Withdraw** (behind a `ConfirmDialog`, online only; home's `clientAction` calls `joinRequest.withdraw`; a request no longer pending counts as gone).
- **New care group** (`/app/groups/new`, `appUrls.newGroup()`; a route under the app layout, not the group route): a `Sheet` with `NewGroupFields` (recipient name, preferred name, group name defaulting to "<name>'s care"). Online only; after `careGroup.create` it waits up to 10 s (`waitForMembership`) and opens the new timeline, else `/app`. Reached from the group menu and `/app` home (`home/NewGroupLink.tsx`). `NewGroupFields` and `newGroupFromForm` live in `components/groups/` (shared with `/join/:code`); `NEW_GROUP_LINK_STATE` and `openedNewGroupFromApp` are in `lib/newGroupLink.ts` (pure, no React, like `lib/timelineSheet.ts`).
- **Invite someone** (`timeline/InviteSomeoneCard.tsx`): owners and admins of a group with no other members see a card linking to Members (on member@'s Dev Family 2 too). `useLiveQuery` compares `initial` by identity: pass a module constant, never a literal, or React loops (error #301).
- **`/join/:code`** (shared, client-only, `accountUrls.join()`): an account form, then "Who do you care for?"; one call creates everything, the confirmation email's `callbackURL` is `/app` (which opens the only group), and the page goes to `/verify-email` for every address, existing or new. Signed in → points to New care group. Expired, revoked, used-up and unknown codes get a plain message.
- **`/admin/*`** (web only, server loaders through `.server/admin.ts`): staff (`admin`, `support`) only, by capability (see [admin](admin.md)); anyone else gets a 404 (group owners too), signed-out visitors go to sign-in. Access codes (list with uses, create, revoke), New group (owner invite), and `/admin/access-codes/:id/print`: an SVG QR (`qrcode` 1.5.4, server only, never in a client or native chunk) for `/join/<code>` on `APP_URL`, with the code in large type. Admin screens show no care data.
  - **`/invite/:token`** (`routes/account/invite/`, shared, client-only; wording in `invitePage.ts`): preview → sign up with the email locked (or sign in) → consent → Join, or Decline; a wrong-account view offers Sign out and comes back (`/sign-out` honours a `safeRedirect`-checked `redirectTo`); expired, revoked, accepted and declined links say so without naming the group. After Join it waits for the membership to sync (`waitForMembership` in `lib/sync/members.ts`), then opens the group.
  - **Leaving waits for the device:** `/app` reads the local copy, so the action waits up to 10 s for the membership to sync away (`waitForMembershipGone` in `lib/sync/members.ts`) before redirecting to `/app`. On a slower sync the user lands back on the group until it goes.
- **Settings** (`/app/settings`, `routes/app/settings/`): a list of subpages from the `ACCOUNT_SETTINGS` registry (`id`, label, description, icon, path), rendered by `SettingsFrame` (`components/`, shared with group settings): one `nav[data-settings-nav]` with `aria-current` (`settingsCurrent` in `lib/settingsNav.ts`). On phones (below `md`) the index is the list and a subpage has a back link to it; from `md` the list is a side nav and the index redirects to the first subpage (`isWideSettings()`), and widening the window on the list opens it. Subpages, each its own route built by `appUrls.settings(page)`: **Units** (`units`), **Timeline layout** (`timeline`; Rows or Cards, saved on change through `saveSettings`, the same save as the timeline's toggle; read through `loadSettings`, so a pending change shows at once), **Account** (`account`; name and email, read-only, and Sign out), Contact details, and **Devices** (`devices`, last; B-80): Better Auth's `listSessions`, `revokeSession`, `revokeOtherSessions` (tokens never reach the page: the action looks them up by session id), this device first, labels from the pure `lib/deviceLabel.ts` ("Chrome on macOS"), Sign out per device behind a `ConfirmDialog` and Sign out everywhere else; online only. Better Auth's `session.freshAge` is `0`, or `list-sessions` refuses sessions older than a day (it also drops the freshness check on `deleteUser`/unlink, unused). `devices.mjs` checks it.
- **Avatars:** `UserAvatar` (image, or initials if it's missing or fails to load) is shared by the user menu and `EditorAvatars`. `lib/initials.ts` has `initials(name)` and `userInitials({ name, email })` (name, then the email's first letter, then "?"). `SessionUser` carries an optional `image`.
- **Tests:** screen behaviour is in `routes/app/layout/frame.browser.test.tsx` and the settings component tests. `app-shell.mjs` keeps the theme before first paint, sign-out, a rename through the server and back, and role changes and a removal reaching a second device; every sign-in in it is on a fresh page (signing in again on a page that just signed out can hit Better Auth's per-IP limit, B-113).
