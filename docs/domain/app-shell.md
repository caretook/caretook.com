# The `/app` frame

The `/app` frame area's rules and decisions.

**The `/app` frame** (`routes/app/layout/route.tsx`, a hot file): fixed regions that slices and PRDs fill through their components, never by restructuring the layout:

- header `group` (left): the Caretook link (mark only below `sm` on group routes, the word kept as screen-reader text), then `GroupMenu` on group routes. The header isn't sticky (the timeline's day headers stick at the top);
- header `sections` (`hidden sm:flex`): `SectionNav`; `status`: `SyncIndicator`; `user`: `UserMenu`;
- the outlet, then `TabBar` (phones, group routes), then `update`: `UpdateNotice` ("A new version is ready" · Reload).
- **The service worker** (web production builds only; `entry.client.tsx` registers it, so dev and native have none): `lib/app-shell/serviceWorker*.ts`, bundled to `/sw.js` by `scripts/build/service-worker.mjs` in React Router's web `buildEnd`. Install caches the server's own `/app` document (with its headers; it holds no care data) and every JS and CSS asset, versioned by their hash; `/app/*` navigations get that shell, assets come cache-first, everything else goes to the network (`routeRequest`, pure). A new worker waits until Reload posts `skip-waiting`; it never takes over by itself. ⚠ The cached shell keeps the CSP of its build until the next worker installs.
- Screens outside a group get the header only.
- **Routes are a nested tree** in `routes.ts` and the area `routes.ts` parts it spreads in: the `app` layout → `home`, `settings`, and the `group` layout (`/app/groups/:groupId`) → an index redirecting to the timeline, `timeline`, `entries/:entryId`, `settings`. **A folder per route:** `routes/app/<area>/<page>/route.tsx`, with what only that route uses beside it; a file moves to `components/` only when a second route uses it.
- **The group route** (`routes/app/groups/layout/route.tsx`): its `clientMiddleware` loads the group once per navigation, before any child loader. **Client middleware works in both builds.** `lib/app-shell/group.tsx`: `setGroup` records the group or the `notOnDevice` error and **never throws** (on native's first load that would render the root boundary). Every loader and action under it calls `getGroup(context)` first (it throws the recorded error into /app's boundary). Components read `useGroup()`, live. Screens never query the group, role or membership themselves.
- **`appUrls`** (`lib/app-shell/appUrls.ts`, composed from the `lib/<area>/urls.ts` parts) builds every `/app/…` path and carries search params through. **Nothing else writes an `/app/…` string**; a new route adds its builder to its area's `urls.ts`.
- **`UserMenu`:** Settings, a **Theme** section (System, Light, Dark; single-selection), and Sign out (POST to `/sign-out`).
- **Theme** (`lib/app-shell/theme.ts`): per device in `caretook:theme`, never sent to the server, kept at sign-out. Light and Dark set `data-theme` on `<html>`; System removes it (and stores nothing), so daisyUI follows `prefers-color-scheme`. `THEME_SCRIPT`, inline first in `root.tsx`'s `<head>`, applies it before first paint.
- **`GroupMenu`:** a menu of every local group (live, offline), the current one checked; choosing one opens its timeline. The trigger shows the current care period's type icon. Then "New care group" (`NEW_GROUP_LINK_STATE`, so closing the sheet comes back), a separator, the profile, Care periods and Group settings last (no period line). It reads the user id from the layout's loader, not `getSync()`.
- **Last group** (`lib/app-shell/lastGroup.ts`): a group route you belong to is saved per user; sign-out forgets it. `/app`'s loader redirects by the pure `resolveHomeGroup`: the remembered group if you're still in it, else the only group, else the list.
- **Group sections** (`lib/app-shell/groupSections.ts`): `GROUP_SECTIONS`, an ordered `{ id, label, icon, path(groupId), match(subpath) }` list (Timeline's `match` also claims `/entries/*`). Four: Timeline, Providers, Medications (opens its Schedule tab), Planner (`CalendarCheck`; its `match` takes `/planner…` and `/todos…`). **A later PRD adds a section by appending one entry and its route**; the shell needs no edit. Planner, which replaced Upcoming and Tasks, is the one deliberate exception. `SectionNav` and `TabBar` (a daisyUI `dock`, `sm:hidden`) render it with `prefetch="render"` and `aria-current` from the pending navigation (`useNavigation().location`). The bar is hidden on `/entries/*`; elsewhere an in-flow spacer of `--tab-bar-height` (`app.css`) means screens never offset for it, and anything else fixed to the bottom of a group screen offsets by that variable.
- **Group settings** (`/app/groups/:groupId/settings`, `routes/app/groups/settings/`; not a section): the same `SettingsFrame` as account settings, with `groupSettingsPages(groupId)` (`layout/settingsPages.ts`) and `appUrls.groupSettings`. Subpages: **Details** (the group card, the recipient's **time zone**, the owners' details switch; the rest is in the profile), **Members**, **Assistants** ([connectors](connectors.md)) and **Calendar & reminders** (`appUrls.calendarSettings`, [calendars](calendars.md); it holds the owners' details switch). **Writes are online only**: each subpage's `clientAction` calls oRPC. Offline or without the role, a card is read-only and says "Needs a connection to edit".
  - **Members:** live from local data, sorted by role then name. Online, owners and admins get a role select and Remove; everyone gets Leave on their own row. Only owners are offered Owner or controls on an owner's row.
  - **Invites** (beside `members/route.tsx`): owners and admins get **Invite by email** (with the attestation checkbox) and a **Pending** list; offline the button is disabled. Invite links and a **Requests** list (Approve, Decline) sit beside them. The requester's `/app` home shows the request's state (`home/PendingRequests.tsx`), hidden once the group is on the device; their device holds no group data until then. A waiting request can be **Withdrawn** (online only).
- **New care group** (`/app/groups/new`, `appUrls.newGroup()`; under the app layout, not the group route): a `Sheet` with `NewGroupFields`, shared with `/join/:code` (`components/groups/`). Online only; after `careGroup.create` it waits up to 10 s (`waitForMembership`) and opens the new timeline, else `/app`. `NEW_GROUP_LINK_STATE` is in `lib/care-groups/newGroupLink.ts` (pure).
- **Invite someone** (`timeline/InviteSomeoneCard.tsx`): owners and admins of a group with no other members see a card linking to Members.
- **`/join/:code`** (shared, client-only): an account form, then "Who do you care for?"; one call creates everything, the confirmation email's `callbackURL` is `/app`, and the page goes to `/verify-email` for every address. Signed in → points to New care group.
- **`/admin/*`** (web only, server loaders through `.server/admin.ts`): staff only, by capability (see [admin](admin.md)); anyone else gets a 404 (group owners too), signed-out visitors go to sign-in. Admin screens show no care data.
  - **`/invite/:token`** (`routes/account/invite/`, shared, client-only): preview → sign up with the email locked (or sign in) → consent → Join, or Decline; a wrong-account view offers Sign out and comes back; dead links say so without naming the group. After Join it waits for the membership to sync, then opens the group.
  - **Leaving waits for the device:** `/app` reads the local copy, so the action waits up to 10 s for the membership to sync away (`waitForMembershipGone`, in `lib/care-groups/members.sync.ts`) before redirecting.
- **Settings** (`/app/settings`, `routes/app/settings/`): subpages from the `ACCOUNT_SETTINGS` registry, rendered by `SettingsFrame` (shared with group settings): one `nav[data-settings-nav]` with `aria-current` (`settingsCurrent`). On phones the index is the list; from `md` it's a side nav and the index redirects to the first subpage. Subpages (`appUrls.settings(page)`): Units, **Timeline layout** (saved on change through `saveSettings`, read through `loadSettings` so a pending change shows at once), Account, Contact details, and **Devices** (last): Better Auth's session list and revokes, then Connected assistants (tokens never reach the page: the action looks them up by session id), online only. Better Auth's `session.freshAge` is `0`, or `list-sessions` refuses day-old sessions.
- **Tests:** screen behaviour is component tests (`routes/app/layout/frame.browser.test.tsx` and the settings tests); browser checks keep only what needs the server.
- **Easy mode** (the view is in [timeline](timeline.md)): `resolveEasyMode({ role, ownerDefault, locked, ownSetting, deviceToggle })` (`lib/assistant/easyMode.ts`) decides it: a lock wins, then this device's toggle, then the user's setting, then the owner's default; viewers get no inputs. The toggle (`lib/assistant/easyModeToggle.ts`, per user and group in localStorage) is cleared when the user changes their own setting and forgotten at sign-out (`wipeDevice`). It's never shown while locked. In easy mode the frame (`layout/useEasyFrame.ts`) drops the group menu, sections and tab bar (search too while locked), and `UserMenu easy` has Settings, Full app (unless locked) and Sign out. The header reads the user's setting from `cachedSettings(userId)` (`lib/app-shell/me.ts`), which the timeline loader refreshes before render.
- **The account setting:** the Timeline layout page's "Easy mode" card (`user.preferences.easyMode`: `group | easy | full`), saved through `saveSettings`.
- **The easy-mode lock** (`lib/assistant/easyModeLock.ts`, `lockedRedirect`, pure): a locked member may stay on the timeline, its sheets and `entries/*`; every other group route redirects to the timeline. It's enforced once, in the group layout route (middleware, plus `LockedRedirect` in `GroupProvider` for a lock that syncs in while elsewhere), never per route. A locked member gets the reduced header everywhere in that group, and `UserMenu easy` adds "Your care groups" when they have several: `appUrls.groupList()` is `/app?groups=1`, which skips home's remembered-group redirect.
